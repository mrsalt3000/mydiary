# AGENTS.md — операционный контракт для агентов

Назначение проекта: локальный (local-first) однопользовательский личный дневник для WSL 2: текстовые сообщения, голосовые сообщения с ручной транскрипцией, история в SQLite, еженедельная TXT-выгрузка и три производных слоя — нормализация (слой 2), саммаризация (слой 3), осторожная wellbeing-рефлексия (слой 4).

Этот документ — обязательный контракт для любого агента (включая будущие сессии) при работе в этом репозитории. Он специфичен для данного проекта; общие руководства применяются только там, где они не противоречат этому файлу.

## 1. Границы MVP и авторитетность

- MVP покрывает задачи Task 01–19 из `tasklist.md`. За пределами MVP — только пост-MVP бэклог из `tasklist.md`; он не реализуется без нового явного списка задач или подтверждения пользователя.
- Источник истины по продукту и порядку работ: `tasklist.md` (авторитетный бэклог, исполняется строго по порядку).
- Порядок авторитетности при разрешении противоречий:
  1. Прямые инструкции пользователя в текущем разговоре;
  2. `tasklist.md` (порядок задач, скоуп, критерии приёмки);
  3. `AGENTS.md` (этот документ);
  4. ADR в `docs/decisions/` и описания навыков в `skills/`;
  5. локальные конвенции кода (см. §12) и общая практика.
- Если спецификация задачи внутренне противоречива или противоречит более авторитетному документу — не выбирать сторону молча. Сначала эмпирически проверить поведение/факты, затем показать конфликт пользователю с вариантами разрешения и дождаться решения.

## 2. Обязательный цикл работы над задачей

Ни одна задача из `tasklist.md` (включая Task 01) не выполняется без следующего цикла:

1. Прочитать задачу полностью; изучить релевантные файлы репозитория (read-only).
2. Выполнить письменный анализ (см. §3) до любых изменений.
3. Предложить конкретный план реализации (см. §4) со списком файлов, тестов и команд валидации.
4. Остановиться и дождаться явного подтверждения пользователя.
5. Только после подтверждения реализовать ровно утверждённый план.
6. Прогнать запланированные проверки валидации; сообщить команды и результаты.
7. Составить отчёт о завершении (см. §5).
8. Остановиться. Не начинать следующую задачу автоматически.

### Запреты цикла

- Не редактировать файлы и не запускать команды, меняющие состояние репозитория, до подтверждения плана.
- Не устанавливать пакеты, не создавать миграции и не генерировать код «по ходу дела» до подтверждения.
- «Продолжай», «давай» или «делай следующую задачу» — это не разрешение молча менять утверждённый скоуп. Если новый запрос существенно меняет текущий план — сначала новый анализ и новый план.
- Task 01 нельзя начать в рамках «подготовки»; подготовка завершается отдельным отчётом и остановкой.

## 3. Требуемая структура анализа (перед планом)

```markdown
## Task N — Analysis

### Objective
...

### Repository impact
- Files to create/change: ...
- Dependencies/configuration: ...
- Data/API impact: ...
- Risks and assumptions: ...
```
В анализе обязательно указывать: зависимости от предыдущих задач, потребность в миграции/конфигурации/новой зависимости/обновлении документации, влияние на данные и приватность.

## 4. Требуемая структура плана (перед реализацией)

```markdown
## Proposed plan
1. ...
2. ...
3. ...

## Validation

- `...`
```
План: короткий конкретный список правок; имена файлов; тесты и команды валидации; упоминание решений, влияющих на архитектуру или пользовательские данные.

## 6. Источник истины и происхождение данных (data lineage)

- SQLite — источник истины для сообщений, метаданных аудио, транскрипций, выгрузок, прогонов обработки и задач (ADR-001).
- Аудио и артефакты выгрузок — файлы на локальной ФС; в SQLite — их метаданные и пути (ADR-002).
- Оригинальные пользовательские данные (текст сообщений, аудио, сырой STT, оригинальные выгрузки) неизменяемы (ADR-005).
- Ни один LLM-конвейер не перезаписывает оригиналы. Повторный прогон создаёт новую версию производного артефакта, не перезаписывая старую.
- Каждый производный артефакт обязан быть прослеживаемым до точного входного артефакта и прогона обработки (ID, хэши, профиль/модель, версия промпта, временные метки).
- Слой 3 (summary) и слой 4 (wellbeing) строятся **только** от слоя 2 (normalized), никогда от оригинала напрямую.
- Подробности: `docs/data-lineage.md`.

## 7. Безопасность и приватность

- Приложение по умолчанию слушает только localhost. Не открывать наружу без явного решения.
- Данные дневника — личные: переписка, транскрипции, тексты выгрузок, аудио, БД и бэкапы никогда не попадают в Git-отслеживаемые файлы, в фикстуры тестов, в скриншоты, в публичные артефакты и в логи (см. §8).
- Примеры и документация используют только синтетические данные; реальное содержимое дневника в репозиторий не добавляется.
- Загрузка файлов: серверная валидация MIME/размера; пути к аудио всегда генерируются сервером (UUID), пользовательские пути не используются — защита от path traversal.
- Внешние LLM-эндпоинты получают содержимое дневника только при явном включении в конфигурации и явном раскрытии в UI/документации. Никаких автоматических облачных вызовов.
- Критические/необратимые операции: новые правки файлов — по циклу §2; действия поверх БД/артефактов с потерей данных требуют подтверждения пользователя и предусмотренных задач (например, revision/re-export, recovery).

## 8. Секреты и логи

- API-ключи и секреты никогда не помещаются в исходный код, Git-отслеживаемые YAML, SQLite, логи, фикстуры, скриншоты и сообщения об ошибках.
- Конфигурация может ссылаться на секрет только по имени переменной окружения (`api_key_env`). Секреты резолвятся из окружения в рантайме.
- Никогда не логировать на уровне INFO/WARNING/ERROR: текст дневника, промпты с содержимым дневника, байты аудио, тексты транскрипций, ответы LLM.
- Не логировать полные стектрейсы провайдеров и сырые payload'ы ошибок провайдеров; использовать безопасные краткие сводки.
- Request ID / job ID добавляются в структурированные логи (план Task 19) без содержимого дневника.
- Подробности: `docs/privacy-and-safety.md`.

## 9. Правила для миграций БД

- Все изменения схемы после первичной настройки миграций выполняются через Alembic (новая миграция на каждое изменение).
- Свежая БД создаётся только через миграции; миграции повторяемы на чистом окружении.
- Миграции не содержат пользовательских данных и секретов.
- Интеграционные тесты используют изолированную тестовую БД, не продовую.

## 10. Правила добавления зависимостей

- Новая зависимость добавляется только в рамках утверждённого плана задачи и после проверки совместимости.
- Зависимость должна быть оправдана: сначала проверяется, нет ли уже утверждённого инструмента в проекте.
- Любая тяжёлая/системная зависимость (STT-модель, GPU-рантайм) документируется и остаётся опциональной для MVP.

## 11. Изменения архитектуры и отступления от ADR

- Архитектурное решение, зафиксированное в ADR, меняется только через новый ADR или явное решение пользователя — не «по ходу» реализации.
- Отступление от ADR в коде без нового ADR — нарушение контракта.
- Новые модули/границы вводятся в рамках задач `tasklist.md` и отражаются в `docs/architecture-brief.md` при необходимости.

## 12. Локальные конвенции кода

- Python 3.12+; layout `src/`; импорты из `src/`, не из корня репозитория.
- Type hints для продакшн-кода. Форматтеры/линтеры/тайпчекеры настраиваются в Task 01 (Ruff, mypy/Pyright, pre-commit).
- Роутеры FastAPI — тонкие; бизнес-логика — в сервисах/доменных модулях (`src/diary/domain/…`).
- Доступ к БД — через репозитории/слой персистентности (`src/diary/db/…`), не из роутеров и не из шаблонов.
- Pydantic — для входа/выхода API и структурированных ответов LLM.
- Атомарная запись артефактов: временный путь → flush/fsync → rename.
- Тесты добавляются вместе с функциональным кодом; тестовые данные синтетические.
- Общие модульные границы см. в `docs/architecture-brief.md` (§ «Границы модулей») и `skills/`.

## 13. Тестирование и definition of done

Задача завершена, только когда выполнены все применимые условия:
- утверждённый план реализован полностью;
- новое поведение покрыто автоматическими тестами;
- существующие релевантные тесты проходят;
- форматирование, линтинг и проверка типов проходят, когда настроены;
- документация/примеры конфигурации обновлены, если поведение видимо пользователю или настраиваемо;
- в Git-отслеживаемые файлы и логи не попали секреты и содержимое дневника;
- отчёт о завершении содержит результаты валидации.

Стратегия тестирования: `docs/testing-strategy.md` и `skills/testing/SKILL.md`.

## 14. Правила для пользовательских и необратимых операций приложения

- Действия, создающие новые версии/ревизии или удаляющие данные (re-export оригинальной ревизии, удаление сообщений по политике, recovery из бэкапа), — только через явное действие/подтверждение пользователя в UI или CLI с обязательным флагом подтверждения.
- Продуктовые действия реализуются только в рамках утверждённых задач 05–18; вне задач такие операции не добавляются.
- Политика удаления сообщений определяется в Task 05; до этого удаление не реализуется.

## 15. LLM-промпты и валидация структурированного вывода

- Промпты версионируются в `prompts/<task>/v<N>.md`; версия промпта фиксируется в метаданных прогона (план Task 12).
- Промпты не содержат содержимого дневника пользователя (только инструкции и синтетические примеры).
- Структурированный вывод LLM валидируется Pydantic до записи любых файлов; невалидный вывод = failed processing run, не частичный/повреждённый артефакт.
- Финальные пользовательские файлы рендерит бэкенд из валидированных структурированных данных, а не «сырой» вывод LLM.
- Правила по задачам: `skills/llm-pipelines/SKILL.md` и `skills/local-stt/SKILL.md`.

## 16. Wellbeing-функциональность и границы кризисной эскалации

- Wellbeing-анализ (слой 4) — всегда явное действие пользователя; автозапуск запрещён.
- Вход — только нормализованные тексты (слой 2); вывод — поддерживающая рефлексия без диагнозов.
- Запрещено: диагностические ярлыки, планы лечения, выдуманные симптомы, уверенность в причинно-следственных связях, неподтверждённые утверждения.
- Каждый отчёт содержит оговорку, что это не медицинский/психологический диагноз и не замена профессиональной помощи.
- Уровни срабатывания правил: `normal`, `needs_support`, `urgent`.
- Для `urgent` предусмотрен **детерминированный** сценарий (правила/контент вне свободной генерации LLM): показ фиксированной эскалационной информации и запись безопасного минимума метаданных. Свободный LLM-текст не управляет кризисным сценарием.
- Правила проектирования: `skills/wellbeing-safety/SKILL.md`; границы — в ADR-006 и `docs/privacy-and-safety.md`.

## 17. Чек-лист перед редактированием файлов

- [ ] Задача из `tasklist.md` прочитана полностью; предыдущая задача завершена и принята.
- [ ] Проведён анализ и план утверждены пользователем явно.
- [ ] Выполнен обзор затрагиваемых файлов (read-only), включая файлы, изменённые ранее/пользователем; конфликты выявлены.
- [ ] Изменения ограничены утверждённым скоупом; посторонние «улучшения» не добавляются.
- [ ] Отмечено, какие файлы создаются, а какие изменяются; влияние на данные/миграции/конфигурацию/документацию понятно.

## 18. Чек-лист перед объявлением завершения

- [ ] Реализовано ровно то, что утверждено; отклонения зафиксированы в отчёте.
- [ ] Прогнаны запланированные команды валидации (тесты, линт, типы); результаты приведены в отчёте.
- [ ] Проверено отсутствие секретов и содержимого дневника в Git-отслеживаемых файлах и логах.
- [ ] `tasklist.md` не переписан без запроса.
- [ ] Сделан вывод об acceptance criteria: passed / partially passed / failed.
- [ ] Следующая задача не начата.
