## 1. Продуктовый скоуп

### 1.1. Назначение

Local-first однопользовательский личный дневник для WSL 2 на русском языке:

- текстовые сообщения (запись и история);
- голосовые сообщения: запись в браузере (`MediaRecorder`) или загрузка файла, воспроизведение в чате;
- транскрипция голосовых сообщений — **только вручную**, отдельной явной кнопкой на каждое сообщение;
- хранение истории чата и метаданных в SQLite (источник истины);
- еженедельная выгрузка календарной недели в структурированный TXT (слой 1, оригинал);
- слой 2 — нормализация текста оригинала LLM;
- слой 3 — краткое саммари на основе нормализованного текста;
- слой 4 — осторожная, фактически обоснованная wellbeing-рефлексия на основе нормализованного текста;
- для каждой задачи (транскрипция, нормализация, саммаризация, wellbeing) независимо настраивается свой провайдер и модель — локальный или коммерческий OpenAI-совместимый.

### 1.2. Обязательные продуктовые решения MVP (зафиксированы)

Источник: раздел «Product decisions fixed for MVP» в `../tasklist.md`. Изменяются только отдельным явным решением.

- Один локальный пользователь.
- Основной язык: русский; язык STT настраивается, по умолчанию `ru`.
- Часовой пояс по умолчанию: `Europe/Moscow`, настраивается через `APP_TIMEZONE`.
- Неделя: понедельник 00:00:00 – воскресенье 23:59:59.999999 в настроенном поясе.
- Дата в имени недельного файла — дата воскресенья этой недели.
- Пустые недели не создают выгрузку.
- Сквозные номера выгрузок присваиваются только фактическим оригинальным выгрузкам, без пропусков.
- Номер оригинальной выгрузки переиспользуется в именах производных артефактов для очевидной трассировки.
- Повторная выгрузка ранее выгруженной недели — только явным действием пользователя, создающим новую ревизию оригинала; молчаливая перезапись запрещена.
- LLM-анализ и нормализация — всегда по действию пользователя; автоматических облачных вызовов нет.
- Wellbeing-рефлексия — поддерживающая, по документированным фактам; не диагноз, не лечение, не кризисная помощь.

### 1.3. Non-goals MVP (сознательные исключения)

- RAG / векторная БД и семантический поиск.
- Многопользовательность и мультиустройственный доступ.
- Нативные мобильные приложения.
- Автоматические облачные вызовы.
- Kubernetes; распределённые очереди/брокеры Redis/Celery/Kafka.
- Fine-tuning моделей на данных дневника.
- Автоматический wellbeing-анализ без действия пользователя.
- Шифрование at rest, локальная аутентификация/PIN (оцениваются в Task 18 как пост-MVP либо как опция, не дестабилизирующая MVP).
- Пост-MVP бэклог целиком: `tasklist.md`, раздел «Post-MVP backlog».

## 2. Архитектура и топология рантайма

### 2.1. Компоненты и поток данных

```text
Browser
  ├── text message
  └── recorded/uploaded audio
        ↓
FastAPI web application
  ├── SQLite database
  ├── local filesystem for audio/artifacts
  └── durable local worker
        ├── local STT provider
        └── configured LLM provider(s)
              ├── local OpenAI-compatible endpoint
              └── optional commercial OpenAI-compatible endpoint
```

Поток:

1. Пользователь в браузере создаёт текстовое сообщение или записывает/загружает аудио.
2. Web-приложение FastAPI валидирует вход, сохраняет метаданные в SQLite, аудио — на локальную ФС (серверные имена), текстовые сообщения — в SQLite.
3. Транскрипция и LLM-конвейеры запускаются только по явным действиям пользователя: действие создаёт **durable job** в SQLite.
4. Отдельный процесс-воркер забирает задачи (атомарный claim), исполняет их локальным STT или настроенным LLM-провайдером и пишет результаты как новые неизменяемые/версионируемые записи и артефакты.
5. Браузер опрашивает статусы (план: HTMX-поллинг/обновление фрагментов) и показывает результаты.

### 2.2. Ключевые архитектурные положения

- **Web и worker — отдельные процессы**, разделяющие одну SQLite-БД и одну файловую структуру `data/`.
- **SQLite — источник истины** для постоянных метаданных и состояния задач (ADR-001, ADR-003).
- **Файлы аудио и артефактов** живут на локальной ФС; в БД — метаданные, хэши и безопасные относительные пути (ADR-002).
- Оригинальные данные неизменяемы; производные артефакты версионируются (ADR-005).
- Внешние эндпоинты опциональны и только с явного согласия (ADR-004, ADR-006; `docs/privacy-and-safety.md`).

## 4. Границы модулей

Целевая структура пакета — под `src/diary/` (см. также раздел «Repository conventions» в `../tasklist.md` и `skills/`):

```text
src/diary/
├── api/        HTTP-роуты, Pydantic-схемы, адаптеры представления
├── core/       конфигурация, пути, логирование, время, безопасность
├── db/         SQLAlchemy-модели, репозитории, интеграция миграций
├── domain/
│   ├── chat/       use case текстовых/аудио-сообщений
│   ├── audio/      хранение аудио и абстракции транскрибации
│   ├── contracts/  контракты производных слоёв фазы 2 и формат golden-набора (ADR-007)
│   ├── exports/    границы недель, нумерация, рендер, скачивание
│   ├── llm/        абстракции провайдеров и структурированные ответы
│   └── pipelines/  оркестрация нормализации, саммари, wellbeing
├── workers/    исполнение durable-задач и обработка повторов
├── templates/  server-rendered HTML (Jinja2)
└── static/     CSS и минимальный браузерный JavaScript
```

Обязательные инварианты границ:

- **Роутеры тонкие**: HTTP-валидация, вызов сервиса, маппинг ошибок в ответы. Без бизнес-логики.
- **Бизнес-логика — в domain-сервисах** (use case-слои).
- **Доступ к БД — в репозиториях/сервисах персистентности** (`db/`); роутеры и шаблоны не обращаются к моделям/сессиям напрямую.
- Файловые операции артефактов инкапсулированы в domain-сервисах; пути наружу не передаются как пользовательский ввод.

Ожидаемые размещения по задачам уточняются в `skills/*/SKILL.md`.

## 5. Модель данных

Ниже — назначение, ключевые связи и критические поля будущих таблиц. Точные типы/ограничения фиксируются в Task 04.

| Таблица | Назначение | Ключевые поля (ожидаемые) |
|---|---|---|
| `messages` | Сообщения дневника | `id` (UUID/стабильный), `kind` (`text`/`audio`), `body_text`, `created_at` (tz-aware), статус удаления по политике Task 05, FK на `audio_files` для audio |
| `audio_files` | Метаданные аудио | `id`, `original_mime`, `size_bytes`, `sha256`, безопасный относительный путь `data/audio/YYYY/MM/<uuid>`, `duration_seconds` (где надёжно), `created_at` |
| `transcriptions` | Результаты STT (сырые) | `id`, FK `audio_files`, текст, язык/модель/профиль, `status`, `created_at`, hash входа/выхода; повторная транскрибация = новая запись, старая не стирается |
| `weekly_exports` | Оригинальные выгрузки | `id`, `week_end_date` (воскресенье), `seq_number` (без пропусков), `revision` (`r1`, `r2`, …), `path`, `sha256`, `created_at`, уникальность (неделя, ревизия) |
| `processing_runs` | Прогоны конвейеров | `id`, тип (`normalize`/`summarize`/`wellbeing`), статус (`queued`/`running`/`succeeded`/`failed`), вход/выход (FK), профиль/модель, версия промпта, временные метки, ошибка (безопасная сводка) |
| `artifacts` | Производные артефакты (слои 2–4) | `id`, слой/тип, FK `weekly_exports` (исходная выгрузка), `version` (`v1`, `v2`, …), `path`, `sha256`, FK `processing_runs`, метаданные провайдера |
| `jobs` | Durable-очередь | `id`, тип (напр. `transcribe_audio`), статус (`pending`/`running`/`succeeded`/`failed`/`retrying`/`cancelled`), `payload` (без содержимого дневника), idempotency key, число попыток, время следующего повтора, ошибка (безопасная сводка) |
| `model_configs` | Решение по профилям | **MVP: не персистится.** Профили задач остаются файловыми (`configs/models.yaml`), см. Task 04 и §8 |

Требования к схеме:

- Стабильные ID (UUID или эквивалент).
- Timezone-aware временные метки, единый формат хранения.
- Внешние ключи и индексы: время сообщения, статус задач, неделя выгрузки, происхождение артефактов (Task 04).
- Enum/check-constraint'ы для статусов, где практично.
- Поля хэша для исходных файлов и артефактов.
- JSON-метаданные — только для действительно гибких метаданных, не для ключевых реляционных полей.

### Типы сообщений и статусы

- Типы сообщений: `text`, `audio`. Аудио-сообщение всегда связано с записью `audio_files`.
- Сырая транскрипция хранится **отдельно** (`transcriptions`) и не заменяет ни аудио, ни текст сообщения; текст аудио-сообщения остаётся пустым, а транскрипция привязывается к аудио и отображается под ним.
- Статус транскрипции аудио (ожидаемый жизненный цикл, уточняется в Task 09): `not_requested` → (`queued` → `running` → `succeeded` | `failed`); повторная транскрибация создаёт новый прогон/результат. Первичный статус новой записи аудио — `not_requested` (Task 07).

## 6. Происхождение данных и неизменяемость (четыре слоя)

### 6.1. Слои артефактов (точные определения)

| Слой | Каталог | Определение |
|---|---|---|
| 1 — оригинал | `data/exports/01_original/` | Исходная еженедельная выгрузка: текст сообщений как введено плюс сырой STT, где доступен. Неизменяема. |
| 2 — нормализация | `data/exports/02_normalized/` | Производный текст, очищенный LLM с сохранением фактов (исправление очевидных ошибок STT, удаление артефактов речи). Версионируется. |
| 3 — саммари | `data/exports/03_summaries/` | Краткое саммари, обоснованное источником. Строится **только** от слоя 2. Версионируется. |
| 4 — wellbeing | `data/exports/04_wellbeing/` | Осторожная, недиагностическая рефлексия. Строится **только** от слоя 2. Версионируется. |

### 6.2. Неизменяемость и версионирование

- **Неизменяемы**: исходные сообщения пользователя, аудиофайлы, сырые транскрипции, оригинальные выгрузки (слои «источник»). Ни один LLM-конвейер их не модифицирует.
- **Производные артефакты версионируются** и прослеживаются через: ID записей БД, хэши, профиль задачи, идентификатор модели, версию промпта, временные метки, ID прогона обработки.
- Повторный прогон конвейера создаёт новую версию (`v2`, …), не перезаписывая предыдущую.
- Повторная выгрузка недели создаёт новую ревизию оригинала (`r2`, …) только явным действием.
- Детали именования, хэшей, ревизий/версий и удаления: `docs/data-lineage.md`; зафиксировано в ADR-005.

## 7. Спецификация недельной выгрузки

### 7.1. Границы и правила

- Часовой пояс: `APP_TIMEZONE`, по умолчанию `Europe/Moscow`.
- Неделя: понедельник 00:00:00 – воскресенье 23:59:59.999999 в настроенном поясе.
- Дата в имени файла — **дата воскресенья** недели.
- Пустая неделя не создаёт выгрузки и не расходует номер.
- Сквозные номера (`NNNN`) присваиваются только фактическим оригинальным выгрузкам, **без пропусков** (неактивные недели пропусков не создают).
- Новая ревизия оригинала — только через явный re-export/revision.
- Производные артефакты версионируются (`vM`) в рамках (выгрузка, ревизия).

### 7.2. Именование файлов (примеры)

```text
2026-09-13_original_0001_r1.txt
2026-09-13_original_0001_r2.txt
2026-09-13_normalized_0001_r1_v1.txt
2026-09-13_summary_0001_r1_v1.md
2026-09-13_wellbeing_0001_r1_v1.md
```

Шаблоны: `YYYY-MM-DD_original_NNNN_rN.txt` (Task 10), `YYYY-MM-DD_<type>_NNNN_rN_vM.<ext>` (Task 12; ext: `.txt` normalized, `.md` summary/wellbeing).

### 7.3. Требуемая структура оригинального TXT

Рендерит **бэкенд** (не LLM) из данных БД; структура обязательна для Task 10:

```text
# Дневник — оригинал
Неделя: YYYY-MM-DD — YYYY-MM-DD
Дата воскресенья: YYYY-MM-DD
Номер выгрузки: NNNN
Ревизия: rN
Создано: ISO-8601 timestamp
Timezone: IANA timezone

---

[YYYY-MM-DD HH:MM] TEXT
Original user text

[YYYY-MM-DD HH:MM] AUDIO
Файл: relative/safe/path
STT raw:
Raw transcription or [не расшифровано]
```

Правила: текст — как введено; для аудио — метаданные + сырой STT при наличии; нетранскрибированные аудио явно помечаются `[не расшифровано]`; порядок вывода детерминированный (хронологический). Оригинальные файлы неизменяемы; атомарная запись; путь/хэш/связи сохраняются в SQLite.

## 8. Спецификация аудио и транскрипции

### 8.1. Запись и загрузка

- Запись в браузере через `MediaRecorder` (webm/opus и т.п. по возможностям браузера); резервный путь — загрузка файла.
- Серверная валидация: допустимые MIME-типы и настраиваемый максимальный размер — обязательны (Task 07).
- Аудио хранится под серверными именами (UUID), **никогда** под пользовательскими путями: защита от path traversal.
- Каталог хранения: `data/audio/YYYY/MM/`; в БД — безопасный относительный путь + метаданные (MIME, размер, SHA-256, время, длительность, где надёжно).

### 8.2. Транскрипция

- Транскрибация — **вручную**: явная кнопка `Transcribe` на сообщение; `Retranscribe` создаёт новый прогон/результат. Автоматический запуск запрещён.
- Работа выполняется durable-задачей (`transcribe_audio`) воркером, не в HTTP-запросе.
- Язык настраивается, по умолчанию `ru`.
- Результат пишется в `transcriptions` (raw), не перезаписывая аудио и не меняя сообщение; сырой текст отображается под аудио-сообщением.
- Жизненный цикл статуса — см. §5; провайдер через интерфейс `TranscriptionProvider` (Task 09).

### 8.3. Рантайм STT

- Устройство/тип вычислений настраиваются: по умолчанию `cpu`; опционально CUDA под WSL 2 (Task 09/17). GPU — опция, не требование MVP.
- Документация CPU-fallback и границ: `skills/local-stt/SKILL.md`, `docs/wsl2-deployment-brief.md`.

## 9. Спецификация конфигурации LLM/провайдеров

### 9.1. Концептуальная модель per-task YAML

Отдельные профили задач (Task 03): `transcription`, `normalization`, `summarization`, `wellbeing_analysis`. Каждый профиль ссылается на провайдера:

- **Локальные провайдеры**: например `faster_whisper` (STT).
- **OpenAI-совместимые эндпоинты** (локальные или коммерческие): поля `base_url`, `model`, `api_key_env` (имя переменной окружения), `timeout`, `temperature`, настройки токенов.
- Флаг/политика внешней обработки: вызов внешнего эндпоинта возможен только при явном включении в конфигурации; в UI/документации эндпоинт раскрывается как внешний.
- Секреты загружаются **только из окружения** по имени переменной; в YAML секретов нет.

### 9.2. Иллюстративный YAML (без секретов)

```yaml
# configs/models.example.yaml — пример, не рабочий конфиг
app:
  timezone: Europe/Moscow

profiles:
  transcription:
    provider: faster_whisper
    model: small
    language: ru
    device: cpu            # или cuda (опционально, WSL 2)
    compute_type: int8

  normalization:
    provider: openai_compatible
```

### 9.3. Инварианты

- Секреты не появляются в YAML, логах, БД и UI (только имя переменной окружения; значение резолвится в рантайме).
- Отсутствие обязательного секрета → понятная ошибка конфигурации без чувствительных данных.
- Валидация конфигурации при старте/явной проверке.
- Профиль доступен/недоступен — диагностика без вывода ключей.
- Разные задачи могут указывать на разные эндпоинты/модели только конфигурацией (критерий Task 11).
- Политика конфигов: `../configs/README.md`; ADR-004.

## 10. Спецификации конвейеров

Общий фреймворк (Task 12): вход по идентификатору артефакта в БД (не по glob'ам), запись артефактов атомарно, версии `vM`, записи `processing_runs`/`artifacts`, статусы `queued`/`running`/`succeeded`/`failed`. Промпты версионируются (`prompts/<task>/v<N>.md`) и не содержат данных дневника.

### 10.1. Нормализация (слой 2, Task 13)

- Вход: оригинальная выгрузка (слой 1), выбранная по ID артефакта или действию пользователя.
- Допустимо: исправление очевидных ошибок STT; удаление явных речевых сбоев/артефактов; нормализация пунктуации/орфографии; консистентное форматирование.
- Запрещено (инварианты промпта): добавлять факты/мотивы/диагнозы/эмоциональные интерпретации; удалять значимую информацию; менять хронологию/временные метки; литературно переписывать голос пользователя; заявлять уверенность при неоднозначной фразе.
- Неоднозначные фразы остаются без изменений или помечаются `[неразборчиво]`; модель не выдумывает исправление.
- Сохранение: порядок записей, временные метки, тип источника, все существенные факты.
- Выход: валидированные Pydantic структурированные данные → бэкенд рендерит итоговый TXT.
- Контроль: входные записи не теряются молча (проверка полноты).
- Длинные оригиналы: чанкинг с сохранением порядка и происхождения; поддержка одиночного и пакетного режимов; сравнение original/normalized в UI.
- Отказ: невалидный вывод LLM → failed run, без частичного/повреждённого артефакта; оригинал не изменяется (байт-в-байт).

### 10.2. Саммаризация (слой 3, Task 14)

- Вход: **только** нормализованный артефакт (слой 2).
- Выход: краткое саммари, обоснованное источником; структура: ключевые события; работа и нагрузка; самочувствие/эмоции — только при явной поддержке источником; поддерживающие факторы; открытые вопросы/неизвестное.
- Запрещено вводить факты, отсутствующие в нормализованном источнике.
- Режимы: однопроходный (вход ниже порога контекста) и map-reduce (выше порога); промежуточные map-выходы — как метаданные прогона или контролируемые временные артефакты, без содержимого дневника в логах.
- Финальный результат рендерится как Markdown в `03_summaries/`; выход идентифицирует точный исходный артефакт.
- Повторный прогон — новая версия.

### 10.3. Wellbeing-рефлексия (слой 4, Task 15)

- Вход: **только** нормализованный артефакт (слой 2).
- Запуск: только явное действие пользователя с подтверждением в UI; автозапуск запрещён.
- Выход: короткая рефлексия: наблюдаемые факты (цитаты/факты отдельно от интерпретации); осторожная интерпретация; 1–3 низкорисковых практических рекомендации; уверенность и ограничения.
- Запрещено: диагнозы, планы лечения, выдуманные симптомы, уверенность в причинности, неподтверждённые утверждения.
- Обязательная оговорка в каждом отчёте (по смыслу): рефлексия основана только на записях дневника за период; это не медицинский/психологический диагноз и не замена квалифицированной помощи.
- **Детерминированный fallback для `urgent`** проектируется отдельно от свободного LLM-вывода: правила + фиксированный контент эскалации, запись безопасного минимума метаданных.
- Уровни правил: `normal`, `needs_support`, `urgent`.
- Настройка приложения полностью отключает wellbeing-анализ.
- Детали: `skills/wellbeing-safety/SKILL.md`, ADR-006, `docs/privacy-and-safety.md`.

## 11. Очередь, надёжность и идемпотентность

- **Состояния задач**: `pending`, `running`, `succeeded`, `failed`, `retrying`, `cancelled`.
- **Retry-политика**: настраиваемое число попыток + экспоненциальная задержка; окончательно упавшая задача сохраняет статус и безопасную сводку ошибки.
- **Атомарный claim**: переход `pending` → `running` условным UPDATE (с владельцем/замком) — задача не обрабатывается двумя воркерами одновременно; устойчиво к перезапуску.
- **Идемпотентность**: idempotency keys для STT и конвейеров; повторная обработка не дублирует результаты.
- **Атомарные записи артефактов**: временный путь → flush/fsync → rename; при сбое не остаётся частичного «финального» артефакта.
- **Поведение при сбое**: исходные данные не мутируются; частичные финальные артефакты не создаются.
- **Перезапуск/восстановление**: задачи и прогоны переживают рестарт приложения/воркера; незавершённые `running` обрабатываются политикой восстановления (повторный claim по таймауту/владельцу) — детали в Task 08.
- Ошибки в логах/UI — безопасные сводки без содержимого дневника и секретов.
- Обоснование выбора очереди: ADR-003.

## 12. Безопасность, приватность и безопасность (safety)

- **Сеть**: привязка к localhost по умолчанию (web, worker не публикует порты).
- **Данные и логи**: политика `docs/privacy-and-safety.md`; содержимое дневника не логируется и не коммитится; Git-защита `.gitignore` вводится в Task 01.
- **Внешние эндпоинты**: раскрытие в UI/документации + явное включение в конфигурации; без согласия внешних вызовов нет.
- **Загрузка**: серверная валидация MIME/размера; серверные пути (UUID), защита от path traversal на всех пользовательских идентификаторах/путях (в т.ч. Task 18).
- **Бэкапы/retention**: режимы бэкапа и политика очистки только `data/temp/` (Task 18); исходные аудио/артефакты автоматически не удаляются.
- **Wellbeing**: ограничения и границы эскалации — §10.3, ADR-006, `docs/privacy-and-safety.md`.
- Секреты: §9.3, `AGENTS.md` §7–8.

## 13. Стратегия тестирования

- **Unit-тесты** доменной логики (границы недель, нумерация/ревизии/версии, статусы, валидаторы).
- **Интеграционные тесты**: SQLite, репозитории, API, поведение ФС (атомарность), очередь/воркер.
- **Mock-провайдеры** STT и LLM в обычных тестовых прогонах; реальные модели/GPU/сеть не требуются в CI.
- **Фикстуры — синтетические**; реальные данные дневника запрещены.
- **End-to-end путь** (Task 19): создание текстового сообщения → аудио-сообщение → мок-транскрибация → выгрузка недели → нормализация → саммари → wellbeing → проверка полной трассировки артефактов; плюс сценарии ошибок.
- Обязательные проверки после настройки инструментов: `make test`, `make lint`, `make typecheck`.
- Детали: `docs/testing-strategy.md`, `skills/testing/SKILL.md`.
