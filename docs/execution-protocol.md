# Протокол исполнения задач

- Источник: `../tasklist.md`; операционный контракт: `../AGENTS.md`.
- Архитектурный контекст: `architecture-brief.md`.

Этот документ описывает, как именно исполняются задачи Task 01–19 и как обрабатываются отклонения и сбои валидации.

## 1. Точный цикл подтверждения задачи

Каждая задача, включая Task 01, проходит одинаковый цикл. Он обязателен и не сокращается:

1. **Read-only инспекция**: прочитать задачу полностью; изучить релевантные файлы репозитория; проверить зависимости от предыдущих задач.
2. **Анализ** (письменно, до любых изменений): цель; затрагиваемые модули/файлы/API/модель данных/тесты/документацию; зависимости; риски и приватность; потребность в миграции/конфигурации/зависимости/документации.
3. **План**: конкретный список правок; имена создаваемых/изменяемых файлов; тесты и команды валидации; упоминание решений, влияющих на архитектуру или пользовательские данные.
4. **Остановка и явное подтверждение пользователя.** До подтверждения: без правок файлов, без установки пакетов, без миграций, без команд, меняющих состояние.
5. **Реализация ровно утверждённого плана.**
6. **Валидация**: прогнать запланированные команды; сообщить команды и результаты (passed/failed).
7. **Отчёт о завершении** по шаблону ниже.
8. **Остановка.** Следующая задача не начинается автоматически.

## 2. Шаблоны

Анализ и план (до реализации):

```markdown
## Task N — Analysis

### Objective
...

### Repository impact
- Files to create/change: ...
- Dependencies/configuration: ...
- Data/API impact: ...
- Risks and assumptions: ...

## Proposed plan
1. ...
2. ...
3. ...

## Validation
- `...`
- `...`

Proceed with this plan?
```

Отчёт о завершении:

```markdown
## Task N — Complete

### Implemented
- ...

### Files changed
- `...`

### Validation
- `command` — passed/failed

### Notes
- ...

Acceptance criteria: passed / partially passed / failed.
```

## 3. Критерии изменения скоупа

- **Материальное изменение скоупа** (новые файлы/модули вне плана, новые зависимости, изменения схемы данных, изменения пользовательских данных, изменение UX-потоков, отступление от ADR) — только через новый анализ и новый план с явным подтверждением.
- Фраза «продолжай», «давай», «делай следующую задачу» — **не** разрешение менять утверждённый скоуп; при неоднозначности запрашивается уточнение.
- Мелкие технические правки внутри уже утверждённой области (переименование локальной переменной, исправление опечатки в комментарии к новому коду) не считаются изменением скоупа, если не влияют на поведение/данные. Сомнение трактуется в сторону запроса подтверждения.
- Обнаруженное противоречие в спецификации не разрешается молча: сначала эмпирическая проверка, затем пользователю показываются варианты.

## 4. Обработка неуспешной валидации

- Команды валидации выполняются из плана; результаты сообщаются **дословно** (passed/failed), без приукрашивания.
- При падении тестов/линта/типов: диагностировать причину; исправить в рамках утверждённого скоупа; повторно прогнать проверки.
- Если причина — противоречие в утверждённом плане или спецификации: остановиться и согласовать с пользователем изменённый план; не обходить проверки (`--no-verify`, отключение линта) как способ «озеленить» результат.
- Если проверка не запускалась (нет тестов, нет окружения): явно указать это в отчёте и не заявлять успех.

## 5. Границы автоматизации

- До подтверждения плана агент не создаёт/не изменяет файлы и не запускает изменяющие состояние команды.
- Задачи исполняются строго по порядку; параллельное исполнение задач не допускается.
- Одно подтверждение относится к одной задаче; после отчёта о завершении требуется новое подтверждение для следующей.

## 6. Документация процесса

- Каждая задача может обновлять `docs/` и `skills/` в рамках своего скоупа (например, Task 02 — ADR/архитектура, Task 19 — known-limitations).
- `architecture-brief.md` и `tasklist.md` — канонические источники; изменения в них — только через план задачи.

## 7. Multi-agent режим исполнения (решение пользователя, 2026-09-09)

По решению пользователя в multi-agent режиме исполняются Task 01–19, задачи фазы 2 (T00–T13b) и UI-этапы (T14–T16). Настоящий раздел **заменяет §§1–2 для цикла задач**; остальные разделы и `AGENTS.md` действуют в части, не противоречащей решению пользователя.

**Поправка от 2026-09-09 (автономный режим):** по дополнительному решению пользователя ведущий ведёт задачи по бэклогу автономно: утверждает планы, диспетчеризует агентов, после успешной приёмки коммитит **без ожидания отдельного «ок»** и автоматически переходит к следующей задаче. Пользователь сохраняет право вмешаться в любой момент. Push выполняется Ведущим **только после вердикта `accepted`** (remote `origin` настроен) — отдельным вызовом с проверкой результата; уточнение пользователя от 2026-09-21, см. «Git-политика» ниже.

### Роли

- **Ведущий** — основная сессия: read-only инспекция, письменный анализ и план задачи; утверждает план; диспетчеризует разработчика и приёмщика; исполняет git-коммиты и push; единственный канал связи с пользователем.
- **Агент-разработчик** — субагент на задачу: реализует ровно утверждённый план, выполняет команды валидации, возвращает отчёт о завершении (шаблон §2). Не выполняет `git add/commit/push`.
- **Агент-приёмщик** — субагент на задачу после отчёта разработчика: независимая проверка соответствия утверждённому скоупу, критериям приёмки и правилам приватности; повторный прогон команд валидации; вердикт `accepted`/`rework`. Единственное допустимое изменение в репозитории — запись в `docs/acceptance-log.md`.

### Цикл задачи

1. Ведущий проводит read-only инспекцию, составляет анализ и план (шаблоны §2) и утверждает план сам. Пользователь может отменить или изменить план на любом шаге.
2. Ведущий запускает агента-разработчика → отчёт о завершении.
3. Ведущий запускает агента-приёмщика → вердикт.
4. Вердикт фиксируется в `docs/acceptance-log.md`: статус, число отправок на доработку, причины каждого возврата. Запись ведёт **Ведущий** (приёмщик возвращает вердикт текстом и в журнал не пишет — так параллельные приёмки не конфликтуют).
5. При вердикте `rework` задача возвращается разработчику (тот же скоуп, причины из журнала); счётчик доработок увеличивается; итерация повторяется с п. 3.
6. При вердикте `accepted` ведущий коммитит задачу и пушит её (коммит-гейт пройден автоматически; итог задачи сообщается пользователю в отчёте о завершении). До вердикта ни коммита, ни push нет.
7. Следующая задача начинается автоматически после принятой и закоммиченной предыдущей.

### Git-политика

- Порядок жёсткий: **разработка → приёмка → коммит → push**. Коммит и push выполняет только ведущий, по одной задаче, **только после вердикта `accepted`**. Пользователь может вмешаться и запретить/изменить коммит в любой момент.
- **Push до вердикта запрещён**, в том числе «чтобы сохранить работу», и коммит до приёмки — тоже (уточнение пользователя от 2026-09-21: пуш в репозиторий — только после успешной приёмки). Если дефект найден уже после коммита, исправление оформляется **новым коммитом**; `git push --force` в `main` запрещён.
- Push выполняется **отдельным вызовом** после коммита задачи; результат проверяется (`git status -sb` не показывает `ahead`). Внутри составной команды push может молча не выполниться (наблюдалось дважды).
- Обязательные пункты приёмки сверх §3 (уборка проверена, отчёт сверен с фактами, мутационная проверка, **пуш не опережает приёмку**, правило интерфейса) — `AGENTS.md` §19.
