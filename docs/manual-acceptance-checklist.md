# Manual acceptance checklist — Local Diary MVP на WSL 2

Ручной сценарий приёмки MVP после Task 19. Предполагается окружение WSL 2 (Ubuntu), Python 3.12 (`~/.local/bin/python3.12`), `make`; подробности развёртывания — в `README.md` и `docs/wsl2-deployment-brief.md`.

Используйте **только синтетические записи** (личные данные в проверку не вносите).

## 0. Подготовка

- [ ] `make install` выполнен без ошибок (создан `.venv/`).
- [ ] `cp .env.example .env`; при необходимости задан `APP_TIMEZONE` (по умолчанию `Europe/Moscow`).
- [ ] Скопирован и при необходимости отредактирован конфиг моделей: `cp configs/models.example.yaml configs/models.yaml` (для локального/внешнего LLM-эндпоинта). Если используется только UI без LLM-шагов — файл можно не создавать, страницы не падают.
- [ ] Применены миграции: `make migrate` (создаст `data/db/diary.db`).
- [ ] (Опционально) CPU-транскрипция: `.venv/bin/pip install -e ".[stt]"` (нужен также ffmpeg в системе для записи с микрофона/конвертации, если браузер пишет не-WAV).
- [ ] Проверки кода (по желанию): `make test`, `make lint`, `make typecheck` — зелёные.

## 1. Запуск

- [ ] Терминал A (web): `make dev` → приложение на http://127.0.0.1:8000.
- [ ] Терминал B (воркер): `.venv/bin/python -m diary.workers.runner --poll-interval 2` → в логе видна строка старта `worker=... started poll_interval=...`.
- [ ] `curl -s http://127.0.0.1:8000/health` → `{"status":"ok"}`.
- [ ] `curl -s http://127.0.0.1:8000/ready` → `{"status":"ready"}` (SQLite доступна).
- [ ] В терминале A запросы сопровождаются строками вида `request_id=<32 hex> | ... http_request method=GET path=/health status=200 duration_ms=...` — request id присутствует, содержимого запросов/дневника в логах нет.

## 2. Текстовые сообщения (слой данных)

- [ ] На http://127.0.0.1:8000 в поле ввода добавлено синтетическое текстовое сообщение → появилось в ленте с временем в `APP_TIMEZONE`.
- [ ] Обновление страницы (F5) — сообщение на месте.
- [ ] Перезапуск web (`Ctrl+C`, снова `make dev`) — история сохранена (SQLite).
- [ ] Ввод пустого сообщения отклоняется с понятной ошибкой; текст с HTML-тегами отображается как текст (экранирован), не исполняется.

## 3. Голосовые сообщения и ручная транскрипция

- [ ] Запись с микрофона (кнопка записи) или загрузка файла WAV → появилось аудио-сообщение с плейером; статус «Не расшифровано».
- [ ] Аудио воспроизводится после перезагрузки страницы.
- [ ] Автоматическая транскрипция НЕ запускается (в `/processing` нет job до явного действия).
- [ ] Нажата кнопка «Расшифровать» → статус «Ожидает расшифровки», затем (воркер с установленным `[stt]`) «Расшифровано» и под аудио — текст расшифровки. Если `faster-whisper` не установлен — понятная ошибка, аудио/сообщение целы.
- [ ] В терминале B при завершении job видна строка вида `worker job=<uuid> type=transcribe_audio status=succeeded attempts=1 duration_ms=... model=... provider=... language=... artifact_bytes=...` — без содержимого.
- [ ] Повторное «Перерасшифровать» создаёт новую версию raw-текста; история версий доступна (API `/api/v1/audio/{id}/transcriptions`), старая не затирается.

## 4. Недельная выгрузка и ревизии

- [ ] На странице http://127.0.0.1:8000/exports выбран текущий календарный период (по умолчанию форма выгружает текущую неделю) → «Выгрузить неделю».
- [ ] В списке выгрузок появился оригинал `YYYY-MM-DD_original_0001_rN.txt`; скачивание возвращает TXT: шапка с номером/ревизией, текстовые записи дословно, аудио — блоком с «Файл: …» и «STT raw: …» (или `[не расшифровано]`).
- [ ] Пустая неделя не создаёт файл и не сжигает номер (кнопка выгрузки пустой недели → понятная ошибка, ничего не создано).
- [ ] «Новая ревизия» (re-export) создаёт `r2` с тем же `NNNN`; файл `r1` не изменён (проверить скачиванием обеих ревизий).

## 5. Слои 2–4 (нормализация → саммари → wellbeing)

Требуется рабочий LLM-профиль в `configs/models.yaml` (локальный эндпоинт или внешний с подтверждением). Все запуски — явными действиями, ничего не стартует само.

- [ ] На детальной странице выгрузки (`/exports/{id}`) для оригинала нажата «Нормализация» → появился слой 2 (файл `…_normalized_…_v1.txt`), «производный от оригинала 0001_rN».
- [ ] Для нормализованного — «Саммаризация» → слой 3 (`…_summary_…_v1.md`), входом указан нормализованный файл.
- [ ] «Wellbeing-рефлексия» с отметкой подтверждения → слой 4 (`…_wellbeing_…_v1.md`); отчёт содержит обязательную оговорку о недиагностическом характере.
- [ ] Оригинал не изменился после всех слоёв (хеш/содержимое при скачивании совпадают с шагом 4).
- [ ] Повторный прогон любого слоя создаёт `v2`, а не перезаписывает `v1`.
- [ ] Страница «Детали и происхождение» показывает цепочку: оригинал → нормализация → саммари/wellbeing; страница `/processing` показывает выполненные задачи со статусами.

## 6. Сбои (безопасность данных)

- [ ] Намеренно сломать LLM-шаг (например, остановить локальный эндпоинт) и запустить нормализацию → задача завершится ошибкой; оригинал, аудио и предыдущие артефакты целы; повтор возможен кнопкой.
- [ ] Повторный запуск после восстановления эндпоинта создаёт новую версию, старые файлы не тронуты.
- [ ] Wellbeing-анализ можно полностью отключить: `APP_WELLBEING_ENABLED=false` в `.env` + перезапуск → действие скрыто в UI, новые запуски отклоняются, ранее созданные отчёты читаются.

## 7. Бэкап и восстановление

- [ ] `python -m diary.cli backup --mode text` (из корня репозитория, в окружении `.venv`) создал архив в `data/backups/`.
- [ ] `python -m diary.cli backup --mode full --clean-temp` — полный архив (с аудио); удалены только файлы `data/temp/`.
- [ ] `python -m diary.cli recover --archive data/backups/<имя>.tar.gz` БЕЗ `--confirm` → отказ с сообщением.
- [ ] Проверка целостности (скрипт из README, `verify_backup`) → `True`.
- [ ] (Опционально, на копии данных) восстановление с `--confirm` возвращает БД и файлы; приложение перезапущено после восстановления.

## 8. Приватность и журнал

- [ ] Страница http://127.0.0.1:8000/privacy показывает для каждой задачи (транскрипция/нормализация/саммаризация/wellbeing): провайдер, модель, endpoint host и локальность/внешность — без значений ключей.
- [ ] В логах терминалов A и B за весь сценарий отсутствует содержимое дневника, промптов, транскрипций и секретов (допустимы только request/job id, статусы, длительности, имена моделей, токены/размеры).

## 9. Альтернативный запуск в Docker (опционально)

- [ ] `docker compose up -d --build` → `migrate` (exit 0), `web`, `worker`; `curl http://127.0.0.1:8000/health` → `{"status":"ok"}`.
- [ ] Данные переживают `docker compose down` (проверить созданную ранее запись после повторного `up -d`).
