## 2. Рантайм: как поднять и как остановить

| Компонент | Как поднят | Как остановить |
|---|---|---|
| Веб :8000 | `scripts/run-local.sh web --host 127.0.0.1 --port 8000` | kill процесса `uvicorn diary.main` |
| Воркер | `scripts/run-local.sh worker` | kill процесса `diary.workers.runner` |
| Ollama :11434 | `setsid nohup ~/.local/bin/ollama serve` с `OLLAMA_KEEP_ALIVE=0`, `OLLAMA_MAX_LOADED_MODELS=2` | убить процесс `ollama serve` |

**Как проверить состояние** (в документах оно не утверждается — только здесь его команда):
`pgrep -ax ollama`, `pgrep -af 'uvicorn|diary.workers'`, `ss -ltn | grep -E '11434|8000'`,
`~/.local/bin/ollama ps` (что резидентно). Различие, которое стоит помнить:
`serve-ollama.sh start` экспортирует `OLLAMA_KEEP_ALIVE=5m` (режим скрипта), а решение §14.0 для
рабочего рантайма — `0`, поэтому рабочий сервер поднимают **вручную** строкой из таблицы (это же
причина, по которой `serve-ollama.sh stop` его не остановит — ловушка 2 ниже).

**Ловушки окружения (проверены на практике):**

1. **Запускать приложение только через `scripts/run-local.sh`**: он экспортирует `.env` (иначе
   `*_API_KEY` не резолвятся — в проекте нет `load_dotenv`) и ставит cuBLAS-шим для GPU-Whisper.
   Для разовых скриптов вне него **экспортировать `OLLAMA_API_KEY=ollama` самому** — иначе
   `LLMProviderUnavailableError` (проверено на живом замере T23).
2. **`scripts/serve-ollama.sh stop` не остановит сервер, поднятый вручную** (нет pid-файла).
3. Профили фазы 2 требуют непустого **`OLLAMA_API_KEY`** в `.env` (значение Ollama игнорирует).
4. Сервер запускают **без `--reload`** — после правок Python его надо перезапускать; шаблоны и статика
   читаются с диска, поэтому при закэшированном HTML нужен **Ctrl+F5**.
5. `num_ctx` задаётся только в `Modelfile` тега. `reasoning_effort: none` обязателен: иначе
   размышление съедает `max_tokens` и `content` приходит пустым.
6. **Скрипты, которым нужен `eval/`** (калибровка, разовые пробы), должны либо добавить корень проекта
   в `sys.path`, либо запускаться из корня: `eval` — не пакет (проверено на пробе T23).
7. **Живой недельный замер дорог**: 10 сводок на CPU-теге — ~25 минут; дневной живой прогон — 10–15 с
   на вызов.

## 5. Факты о среде, которые дорого переоткрывать

- **Локальная нормализация падала** на `PipelineOutputError`: перезапись без потерь
  (`промпт + 2×вход ≤ num_ctx`), лечение только конфигом: `APP_NORMALIZE_CHUNK_ENTRIES=5`,
  `max_tokens: 3000`. **`configs/*.yaml` не в git** — знание живёт здесь.
- **Оценка токенов консервативна на 4–24 %** (день: оценка 2456 по строке входа чанка и 2450 по строке живого прогона против измеренных endpoint 2324);

- **`--strict` в харнессе = полное покрытие**; пропущенный чанк в strict-режиме — провал.
- **`reasoning` тратит `max_tokens`**; `/v1` не наследует `top_p`/`temperature` из тега; резидентно
  загруженный CPU-тег недели обслуживает запросы к GPU-тегам (`cli coach` 108 с вместо 8.45 с).
- **Whisper large-v3 на GPU** требует шима `libcublas.so.12` (`~/.local/lib/ct2-cuda`).
- **Микрофон на хосте Windows отключён системно** → UI-проверки настоящим Chrome через CDP либо
  Chromium из `~/.cache/ms-playwright` с флагами фейкового устройства.
- **Ollama в user space** (`~/.local`), `sudo` требует пароль; релизы `.tar.zst`, бинарника `zstd`
  нет — распаковка системным `/usr/bin/python3` (3.14, `tarfile`, `filter="data"`).

## 7. Процессные уроки (накопленные, включая эту сессию)

1. **Заявленная агентами уборка не выполняется** — нужен отдельный пункт приёмки «уборка проверена»;
   иначе остаются кэши с текстом дневника (T16a/b/c, T24a/T24b — восемь стендов на 283 МБ, T26).
2. **Пуш внутри составной команды не уходит**: `git push` — отдельным вызовом, затем `git status -sb`.
3. **Шаблоны поиска процессов не должны совпадать с собственной командой** (`pkill -f` дважды убил мой
   же шелл): писать `'diary[.]workers'`.
4. **Отчёты агентов требуют проверки фактом** (находил невыполненную уборку, заниженный объём стенда,
   изменение существующего теста под новую политику, ложное «недостижимо» в докстринге).
5. **Дерево нельзя менять во время работы приёмщика** — вердикт относится к снимку; заморозка дешевле
   расхождения хешей.
6. **DoD ничего не гарантирует, пока не покрыт тестом** (пункт T19 «выключение вместо падения» не
   работал). Приёмка **читает DoD буквально** — и именно так нашла пропущенный пункт 6 у T23 (handoff).
7. **Документы обещают больше, чем печатает код** (`eval/golden/README.md` про метрики токенов).
8. **Провайдер срывает запуск субагентов** примерно в половине случаев; при двух отказах подряд —
   короткий бриф или честная пометка «независимой приёмки не было».
9. **Повторный живой прогон замера — не формальность.** Перезапуск живого замера T26 нашёл **дефект
   самого скрипта**: при отказе слоя харнесс не отдаёт сводку судье, а скрипт брал payload предыдущего
   прогона (карта по ключу чанка) и судил его против пустой премисы — подмена данных, затем падение на
   25-й минуте. Ни один раунд приёмки тестов этого не видел: путь достижим только в живом прогоне с
   вооружённым гейтом. Тот же перезапуск дал решающее число (доля отвергнутых **сводок**).
10. **Числа в прозе — отдельный класс дефектов, и он самый частый.** Восемь раундов T26 — почти все
    находки про *производные числа*: склейка двух строк пробы в одну цифру, неверная строка свипа,
    диапазон, противоречащий собственной скобке, артефакт, названный для числа, которого в нём нет,
    «измерено в трёх прогонах» вместо четырёх. Лечение: (а) после замера каждое производное число —
    утверждение, проверяемое по артефакту; (б) **заставить инструмент печатать каждое число, на
    котором стоит решение** (так появился счёт отвергнутых сводок); (в) найдя класс дефекта, сразу
    искать **все** его вхождения в дереве, а не по одному файлу за раунд (последний раунд закрылся,
    когда я сам проверил все 26 вхождений).
11. **Правки после вердикта тоже ломают текст**: дважды исправление одной формулировки создавало
    ошибку в соседней. Поэтому косметика применяется пачкой и с повторной проверкой шлюза.
12. **Причина, записанная в документе или в докстроке, — тоже утверждение, и его тоже надо мерить.**
   T38 (2026-09-23): тезис «в чистом окружении `model_fields_set` содержит все поля» был записан как
   подтверждённый фактом и перешёл в докстроку кода. Приёмщик разобрал механизм: источники передают
   **только** заданные поля, а в множество поле попадает от **присваивания** в валидаторе; замер,
   породивший прежнюю запись, шёл в окружении с **15 экспортированными `APP_*`** (проверка —
   `env | grep -c '^APP_'`). Лечение: суть объяснения должна проверяться по **этому** файлу, а утверждение о
   поведении библиотеки — стоять на замере здесь и называть свою версию (у T38 в докстроке так и сделано:
   «присваивание помечает поле заданным» проверено на pydantic 2.15.0, стоящем в `.venv`).
13. **Стенд, импортирующий не ту копию, неотличим от успешного.** Приёмщик T38 на первом шаге указал
   `PYTHONPATH` на корень копии вместо `<копия>/src`, сработал editable-`.pth`, и проба читала рабочее
   дерево вместе с его `.env` (в транскрипт попали значения локальных ключей). Копия дерева работает
   только вместе с проверкой: каждая проба печатает `diary.__file__` и утверждает префикс пути.
