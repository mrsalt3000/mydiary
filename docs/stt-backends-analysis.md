# STT-бэкенды: рантайм GigaAM-v2 CTC+LM — замеры и способ установки (спайк, 2026-09-23)

Документ отвечает числами на два вопроса спайка T42 (`tasklist-phase2.md` §17): **сколько стоит
второй STT-бэкенд `gigaam2_ctc_lm` на этой машине** и **ставить его in-process в venv приложения или
изолированным venv-сайдкаром**. Постановка задачи и границы блока — `tasklist-phase2.md` §17; статусы
задач — `docs/acceptance-log.md`; этот документ описывает замеры и выбор способа установки, а не состояние
работ.

Все замеры сняты **2026-09-23** на описанной ниже машине. Каждое число называет своё основание:
**измерение** (файл, прогон, команда) или **оценка**; оценки помечены словом «оценка». Текстов
распознавания в документе нет — только длины, `sha256` и метрики согласия; сами тексты писались в `/tmp`
и после переноса чисел удалены (§13).

**Что в этом проходе перемерено заново.** Все основные таблицы (§5–§6, §8–§9) собраны из прогонов,
сделанных одним заходом 2026-09-23 после правки прибора нарезки (§7): один общий фон занятости GPU
(437 MiB перед каждым прогоном) делает прибавки VRAM сравнимыми. Прогоны 22:29–22:42 того же дня остались
в документе только там, где предметом является **разброс** (§6.2, §6.3, §8), — и там они названы по
времени.

## 1. Итог

- GigaAM-v2 CTC+LM **быстрее** Whisper `large-v3`: на паре прогонов одного захода — **в 6.5–7.6 раза**, по
  всем парам дня — 4.1–9.4 (min/max, §6.5); прибавка VRAM — **в 3.7–4.0 раза** меньше, и тракт
  детерминирован (§6–§8). Все диапазоны этого раздела — из сводки §6.5.
- Пик VRAM GigaAM определяется **размером чанка, а не длиной файла**: 15 с одним куском — **+861 MiB**
  (§5), 332 с кусками по 20 с — **962–981 MiB**, 332 с кусками по 120 с — **+1904 MiB** (§5, §6.5, §7.2).
- Цена GigaAM — **RAM, а не VRAM**: контур с языковой моделью доходит до `VmHWM 4553.2 MiB` (§9), из них
  2.64 GiB KenLM на CPU (= 2702.9 MiB / 1024, §9), и `unload()` **не возвращает эту память** (§9).
- **Швы нарезки не портят текст**: для пары «20 с против 120 с» различий у швов **меньше**, чем дало бы
  случайное размещение (22 против ожидаемых 37.1 при окне ±1 %, §8), — то есть концентрации у швов нет.
- **Рекомендация: сайдкар** в отдельном venv вне репозитория, долгоживущий процесс (§10).

### 4.2 Команды установки

**Оговорка о происхождении.** История команд той сессии не сохранилась (`~/.bash_history` пуст по
установке), поэтому команды ниже — реконструкция: под каждым шагом указано, чем именно она подтверждается
(артефактами в венве и кэше uv). Реконструкция проверялась не запуском «как было», а совпадением
результата: установленные версии и происхождение артефактов видны в венве и кэше, а сборка `kenlm` из
sdist воспроизведена заново в отдельном одноразовом venv (§4.3).

```bash
# 1. venv вне репозитория
uv venv ~/.local/share/mydiary/gigaam-spike/venv --python 3.12
#    подтверждение: venv/pyvenv.cfg (uv = 0.12.7), Python 3.12.14

# 2. torch/torchaudio с CUDA-колёсами (индекс PyTorch, а не PyPI: локальная метка +cu126)
uv pip install --python ~/.local/share/mydiary/gigaam-spike/venv/bin/python \
    torch==2.14.0+cu126 torchaudio==2.11.0+cu126 \
    --index-url https://download.pytorch.org/whl/cu126
#    подтверждение: torch 2.14.0+cu126, torch.version.cuda == 12.6, cuda.is_available() == True;
#    в кэше uv остался отдельный индекс, чьи записи — ровно замыкание зависимостей torch
#    (torch, torchaudio, triton, sympy, networkx, filelock, fsspec, jinja2, nvidia-*-cu12,
#    cuda-toolkit/cuda-bindings/cuda-pathfinder, typing-extensions) — такого набора PyPI-индекс не даёт

# 3. обвязка HF
uv pip install --python ~/.local/share/mydiary/gigaam-spike/venv/bin/python \
    transformers==5.17.0 safetensors==0.8.0 av==18.1.0

# 4. LM-контур — обход пина `numpy` у pyctcdecode, поэтому без зависимостей
uv pip install --python ~/.local/share/mydiary/gigaam-spike/venv/bin/python --no-deps \
    kenlm==0.3.0 pyctcdecode==0.5.0 pygtrie==2.6.2
```

Почему шаг 4 обязателен именно с `--no-deps` — это **доказательство, а не догадка**: метаданные
`pyctcdecode 0.5.0` требуют `numpy (<2.0.0,>=1.15.0)` и `hypothesis (<7,>=6.14)`, а в спайк-venv стоит
`numpy 2.5.3` и `hypothesis` отсутствует вовсе (измерено: `importlib.metadata` + `ls site-packages`).
Значит зависимости были пропущены, а `numpy` не понижался. `pygtrie` при этом объявлен явно — это
единственная зависимость, которая нужна `pyctcdecode` в рантайме (`hypothesis` нужен только тестам).

### 4.3 Из двух тяжёлых зависимостей собирается только `kenlm`

Что именно приехало колесом, а что собиралось, видно по кэшу uv (измерено `find`/`ls` 2026-09-23):

| Пакет | Как получен | Время сборки |
|---|---|---|
| `pyctcdecode 0.5.0` | **колесом с индекса**: `wheels-v6/pypi/pyctcdecode/0.5.0-py2.py3-none-any.http` — запись о скачивании | сборки нет |
| `kenlm 0.3.0` | **из sdist**: `sdists-v9/pypi/kenlm/0.3.0/…` содержит исходники и собранное колесо `kenlm-0.3.0-cp312-cp312-linux_x86_64.whl` | **38.33 с** (`Prepared 1 package in 38.33s`), измерено заново 2026-09-23 в одноразовом venv из того же sdist с `--offline` |

`kenlm` — это **C++/cmake-сборка**, а не Python-пакет: инструменты, которыми она прошла, — `cmake 4.2.3`,
`g++ 15.2.0`, `make` (измерено: `cmake --version`, `g++ --version`, `which`). То есть провижининг тянет
системный тулчейн; для машины без `cmake` сборка не пройдёт. Наблюдение по ходу повторной сборки: она
**падает**, если рядом лежит каталог `build/` от предыдущей сборки (CMakeCache со старыми путями); на
чистом дереве исходников — проходит.

замеров, поэтому одна пара её не измеряет: все пять имеющихся пар сведены в §6.5. Читать её следует как
«около 5 с», а не как число из одной пары. Пик VRAM при этом не меняется вовсе: у LM и greedy он одинаков
по обеим строкам таблицы выше (658.3 МиБ аллокатора) — KenLM считается на CPU (§9).

## 7. Деление длинного файла и шов

Проба режет файл по **тишине** (энергетический детектор, без отдельной зависимости: RMS кадра ниже
`max(1e-4, 0.05·p95)`), и только если рядом с целевой границей тишины нет — по фиксированному окну
(такой чанк помечается честно, как `window`). Перекрытие расширяет чанк с обеих сторон, а склейка удаляет
слова, которые перекрытие продублировало.

### 7.1 Что проверено измерением, а что является свойством планировщика

Это разделение — суть правки этого прохода. `plan_chunks` строит владеемые диапазоны из **соседних
границ**, поэтому внутренняя дыра или двойное владение его планом не порождаются **по построению**: прибор,
который только шагает по границам, подтверждает то, что и так гарантировано, и не измеряет ничего.
Единственный достижимый для такого планировщика пропуск — **незакрытый хвост** (если последняя граница не
добавлена), и именно его прежняя версия прибора не видела: `chunk_coverage` шагала по границам и
возвращала `(0.0, 0.0)` на плане, потерявшем хвост.

Прибор исправлен и теперь **отказывает** прогону (SystemExit, до всякого инференса), если не выполнено
любое из трёх:

- владеемые диапазоны стыкуются (внутренняя дыра / двойное владение);
- последний диапазон кончается **на длине файла** — для этого в проверку передаётся `total_s`;
- сумма владеемых секунд равна длине файла.

Допуск — `1e-6 с` (микросекунда; один сэмпл при 16 кГц — 62.5 мкс), он покрывает только округление
пересчёта сэмплов в секунды. Проверка запускается до загрузки модели, поэтому испорченный план не тратит
ни GPU, ни времени.

**Мутация, воспроизводящая дефект.** Из копии пробы убрана строка `bounds.append((total, "end"))`; прогон
по живому длинному файлу 2026-09-23:

```
$ python /tmp/t42-mutant-probe.py run --backend gigaam-lm --audio data/audio/2026/09/f631cb6f-…webm \
      --device cuda --max-chunk-s 20 --chunk-overlap-s 0.5 --emit-text /tmp/… --json /tmp/…
chunk plan does not tile the file exactly once (tolerance 1e-06s): uncovered tail 1.140000s
(plan ends at 331.020000s of 332.160000s); owned 331.020000s != file 332.160000s
MUTANT EXIT=1
```

Ни текста, ни JSON мутант не записал: проверка стоит **до** загрузки модели, поэтому испорченный план не
тратит ни GPU, ни времени — по замеру приёмки мутированный прогон падает за **0.78 с** (§6.5). На
**прежней** версии прибора тот же мутант заканчивался `exit 0` с `coverage_gap_s 0.000`,
`coverage_double_s 0.000` (замер независимой приёмки, 2026-09-23, повторить его теперь нечем — прежней
реализации в дереве нет) — то есть документ, ссылавшийся на «обе величины ровно 0.0», выдавал структурное
свойство за измерение.

**Самопроверка прибора** (`selftest`, без модели, GPU и живого аудио — только numpy и синтетика):

## 8. Качество: согласие между бэкендами и его граница

**Метрика.** Нормированное согласие по символам: `1 − Левенштейн(a,b) / max(|a|,|b|)` по нормализованному
тексту (нижний регистр, `ё`→`е`, пунктуация выброшена, пробелы схлопнуты). Реализация — `compare` в пробе.
Отнесение различий к швам считается **в каноническом порядке текстов** (длиннее — первым), иначе ответ
зависел от порядка аргументов: на прежней реализации та же пара «20 с против 120 с» давала **107 различий
и 59 из них у швов** при одном порядке `--text` и **105 и 22** при другом (то же воспроизведено счётом по
прежнему алгоритму, 2026-09-23). После правки порядок `--text` на числа не влияет — проверено обоими
порядками, результаты совпадают до последнего знака.

**Граница метрики названа прямо: это согласие между бэкендами, а не точность.** Человеческого эталона
(транскрипта, выверенного руками) нет, поэтому WER и «какой бэкенд правильнее» этими числами **не**
измеряются.

`±1 % covers 35.3 % of the file`. Поэтому сырое «у швов 105 символов» не значит ничего, а сравнение с
ожиданием — значит.

**Концентрации различий у швов нет — и это важный вывод для T44.** Для пары «20 с против 120 с» у швов
оказалось **22 различия при ожидаемых 37.1**, то есть **меньше**, чем дало бы случайное размещение; то же
для пары «greedy против 120 с» (25 против 38.5). По всем парам с Whisper отношение колеблется вокруг
единицы (0.92–1.46) без систематического превышения. Единственная пара с заметным превышением —
`lm vs greedy` (12 против 8.1), и она же самая близкая по тексту, где абсолютные числа малы (23 различия
на 3246 символов). Вывод: различия между нарезками и между бэкендами **распределены по файлу, а не
собраны на швах**; склейка не оставляет следов, которые эта метрика может поймать.

**Два вывода, которые следуют из этих же чисел, и один, который не следует:**

1. **GigaAM-контур детерминирован, Whisper — нет.** Пять прогонов LM с одинаковыми параметрами (четыре
   наших и приёмочный, §6.2) дали **один и тот же `sha256`** текста (`431180…`; greedy — `e61407…`), а три
   прогона Whisper на том же файле — **три разных `sha256`** и тексты длиной 3190–3261 символов
   (§8.1).
2. **Разница между бэкендами больше, чем собственный разброс Whisper.** Согласие Whisper с самим собой на
   этом файле — **0.9668–0.9912** по четырём свежим парам (три наших и одна приёмочная; сводка — §6.5), а
   GigaAM против Whisper на **20-секундной** нарезке — **0.8746–0.9007** по десяти парам (шесть наших и
   четыре приёмочные, §6.5; 120-секундные пары туда не смешаны и дают отдельную строку), то есть **ниже
   пола на всех имеющихся прогонах**. То есть метрика бэкенды **различает**. Оговорка: пол не константа
   (более ранние пары того же дня дали 0.9100–0.9846) и оценён по малой выборке (§12).
3. Из «`lm vs greedy` = 0.9929» **не** следует, что языковая модель не нужна: greedy согласуется с LM
   почти всюду, но без эталона не видно, кто из них прав в тех 23 символах, а на коротком файле они
   совпали полностью. Вопрос «что покупает LM» требует эталонного корпуса и этой пробой не решается.

### 8.1 Две особенности вывода, которых метрика не показывает

Основание — сами тексты прогонов этого захода (в документе только счётчики; тексты удалены после переноса
чисел, §13):

1. **Пунктуация и регистр.** На длинном файле вывод GigaAM — **0 заглавных букв и 0 знаков пунктуации** во

   пунктуации** (три прогона). На коротком файле (15 с префикса) **оба** контура выдали по нулю и там, и
   там. То есть «Whisper расставляет пунктуацию» верно для длинного файла и коротким не подтверждается;
   **причина расхождения не измерялась**.
2. **Дословный повтор фразы.** В GigaAM-текстах с чанками по 20 с одна и та же фраза встречается
   **дважды** — и в LM, и в greedy, и при перекрытии 0.5, и при 0; в текстах Whisper она по одному разу
   (три прогона), а в нарезке по 120 с её нет вовсе. Повторы лежат на 2.0 % и 2.6 % длины текста при
   первом шве на 5.7 %, то есть **внутри первого чанка** (≥3.1 % от ближайшего шва = 5.7 − 2.6), и в
   одинаковых позициях во всех вариантах (позиции — по длине текста из таблиц §6.2/§6.3 и `seams_frac`
   прогона 20 с). Значит, это **не следствие склейки**, а вывод декодера на этом аудио. Природа явления
   **не исследовалась**.

## 9. RAM: цена контура в процессе

RSS процесса — `/proc/self/status`: `VmRSS` (текущая) и `VmHWM` (пик с начала процесса, «водяной знак»
ядра, который не может пропустить всплеск). Снималось трижды за прогон: до загрузки модели, после
загрузки, после `unload()`. Это и есть та часть цены, которой **не видит `nvidia-smi`**: KenLM живёт на
CPU. Длинный файл, прогоны одного захода 2026-09-23.

| Контур | RSS до загрузки | RSS после загрузки | `VmHWM` после загрузки | RSS после `unload()` | `VmHWM` (пик процесса) | Пик == RSS после выгрузки? |
|---|---|---|---|---|---|---|
| `gigaam-lm` (с KenLM) | 540.1 MiB | **4411.7 MiB** | 4411.7 MiB | 4553.2 MiB | **4553.2 MiB** | да (4553.2 = 4553.2) |
| `gigaam-greedy` (без KenLM) | 540.0 MiB | **1708.8 MiB** | — (в том прогоне не снял) | 1877.5 MiB | **2068.3 MiB** | нет: 2068.3 > 1877.5 |
| `whisper large-v3` (`.venv` приложения) | 103.5 MiB | 3089.2 MiB | 3499.9 MiB | 3598.7 MiB | **3666.4 MiB** | нет: 3666.4 > 3598.7 |

Пик процесса совпадает с RSS после выгрузки **только у LM-контура**; у greedy и Whisper `VmHWM` заметно
выше последнего замера (2068.3 против 1877.5 и 3666.4 против 3598.7) — то есть у них пик приходится на
работу, а не на момент после `unload()`, и последний замер его не показывает. У Whisper пик набирается уже
**к моменту окончания загрузки**: после загрузки RSS 3089.2, а `VmHWM` уже 3499.9 (короткий файл даёт ту же
картину: 1668.6 против 3161.1, §5) — CTranslate2 читает свои 3 GB весов (§4.5) в RAM, прежде чем отдать их
на GPU.

- **Языковая модель стоит 2702.9 MiB RSS** (4411.7 − 1708.8) — это её 2.14 GB на CPU плюс структуры
  `pyctcdecode`. В VRAM она не попадает вовсе (прибавка VRAM у greedy и LM одинакова — §6.1).
- **`unload()` освобождает VRAM, но не RAM**: ни у одного из трёх контуров RSS после выгрузки не падает
  (у LM даже растёт: 4553.2 против 4411.7). Аллокатор Torch при этом показывает **8.5 МиБ** (§7.2, столбец
  «после `unload()`»), а `nvidia-smi` — остаток **+217 MiB** над базой у LM/greedy (654 − 437, обе
  величины из §7.2) и **+117 MiB** у Whisper (554 − 437; 554 — строка «этот заход a/b/c» в §6.3).
  «VRAM после выгрузки почти ноль» верно для счётчика аллокатора и лишь «почти» — для `nvidia-smi`.
- Свободной RAM в WSL 14 GiB (измерено `free -g`), так что пик LM-контура влезает: 4.45 GiB
  (4553.2 MiB / 1024 — из таблицы выше). Но это цена **на процесс**: пока в процессе живёт LM-контур,
  столько и занято, и освобождается это только выходом процесса.

## 10. In-process или сайдкар: рекомендация и цена обоих

**Рекомендация: изолированный сайдкар в отдельном venv вне репозитория, долгоживущий процесс.**
Обоснование — измеренные числа, а не общие соображения. Числа ниже — на 2026-09-23; после переключения
живого конфига на GigaAM (T46) роли «текущий бэкенд» и «второй бэкенд» поменяются местами, а цены
установки и памяти останутся теми же.

**Цена сайдкара**

| Статья | Числа |
|---|---|
| venv приложения | **не меняется вовсе**: снимки до/после совпадают по составу из 63 пакетов плюс editable-строка `diary`, `numpy 2.5.3` (§4.4) |
| Диск | **6.5 GB** вне репозитория (спайк-venv целиком; из них 5.4 GB — CUDA-рантайм: `nvidia/*` 3.6 GB + `triton` 892 MB, §4.5) |
| Память процесса | пик **4553.2 MiB** `VmHWM` в процессе-сайдкаре (§9); в процессе приложения эта память не появляется |
| Долговечность | загрузка LM-контура — **15.9–25.6 с** по четырём прогонам (§6.5). Долгоживущий сайдкар платит её один раз на процесс, вызов «процесс на файл» — на каждый файл. Причина разброса внутри диапазона не измерялась (§12) |
| Границы доверия | `trust_remote_code=True` — исполнение чужого кода, но **в отдельном процессе** со своим venv, а не в процессе веб-приложения |
| Цена разработки | IPC и жизненный цикл процесса (протокол, перезапуск, состояние «занят/свободен») — оценка: это работа T44/T45, не этой пробы |

**Цена in-process** (GigaAM внутри `.venv` приложения)

| Статья | Числа |
|---|---|
| Диск | **+6.5 GB** к `.venv` (та же раскладка: 3.6 GB `nvidia/*` + 1.7 GB `torch` + 892 MB `triton`) |
| RAM приложения | пик **4.45 GiB** на время транскрипции (4553.2 MiB `VmHWM` контура с LM, §9 — деление на 1024), и эта память не возвращается `unload()` — только выходом процесса |
| VRAM | прибавка **962–981 MiB** над базовой занятостью на чанках 20 с (§6.5; пик аллокатора 658.3 МиБ, §6.1), после `unload()` остаётся **+217 MiB** по `nvidia-smi` (§9) |
| Пин `numpy` | `numpy` остаётся 2.5.3: `pyctcdecode` требует `<2`, но работает с 2 — проверено всеми прогонами (установка обязана идти `--no-deps`, §4.2). Понижение `numpy` в общем venv — то, чего DoD T45 прямо запрещает |
| Два CUDA-стека в одном процессе | в `.venv` `ctranslate2` требует `libcublas.so.12` и получает его шимом `~/.local/lib/ct2-cuda` (видно фактом: без шима прогон Whisper падает `RuntimeError: Library libcublas.so.12 is not found or cannot be loaded`, с шимом — проходит), а `torch` приносит свои CUDA-12.6-библиотеки колёсами. Сосуществование двух наборов в одном процессе — **названный риск, не измерен** |
| Зависимости приложения | +6.5 GB и цепочка CUDA-колёс в venv приложения, который на 2026-09-23 несёт 63 пакета штатного стека (§4.4) |

**Почему всё-таки сайдкар, в трёх измеренных фактах:**

1. **`unload()` не возвращает RAM** (RSS после выгрузки не падает ни у одного контура, §9). В in-process
   варианте 4.5 GiB остаются занятыми до выхода процесса; сайдкар делает «выгрузку» структурной — выход
   процесса. Что выход процесса действительно возвращает память, видно по измерениям: после завершения
   процесса Whisper GPU вернулся к **388 MiB** — ровно к тому значению, что было перед прогонами того
   часа (строка 23:36 в §6.3), тогда как in-process `unload()` Whisper оставлял **504 MiB** (504 − 388 =
   +116 MiB над той же базой; обе величины из той же строки §6.3).
2. **venv приложения остаётся нетронутым** — и это не рассуждение, а измерение (§4.4): шестьдесят три
   пакета плюс editable-строка `diary` до и после, `numpy 2.5.3`, ни `torch`, ни `transformers`, ни
   `kenlm`, ни `pyctcdecode` внутри. In-process вариант обязан этот venv изменить (6.5 GB) и оставляет
   вопрос о сосуществовании двух CUDA-стеков.
3. **Цена сайдкара — не латентность.** Контур и так быстрее того бэкенда, что работал 2026-09-23:
   на паре прогонов одного захода — в 6.5–7.6 раза (§6.5). Загрузка модели — единственная статья, которую
   сайдкар оптимизирует долговечностью процесса, а не вычислительной мощностью.

**Что этот документ не решает:** конкретный протокол IPC, формат обмена и политику жизненного цикла
сайдкара (кто его поднимает и когда гасит). Это работа T44/T45 по их DoD.

## 11. Риски

1. **Неофициальная обёртка.** Чекпоинт `waveletdeboshir/gigaam-ctc-with-lm` — «unofficial Transformers
   wrapper» над `salute-developers/GigaAM` (так сказано в его же карточке), и он исполняется у нас
   локально через `trust_remote_code=True` (`gigaam_transformers.py` + `encoder.py` приходят из
   репозитория модели). Замеров безопасности тут нет; что нужно решением — пин по ревизии
   (`07d97cf8a4f178b68679cafae0600c8487877301` — та ревизия, к которой привёл первый запуск) плюс
   `sha256` весов (§4.5). **Проба ревизию не пинит** — она качает `main`; пин обязан появиться в T45.
2. **`transformers` 5.17 против объявленных автором 4.49.0.** Карточка модели называет её версии:
   `torch` 2.7.1, `torchaudio` 2.7.1, `transformers` 4.49.0; фактически работали `torch 2.14.0+cu126`,
   `torchaudio 2.11.0+cu126`, `transformers 5.17.0`. Прямое следствие измерено: `AutoModel.from_pretrained`
   из обёртки **падает** с `RuntimeError: Tensor.item() cannot be called on meta tensors` (transformers 5.x
   строит модель в контексте `torch.device("meta")`, а обёртка вызывает `int(tensor)` в
   `StridingSubsampling.__init__`). Обход, применённый в пробе: `AutoConfig.from_pretrained` +
   `AutoModel.from_config` (без meta-контекста) + загрузка весов из `model.safetensors` через
   `safetensors.torch.load_file`. **Проверено, что веса при этом совпадают полностью**: у модели и
   чекпоинта по **600 тензоров**, `unexpected_keys = 0`, `missing_keys = 0` (проверено 2026-09-23 сборкой
   модели через `AutoConfig.from_pretrained` + `AutoModel.from_config` и сравнением множеств ключей
   `state_dict()` с ключами `model.safetensors`; `load_state_dict(strict=False)` в пробе — страховка, а не
   маскировка). Остаточный риск — обёртка предупреждает «You are using a model
   of type `gigaam-ctc` to instantiate a model of type ``», и это ровно тот путь, который автор не
   тестировал.
3. **`pyctcdecode 0.5.0` при `numpy>=2`.** Метаданные требуют `numpy<2`, установлен 2.5.3. Работает —
   измерено всеми прогонами (тексты получены, в том числе с 3-граммной LM), но это опора на несовпадение
   с объявленным пином, и обновление `pyctcdecode`/`numpy` может её сломать. Установка обязательно
   `--no-deps`, иначе резолвер понизит `numpy`.
4. **`kenlm` только sdist.** Сборка из исходников: `cmake 4.2.3` + `g++ 15.2.0` + `make`, измерено 38.33 с
   (2026-09-23). Это системный тулчейн в провижининге (в репозиторий не коммитится), и сборка ломается на
   грязном дереве с чужим `build/`.
5. **Объём весов 2.64 GB** (2.46 GiB) на диске, из которых 2.14 GB — языковая модель (§4.5). Скачиваются
   при первом запуске; без `cache_dir` `pyctcdecode` уводит LM мимо `HF_HOME` (§4.5).
6. **VRAM растёт с размером чанка.** Измерено ровно два размера: 20 с и 120 с; прибавка — **962–981 MiB**
   против **+1904 MiB** (§6.5), аллокатор 658.3 против 1182.1 МиБ (§7.2). Абсолютные пики обоих размеров
   видны в §7.2 (1400 и 2342 MiB при базах 429–438 MiB) и потому не перепечатываются здесь: абсолют
   зависит от того, что помимо нас держит GPU (база в прогонах дня менялась 388–1133 MiB — крайние
   значения из §6.2 и §6.3), поэтому ориентироваться надо на прибавку.
7. **KenLM в RAM — невидимая снаружи статья** (§9): +2702.9 MiB RSS, и `unload()` её не возвращает.
   Именно она, а не VRAM, определяет границу «сколько контуров можно держать одновременно».
8. **Параметры декодирования не те, что в примере.** Прогоны шли с `beam_width 64` (дефолт пробы
   `--beam-width`, §13) и **незаданными** `alpha`/`beta` — обёртка берёт их из `language_model/attrs.json`
   чекпоинта: измерено `alpha = 0.4612549346468768`, `beta = 0.3271780420615455`. Карточка модели и
   `tts_research.md` приводят `alpha=0.5, beta=0.5` — эти числа **не** относятся к нашим замерам;
   качество (§8) измерено на параметрах чекпоинта.
9. **Судить о качестве по согласию нельзя** (§8): эталона нет, а шумовой пол (согласие Whisper с самим
   собой — 0.9668–0.9912 по четырём свежим парам, §6.5) сам оценён по малой выборке и не является
   константой.

## 12. Что не проверено

- **Точность распознавания.** Человеческого эталона нет; в документе только согласие между бэкендами
  (§8). WER/NER GigaAM и Whisper не измерены.
- **Шумовой пол Whisper** измерен по **семи** парам одного файла (§6.5: четыре свежие, включая
  приёмочную, и три более ранние), причём свежие и ранние пары дали разные границы. Пол не константа,
  выборка мала, поэтому вывод «разница между бэкендами ниже пола» (диапазоны — §6.5) верен на всех
  имеющихся парах, но опирается на небольшое их число.
- **Корпус.** Два живых файла (§3: 18.8 с и 332.1 с — контейнерные длительности, округлённые).
  Синтетических и «золотых» записей не прогоняли.
- **CPU-режим GigaAM** (`--device cpu`) не запускался ни разу: флаг в пробе есть, замеров нет.

## 13. Воспроизведение

Все команды — из корня репозитория. Тексты и метрики пишутся **только** в `/tmp`; проба отказывается
писать их в репозиторий. Спайк-venv и HF-кэш — вне репозитория (§4).

```bash
SPIKE=~/.local/share/mydiary/gigaam-spike
export HF_HOME=$SPIKE/hf HF_HUB_OFFLINE=1
LONG=data/audio/2026/09/f631cb6f-26fc-4cb2-a243-e9bc7f353a10.webm
SHORT=data/audio/2026/09/77a9a61e-25ec-4834-9de5-86c8b8c79414.webm

# Приборы: покрытие нарезки (мутация «потерянный хвост») и декодирование контейнеров
# без системного ffmpeg. Модель, GPU и живое аудио не нужны; PATH можно опустошить.
$SPIKE/venv/bin/python scripts/probe-stt-backend.py selftest

# GigaAM с языковой моделью, длинный файл, чанки 20 с (и то же с --max-chunk-s 120)
$SPIKE/venv/bin/python scripts/probe-stt-backend.py run --backend gigaam-lm \
  --audio $LONG --device cuda --max-chunk-s 20 --chunk-overlap-s 0.5 \
  --emit-text /tmp/t42-long-lm.txt --json /tmp/t42-long-lm.json

# GigaAM без языковой модели — контроль «сколько стоит LM»
$SPIKE/venv/bin/python scripts/probe-stt-backend.py run --backend gigaam-greedy \
  --audio $LONG --device cuda --max-chunk-s 20 --chunk-overlap-s 0.5 \
  --emit-text /tmp/t42-long-greedy.txt --json /tmp/t42-long-greedy.json

# Whisper (бэкенд живого конфига на 2026-09-23), тот же файл.
# ВНИМАНИЕ: ctranslate2 4.8.2 требует libcublas.so.12, а в системе CUDA 13 —
# без шима прогон падает "Library libcublas.so.12 is not found or cannot be loaded".
LD_LIBRARY_PATH=$HOME/.local/lib/ct2-cuda${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH} \
  .venv/bin/python scripts/probe-stt-backend.py run --backend whisper \
  --audio $LONG --device cuda --emit-text /tmp/t42-long-whisper.txt --json /tmp/t42-long-whisper.json

# Короткий файл: тот же набор с --max-seconds 15

# Согласие текстов; швы берутся из метрик-JSON прогона, а не набираются руками.
# Число различий у швов сравнивается там же с ожиданием при равномерном размещении.
.venv/bin/python scripts/probe-stt-backend.py compare \
  --text /tmp/t42-long-lm.txt --label gigaam-lm \
  --text /tmp/t42-long-greedy.txt --label gigaam-greedy \
  --text /tmp/t42-long-whisper.txt --label whisper-large-v3 \
  --seams-from-json /tmp/t42-long-lm.json --json /tmp/t42-long-compare.json
```

**Правило о числах удалённых прогонов.** Тексты распознавания — личные данные, поэтому артефакты прогонов
удаляются после переноса чисел; числа таких прогонов в таблицы **не возвращаются** и в прозе приводятся
только с явной пометкой «артефакты удалены» и **без ссылки на строку таблицы** (пример — ранний прогон
короткого файла в §6.4). Всё, на что в таблицах и в прозе стоит ссылка, должно быть перемерено заново и
лежать в таблице текущей редакции.
