# Известные ограничения MVP (актуализировано, Task 19)

- Дата актуализации: 2026-09-09 (после приёмок Task 01–18; финальная задача Task 19).
- Статус: документ описывает **реальные ограничения реализованного MVP** Local Diary. Список собран из журнала приёмок (`acceptance-log.md`), кода, ADR и документации; пост-MVP-функции перечислены в бэклоге `../tasklist.md` и здесь не дублируются, кроме явных границ безопасности.

## 1. Один пользователь, локальные данные

- Приложение локальное, однопользовательское и по умолчанию слушает только `127.0.0.1` (web; воркер портов не публикует).
- Защита доступа — только «localhost + политика приватности»: **PIN/аутентификации и шифрования at rest нет** (post-MVP). Любой локальный процесс пользователя может читать `data/`.
- Реальное содержимое дневника (`data/`, `.env`) не попадает в Git, фикстуры, скриншоты и логи; в тестах и примерах — только синтетика.

## 2. Аудио и транскрипция (STT)

- `audio_files.duration_seconds` всегда `NULL`: длительность в MVP не вычисляется (нужен демультиплексор/ffprobe — вне скоупа).
- Проверка загружаемого аудио — **только по «магическим байтам» контейнера и размеру/лимиту MIME**. Декодируемость и реальная воспроизводимость не проверяются: файл с корректной сигнатурой, но битым содержимым будет принят.
- `faster-whisper` — опциональный extra (`pip install -e ".[stt]"`); в обычном окружении и CI он не установлен. Без него задача расшифровки завершается понятной ошибкой, аудио и сообщение не затрагиваются.
- При первом использовании faster-whisper скачивает модель в локальный кэш (разовая операция, нужна сеть); GPU/CUDA — опциональная настройка вне требований MVP.
- Точность STT для русского языка и качество последующей нормализации на реальных данных в репозитории не оцениваются (только синтетические тесты); оценку пользователь проводит на своих данных вне репозитория.

## 3. LLM-конвейеры (слои 2–4)

- Поддерживаются только **OpenAI-совместимые эндпоинты** (локальные или внешние). Внешняя обработка возможна только при `external: true` в профиле и явном согласии в UI; автоматических облачных вызовов нет.
- Секреты резолвятся из переменных окружения по имени (`api_key_env`); ключи не хранятся и не логируются. Если внешний провайдер меняет API/возвращает ошибки — задача падает безопасно и повторяется по политике очереди; ручной повтор доступен в UI.
- Токен-счётчики фиксируются в метаданных прогона, когда провайдер их возвращает; учёта стоимости нет.
- Очень длинные документы обрабатываются детерминированным чанкингом (нормализация) и map-reduce (саммаризация) с параметрами по умолчанию (`APP_NORMALIZE_CHUNK_ENTRIES`, `APP_SUMMARIZE_*`); поведение для экстремальных объёмов не тестировалось на реальных данных.

## 4. Очередь, воркер, согласованность

- Очередь — на SQLite (ADR-003), рассчитана на одного локального пользователя и несколько локальных воркеров; это не распределённая система (Redis/Celery/Kafka — пост-MVP).
- Атомарный claim защищает job от двойного выполнения двумя воркерами (покрыто тестами), но при жёстком падении процесса job остаётся `running` до явного `--reset-stale` (порог `APP_JOB_STALE_AFTER_S`).
- Окно «файл записан → коммит строки БД»: при краше процесса строго между атомарным `rename` артефакта/выгрузки и коммитом может остаться файл-«сирота» без строки в БД. Данные не теряются и не повреждаются; повторный прогон создаёт новую версию. На ошибках (не крашах) файл подчищается кодом.
- Гонка глобального номера выгрузки (`seq_number`): следующий номер выбирается чтением `max+1` без отдельной блокировки. Параллельные экспорты **разных** недель теоретически могут получить одинаковый номер. Для одного локального пользователя риск минимален (экспорт синхронен в web-процессе); уникальность пары «неделя + ревизия» гарантирована ограничением БД.
- Восстановление из бэкапа **нетранзакционно**: файлы из проверенного манифеста перезаписываются по одному (каждый атомарно). При краше в середине восстановления часть файлов может быть обновлена, часть — нет; рекомендуется перед восстановлением делать свежий бэкап и останавливать web/воркеры.

## 5. Выгрузки и происхождение данных

- Оригиналы (сообщения, аудио, raw-STT, оригинальные выгрузки) неизменяемы конвейерами; повторные прогоны создают новые версии (`vM`) и ревизии (`rN`). Частые повторы увеличивают число файлов в `data/exports/`; политики хранения/автоочистки нет (риск роста при многолетнем использовании).
- Удаление сообщения необратимо и по явному подтверждению пользователя (ADR-011 / T15): ставится метка `deleted_at`, стираются `body_text` и текст транскрипций, файл аудио удаляется с диска. Восстановления нет; производные артефакты и уже сделанные недельные выгрузки удаление не трогают, поэтому удалённый текст может остаться в них. Если удаление файла с диска не удалось (например, права), байты остаются «сиротой»: приложение их больше не отдаёт и не расшифровывает, автоповторов очистки нет.
- Временные файлы атомарных записей и `--clean-temp` работают только с `data/temp/`; другие каталоги автоматически не чистятся.
- Формат выгрузок фиксирован: TXT для оригинала и нормализации, Markdown для саммари и wellbeing-рефлексии. Другие форматы (PDF/DOCX) не реализованы.

## 6. Wellbeing-рефлексия

- Рефлексия недиагностическая, запускается только явным действием пользователя и отключается настройкой (`APP_WELLBEING_ENABLED=false`).
- Классификатор уровней консервативен: ложное срабатывание `urgent` допустимо, пропуск — нет. Эскалационный контент фиксированный и поддерживается отдельно от кода; приложение не предоставляет медицинскую/психологическую помощь.

## 7. Наблюдаемость и диагностика

- `GET /ready` проверяет только **доступность SQLite** (лёгкий `SELECT 1`); состояние миграций и наличие настроенных профилей/моделей он не проверяет (для этого есть jobs и страница `/privacy`).
- В логах присутствуют request id и безопасные метрики job'ов (длительность, модель/провайдер, токены, размеры файлов), но **никогда** содержимое дневника; формат и уровень логирования фиксированы (настройки для смены уровня/формата нет).
- `docs/privacy-and-safety.md` §4 и `AGENTS.md` §8 остаются источником истины по логам.

## 8. Окружение, зависимости, операции

- При смене `APP_TIMEZONE`/`APP_*` нужен перезапуск процессов (settings кэшируются при старте).
- В прогонах тестов видны deprecation-предупреждения библиотек (например, `StarletteDeprecationWarning` про `httpx`/`starlette.testclient` и алиас `anyio.abc.BlockingPortal`). На поведение MVP они не влияют и устраняются обновлением зависимостей.
- WSL 2 / Docker: данные желательно держать на ext4 (не `/mnt/c`); в контейнерах ожидается UID/GID владельца `data/` (по умолчанию 1000); GPU-профиль требует NVIDIA driver + nvidia-container-toolkit и настраивается отдельно.
- **Устройство LLM слоёв фазы 2 — названный компромисс (измерено в T13, `docs/device-choice.md`).** На GPU (текущий дефолт) LLM и Whisper делят 6 ГБ VRAM, поэтому действует veto «STT и LLM не в VRAM одновременно»: либо холодная LLM (`OLLAMA_KEEP_ALIVE=0`, +3.5–4.6 с на каждый вызов), либо осознанная выгрузка через `asr.run()` (**сделано в T11**, см. `ADR-010`). На CPU (теги `diary-*-cpu`, `num_gpu 0`, конфиг `configs/models.cpu.example.yaml`) VRAM свободна целиком и Whisper может быть резидентным на GPU, но операция занимает 32–127 с вместо 1.6–10.3 с (prefill ≈ 45×, генерация ≈ 6.6× медленнее) и ~4–4.6 ГБ RAM заняты постоянно, а пороги T10 (5 с / 15 с) на CPU недостижимы и без решения пользователя не пересматриваются.
- Единая SQLite-БД и очередь при многолетнем активном использовании могут потребовать архивирования старых недель; автоматической политики нет.
