# Local Diary — бэклог второй фазы (T00–T12)

- Архитектурное решение: [`decisions/ADR-007`](decisions/ADR-007-second-anchor-family-for-derivational-layers.md) (вариант B — вторая семья якорей происхождения).
- Операционный контракт: [`../AGENTS.md`](../AGENTS.md); цикл задач: [`execution-protocol.md`](execution-protocol.md) §7 (Ведущий → агент-разработчик → агент-приёмщик).
- Источник истины по первой фазе остаётся [`../tasklist.md`](../tasklist.md) (Task 01–19, MVP принят). Этот документ — бэклог **второй** фазы; он не переписывает первую фазу и не отменяет её решений.

## 1. Контекст

MVP привязывает все производные артефакты к оригинальной недельной выгрузке (`weekly_exports`, `NNNN`/`rN`/дата воскресенья). Пользователь добавил второй бэклог T00–T12 и принял вариант **B**: вторая семья якорей происхождения — от сообщения, дня и ISO-недели — и новый **слой 5 `coach_note`**. Существующий слой 4 (`wellbeing`) не заменяется и не изменяется.

Что уже сделано в рамках фазы 2:

- **T00** — контракты (`src/diary/domain/contracts/`, 5 моделей + `COACH_DISCLAIMER`), производные JSON Schema (`schemas/`, генератор `scripts/generate_contract_schemas.py`, `make contracts`), golden-набор из 10 синтетических RU-чанков (`eval/golden/`), ADR-007, этот документ, тесты `tests/unit/test_contracts_schemas.py` и `tests/unit/test_golden_manifest.py`.

Всё остальное ниже — запланировано, но **не реализовано**; задачи исполняются строго по номерам, одна задача за раз, после явного подтверждения (AGENTS.md §2).

## 2. Роли A1–A5

| Роль | Зона ответственности | Владеет |
|---|---|---|
| **A1** | Контракты и golden-набор | `src/diary/domain/contracts/`, `schemas/`, `eval/golden/`, `scripts/generate_contract_schemas.py`, ADR по контрактам |
| **A2** | Промпты и LLM-слои фазы 2 | `prompts/stt_corrected|daily_summary|weekly_summary|coach_note/`, сервисы слоёв, конфигурация профилей фазы 2 |
| **A3** | Хранилище и миграции | `src/diary/db/`, `alembic/`, единственный владелец изменений схемы |
| **A4** | Рантайм: очередь, оркестрация, UI/API | `src/diary/workers/`, `src/diary/api/`, `src/diary/templates/`, обработчики job'ов фазы 2 |
| **A5** | Eval и приёмка | `eval/` (harness), `docs/known-limitations.md`, приёмочные прогоны, `docs/acceptance-log.md` |

Правило владения: файл меняет только роль-владелец. Задача, которой нужен чужой файл, сначала возвращается Ведущему (новый анализ и план), а не «правится по ходу».

## 3. Сквозные правила фазы 2

1. **Одна задача — один коммит**: коммитит только Ведущий, после вердикта `accepted` агента-приёмщика (execution-protocol.md §7).
2. **Схема БД — только T08** (роль A3). Никакая другая задача фазы 2 не меняет `src/diary/db/models.py` и `alembic/`.
3. **Промпты — только T04–T07** (роль A2). Новые промпты версионируются `v<N>`; существующие промпты первой фазы не правятся.
4. **Никакие правки первой фазы** без отдельного ADR: пайплайны `pipelines/normalize|summarize|wellbeing`, `core/models_config.py` (кроме T02), `configs/*`, существующие энумы.
5. **Никаких новых зависимостей** без отдельного решения (AGENTS.md §10). Контракты, схемы и harness живут на stdlib + Pydantic.
6. **Приватность**: только синтетические данные в golden, фикстурах, отчётах и логах harness; содержимое дневника не попадает в Git-отслеживаемые файлы и логи (AGENTS.md §7–8).
7. **Две семьи якорей не смешиваются**: первая (`NNNN`/`rN`/воскресенье) продолжает обслуживать слои 1–4; вторая (`raw_id`/`date`/`week_id`) — слои фазы 2 (ADR-007 §1, §5).
8. **Невалидный вывод LLM = failed run**, без частичного артефакта (AGENTS.md §15).

## 4. Задачи

### T00 — Контракты + 10 golden-чанков RU

- **Владелец:** A1. **Зависимости:** нет. **Статус:** реализовано, ожидает приёмки.
- **Скоуп:** пять контрактов фазы 2 (`raw_entry`, `stt_corrected`, `daily_summary`, `weekly_summary`, `coach_note`) + `COACH_DISCLAIMER`; `ContractModel` с `extra="forbid"`, `contract_name`, `schema_version`; генератор JSON Schema (`make contracts`, `--check`); `schemas/`; golden-набор: ровно 10 синтетических RU-чанков (3/3/2/2) + манифест; ADR-007; этот документ; unit-тесты контрактов, схем и golden.
- **DoD:** `make lint`, `make typecheck`, `make test`, `make contracts`, `generate_contract_schemas.py --check` проходят; `schemas/*.json` байт-в-байт равны регенерации; golden валиден против контрактов, `chunk_chars` совпадает с фактическим входом, privacy-инвариант не пересекается с `data/`.
- **Veto:** миграции БД; правки `db/models.py`, `alembic/`, существующих энумов, существующих пайплайнов, `core/models_config.py`, `configs/*`; создание `prompts/*`; новые зависимости; реальное содержимое дневника в golden; `git add/commit/push` агентом-разработчиком.

### T01 — Рантайм-обвязка контрактов фазы 2

- **Владелец:** A1. **Зависимости:** T00.
- **Скоуп:** единый путь «структурированный ответ LLM → контракт»: строгий разбор JSON, валидация через `ContractModel`, ошибка = failed run без записи артефакта; передача JSON Schema контракта в промпт (schema-driven запрос); заполнение envelope-полей (`model`, `prompt_ver`) **бэкендом** из разрешённого профиля и версии промпта; отказ от парсинга чего-либо из свободного текста ответа.
- **DoD:** невалидный ответ не создаёт артефакт и не портит вход; envelope-поля заполняются кодом и покрыты тестами; схемы не дублируются (берутся из моделей или из `schemas/`); тесты на лишнее поле, отсутствие поля, неверный тип.
- **Veto:** чтение `model`/`prompt_ver` из ответа модели; изменения контрактов T00 без нового ADR; «мягкая» валидация с игнорированием лишних полей.

### T02 — Профили моделей и контекстный бюджет фазы 2

- **Владелец:** A2. **Зависимости:** T00, T01.
- **Скоуп:** новые профили задач фазы 2 (коррекция, дневная/недельная сводка, coach-note) и параметр контекстного окна (`num_ctx`), согласованный с правилом eval-контракта (8192 по умолчанию; 16384 для недельного чанка, который подаётся несколькими кусками — ADR-007 §9).
- **Ограничение (обязательное).** `ModelsConfig` объявлен с `extra="forbid"`, а все четыре профиля MVP (`transcription`, `normalization`, `summarization`, `wellbeing_analysis`) — **обязательные**; рабочий файл `configs/models.yaml` не коммитится (`.gitignore` исключает `configs/*.yaml`) и не обновляется централизованно. Поэтому **любой новый профиль/ключ фазы 2 обязан быть опциональным** (значение по умолчанию, выключенное состояние): необязательный профиль означает «слой фазы 2 отключён», а не ошибку. Обязательное новое поле сломает старт **принятого** приложения у пользователя (`load_models_config` → `ModelsConfigError` на его существующем файле) — этого делать нельзя.
- **DoD:** существующий `configs/models.yaml` без новых ключей остаётся валидным (тест на «старый» конфиг); отсутствие профиля фазы 2 отключает соответствующий слой без падения; наличие профиля включает его; секреты — только имя переменной окружения; `num_ctx` не влияет на слои первой фазы.
- **Veto:** обязательные новые поля/профили; значения секретов в YAML; изменение обязательности существующих четырёх профилей.

### T03 — Дневной агрегатор (отбор сообщений дня)

- **Владелец:** A2. **Зависимости:** T00, T01, T02.
- **Скоуп:** отбор сообщений одного календарного дня в `APP_TIMEZONE`, сборка входа `raw_entry[]` (порядок хронологический, идентичность сообщений сохраняется), границы дня и переходы времени (DST), отказ при пустом дне, отсутствие агрегации недели в этой задаче.
- **DoD:** тесты границ дня (00:00, 23:59, смена пояса/DST); вход собирается без изменения источника; пустой день — явная ошибка/пустой результат, а не пустая сводка; маппинг `messages`/`transcriptions` → `raw_entry` покрыт тестами (включая нетранскрибированное аудио с пустым `text`).
- **Veto:** изменение собранного входа; подмешивание сообщений других дней; правки схемы БД.

### T04 — Слой `stt_corrected`: промпт v1 + сервис

- **Владелец:** A2. **Зависимости:** T00–T02.
- **Скоуп:** `prompts/stt_corrected/v1.md`; вызов профиля коррекции для одного сообщения; валидация ответа контрактом `stt_corrected`; заполнение `model`/`prompt_ver` бэкендом; сохранение исходного сообщения и сырой транскрипции без изменений.
- **DoD (обязательно).** Маркер сомнения — **только `uncertain[]`, литерал `[?]` не вводится**: `text` содержит фразу без пометок, `uncertain` — список дословных подстрок `text` (валидатор контракта), промпт требует именно такой формы и запрещает вставлять маркеры в текст. Плюс: тесты на сообщение без сомнений и с несколькими сомнениями; исправление не добавляет имена/числа, отсутствующие во входе; сырой вход не изменён байт-в-байт.
- **Veto:** литерал `[?]` или любой другой маркер внутри `text`; правки входного сообщения/транскрипции; чтение `model`/`prompt_ver` из ответа модели; правка промптов первой фазы.

### T05 — Слой `daily_summary`: промпт v1 + сервис

- **Владелец:** A2. **Зависимости:** T03, T04 (общая обвязка T01/T02).
- **Скоуп:** `prompts/daily_summary/v1.md`; сводка дня по `raw_entry[]`; валидация контрактом; факты — только из источника.
- **DoD:** `energy` не выдумывается: при отсутствии высказывания источника поле остаётся `None` (тесты на «источник молчит» и на явное высказывание); `facts` непусты и проверяются на grounding (числа и имена из входа); `date` — календарный день `APP_TIMEZONE`; вход не изменён.
- **Veto:** значение `energy` по умолчанию; факты, которых нет во входе; агрегация нескольких дней «заодно».

### T06 — Слой `weekly_summary`: промпт v1 + сервис

- **Владелец:** A2. **Зависимости:** T05.
- **Скоуп:** `prompts/weekly_summary/v1.md`; сводка по `daily_summary[]` недели; `week_id` в ISO-формате; чанкинг входа при превышении контекстного бюджета (правило `num_ctx` из T02/ADR-007 §9) с сохранением порядка; `rollup` — grounded текст без советов.
- **DoD:** `week_id` соответствует ISO-неделе своего понедельника (`%G`-год, ADR-007 §5); `set(daily_ids) ⊆ вход`; `rollup` непуст и оценивается инвариантами, а не эталонной строкой; при дроблении входа части не теряются и не дублируются; входные сводки не изменяются.
- **Veto:** привязка недельной сводки к недельной выгрузке (`weekly_exports`) вместо ISO-недели; потеря/дубль дня при чанкинге; советы и диагнозы в `rollup`.

### T07 — Слой 5 `coach_note`: промпт v1 + сервис

- **Владелец:** A2. **Зависимости:** T06.
- **Скоуп:** `prompts/coach_note/v1.md`; заметка над одной `weekly_summary`; валидация контрактом; `summary_id` = `week_id` сводки; обязательная оговорка `COACH_DISCLAIMER`; ручной запуск с подтверждением (автозапуск запрещён, ADR-006 применяется и к слою 5).
- **DoD:** ровно 3 наблюдения и 2 гипотезы; `experiment_7d` содержит явный горизонт «7»; `disclaimer` равен `COACH_DISCLAIMER`; запрещённые лексемы (диагноз, лечение, «тебе следует») отсутствуют в сгенерированных полях; слой 4 не затронут (отдельная константа оговорки, отдельный промпт, отдельный тип прогона).
- **Veto:** объединение слоя 5 с wellbeing; переиспользование или правка `wellbeing.safety.DISCLAIMER`; автозапуск анализа; гипотезы, сформулированные как установленные причины.

### T08 — Миграция БД: дельта схемы под вариант B

- **Владелец:** A3. **Зависимости:** T00, T01. **Блокирует:** T09, T11.
- **Скоуп (единственный владелец схемы в фазе 2):** снять или обойти ограничение `artifacts.export_id NOT NULL`, которое сегодня запрещает артефакты без недельной выгрузки (ADR-007 §10); ввести хранение результатов второй семьи якорей (записи/артефакты с полями `raw_id`/`date`/`week_id`/`summary_id`, версией результата, путём, хэшем, ссылкой на `processing_runs` и временными метками); Alembic-миграция; индексы по новым якорям; обратная совместимость данных MVP.
- **DoD:** `make migrate` проходит и на чистой БД, и на БД с данными MVP; существующие записи `weekly_exports`/`artifacts` не портятся; трассируемость «результат фазы 2 → источник (сообщение/день/неделя) → прогон» проверяется тестом; миграция не содержит пользовательских данных и секретов (AGENTS.md §9).
- **Veto:** изменение существующих энумов и смысла существующих колонок без нового ADR; изменения схемы в любой другой задаче фазы 2; миграции, требующие ручной правки продовой БД пользователя.

### T09 — Очередь и воркер фазы 2

- **Владелец:** A4. **Зависимости:** T08.
- **Скоуп:** новые типы задач очереди для слоёв фазы 2; атомарный claim, retry/backoff и idempotency по существующей механике MVP; безопасные сводки ошибок; метрики job'ов без содержимого дневника; восстановление после рестарта.
- **DoD:** задачи переживают рестарт; один job не обрабатывается двумя воркерами; повторный запуск не дублирует результат (новая версия вместо перезаписи); при падении не остаётся частичного артефакта; логи без содержимого дневника — проверяется тестом.
- **Veto:** обработка слоёв фазы 2 в HTTP-запросе; логирование текста дневника/промптов; изменения схемы БД.

### T10 — Eval-harness golden-набора

- **Владелец:** A5. **Зависимости:** T04–T07, T08–T09.
- **Скоуп:** прогон 10 golden-чанков из `eval/golden` через слои фазы 2; проверка инвариантов каждого чанка (`invariants` из манифеста): вывод валидируется контрактом, вход не изменён, запрещённые лексемы отсутствуют, grounding, `uncertain ⊂ text`, `week_id`, `daily_ids ⊆ вход`, 3/2/7/оговорка; проверка контекстного бюджета (`chunk_tokens_est ≤ num_ctx − reserve`); отчёт pass/fail по чанкам без содержимого дневника.
- **Пороги (обязательные).** Правка STT — **менее 5 секунд** на чанк; дневная сводка — **менее 15 секунд** на чанк; прохождение — **не менее 8 из 10** golden-чанков (манифест: `threshold {pass: 8, total: 10}`, `latency_budget_s {stt_fix: 5, daily: 15}`).
- **DoD:** harness читает набор только через `diary.domain.contracts.golden` (никаких собственных парсеров формата); в CI проверяются инварианты на мок-провайдере (без сети и GPU); прогон на реальном локальном провайдере — ручной, с отчётом (латентность, pass/fail); при падении ниже порогов задача считается невыполненной.
- **Veto:** снижение порогов без решения пользователя; запись реального содержимого дневника в отчёты/логи; изменение golden-набора «под результат» (правка входов или инвариантов ради прохождения).

### T11 — UI/API фазы 2

- **Владелец:** A4. **Зависимости:** T08–T10.
- **Скоуп:** страницы/эндпоинты для дня, недели, списка заметок и правок; ручной запуск каждого слоя с явным подтверждением (coach-note — обязательно); отображение `uncertain` отдельным списком с подсветкой фрагментов в тексте; статусы задач и безопасные сводки ошибок; предупреждение о внешнем провайдере перед вызовом.
- **DoD:** пользователь без API проходит путь «сообщение → правка → день → неделя → заметка»; исправленный текст не теряет связь с исходным; отображается оговорка `COACH_DISCLAIMER`; автозапуска нет; HTML безопасен к инъекциям.
- **Veto:** автозапуск анализа; раскрытие секретов/стектрейсов; смешивание эндпоинтов слоя 4 и слоя 5 без явного различия.

### T12 — Приёмка второй фазы

- **Владелец:** A5. **Зависимости:** все предыдущие.
- **Скоуп:** e2e-сценарий фазы 2 на моках; проверка полной трассируемости второй семьи якорей; обновление `docs/known-limitations.md` и `README.md`; приёмочный чек-лист и вердикт в `docs/acceptance-log.md`.
- **DoD:** e2e проходит в CI; первичные данные не изменяются ни при одном сбое; документация описывает ограничения (включая статус `num_ctx` и вторую семью якорей); вердикт зафиксирован.
- **Veto:** заявление о готовности без прогона порогов T10; «приёмка заодно» вместе с незавершённой задачей.

## 5. Veto-список фазы 2 (сквозной)

Любое из перечисленного — остановка задачи и возврат к Ведущему (AGENTS.md §1, §11, execution-protocol.md §3–4):

1. Изменения схемы БД вне T08 (включая `src/diary/db/models.py`, `alembic/`, существующие энумы).
2. Правки существующих пайплайнов (`pipelines/normalize|summarize|wellbeing`), промптов первой фазы и `configs/*` вне T02.
3. Обязательные новые поля/профили в конфигурации, ломающие старт принятого приложения (T02).
4. Новые зависимости (в том числе `jsonschema`) без отдельного решения (AGENTS.md §10).
5. Литерал `[?]` или другой маркер сомнения внутри текста (ADR-007 §3, T04).
6. Выдуманное значение `energy` (ADR-007 §4, T05).
7. Изменение принятого контракта без нового ADR и поднятой `schema_version` (ADR-007 §2).
8. Реальное содержимое дневника в golden, фикстурах, отчётах harness, логах или Git (AGENTS.md §7–8).
9. Автозапуск wellbeing/coach-анализа и любая замена или правка слоя 4.
10. Обход проверок (`--no-verify`, отключение линта/тестов/типов) и «зелёный» отчёт без фактического прогона.
