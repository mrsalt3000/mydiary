## 1. Цель продукта

Локальный пайплайн дневника: правка ошибок STT, суммаризация, советы по развитию и wellbeing.

Железо: ноутбук (заявлено 32 ГБ RAM; в WSL видно 15 ГБ — вероятный лимит WSL2 в 50 % от хоста), 6 ГБ VRAM, WSL2, Ollama.

Основная модель: `qwen3.5:4b` (Q4), целиком на GPU, `num_ctx` 8192 по умолчанию, до 16384 для недели кусками.

**STT и LLM никогда не работают одновременно:** голос → ASR → выгрузить Whisper → LLM.

## 4. Контракты (зафиксированы в T00)

```
raw_entry:      id, ts, source=text|voice, text, audio_path?
stt_corrected:  raw_id, text, uncertain[], model, prompt_ver
daily_summary:  date, facts[], themes[], energy, open_questions[]
weekly_summary: week_id, daily_ids[], rollup
coach_note:     summary_id, observations[3], hypotheses[2], experiment_7d, disclaimer
```

Реализация: `src/diary/domain/contracts/`, производные JSON Schema — `schemas/` (`make contracts`, детерминированно, `--check`).

**Правило версий: AI-слой только append. Повторный прогон = vN+1. raw не трогать.**

Отступления от буквы постановки, принятые пользователем при приёмке T00 (см. ADR-007):

- маркер сомнения — **только `uncertain[]`** (дословные подстроки `text`); литерал `[?]` не вводится, промпт T04 обязан это соблюдать;
- `energy` при отсутствии высказывания источника — `None`, не выдумывается;
- `model`/`prompt_ver` заполняет бэкенд, не LLM;
- категория golden `wellbeing` реализуется контрактом `coach_note`.

## 5. Профили LLM

| Профиль | temperature | ctx | Правила |
|---|---|---|---|
| `diary-stt` | 0.15 | 8192 | Орфография, пунктуация, фонетика. Не выдумывать факты, не сглаживать эмоции, не улучшать стиль. Неуверен → оставить фразу в `text` без пометки и внести её в `uncertain[]` |
| `diary-sum` | 0.25 | 8192 | Сначала дни, потом merge недели. Только факты/темы/энергия/открытые вопросы. Без советов и морали |
| `diary-coach` | 0.4 | 8192 | Только по явному запросу. Формат 3 наблюдения + 2 гипотезы + 1 эксперимент на 7 дней. Не диагноз |

**Точные числа вместо диапазонов (решение T02).** Бриф задавал диапазоны `temperature` — 0.1–0.2 (`diary-stt`), 0.2–0.3 (`diary-sum`) и 0.4 (`diary-coach`); диапазон — это границы выбора, а в артефакты попадает одно число. Зафиксированы 0.15 / 0.25 / 0.4. **`ctx 4096` для `diary-stt` из прежней версии этого документа отменён:** у всех трёх тегов общий `num_ctx 8192` (DoD T02, §9.9).

**Источник истины — согласованная пара.** `temperature` живёт в двух местах и обязана совпадать: `PARAMETER temperature` в `ollama/Modelfile.stt|sum|coach` и поле `temperature` соответствующего профиля (`diary_stt`/`diary_sum`/`diary_coach`) в `configs/models.example.yaml`. Расхождение запрещено, потому что `resolve_completion_params()` (`src/diary/domain/llm/providers.py`) всегда отправляет `temperature` из профиля — то есть Modelfile молча проигрывает. Согласование проверяет автотест (`tests/unit/test_models_config.py`), он падает при расхождении в любую сторону.

**Контекстный бюджет.** `num_ctx` задаётся **только в `Modelfile`** — OpenAI-совместимый API Ollama его не принимает (docs.ollama.com/api/openai-compatibility). Значит `num_ctx` — не поле профиля в `configs/models.yaml`, а свойство созданной модели: у трёх тегов фазы 2 это общий `num_ctx 8192` (T02). Правило 16384/8192 — из eval-контракта: формулировка («8192 по умолчанию, 16384 для недельного чанка, который подаётся кусками») живёт в `eval/golden/README.md` (функция `num_ctx_for()`) и в ADR-007 §9; в `eval/golden/manifest.json` есть только `budget_default.num_ctx = 8192` и `latency_budget_s`. В рантайме ветка 16384 достигается дроблением входа, а не вторым тегом.

## 9. Сквозные правила и ограничения фазы 2

1. **Схема БД — только T08.** Никакая другая задача не меняет `src/diary/db/models.py` и `alembic/`.
2. **Промпты — только T04–T07.** Версионируются `v<N>`; промпты первой фазы не правятся.
3. **Никаких правок первой фазы** (пайплайны слоёв 1–4, существующие энумы, `configs/*` вне T02) без отдельного ADR.
4. **Никаких новых зависимостей** без отдельного решения (AGENTS.md §10).
5. **Приватность:** только синтетические данные в golden, фикстурах, отчётах и логах; содержимое дневника не попадает в Git и логи (AGENTS.md §7–8).
6. **Две семьи якорей не смешиваются** (ADR-007 §1, §5).
7. **Невалидный вывод LLM = failed run**, без частичного артефакта (AGENTS.md §15).
8. **Новые профили в конфигурации обязаны быть опциональными.** `ModelsConfig` объявлен с `extra="forbid"`, а четыре профиля MVP обязательные, при этом рабочий `configs/models.yaml` не коммитится. Обязательное новое поле сломает старт **принятого** приложения на существующем файле пользователя. Отсутствие профиля фазы 2 = слой отключён, а не ошибка.
9. **`num_ctx` — свойство модели, не профиля** (см. §5).
10. **GPU-серийность.** `OLLAMA_MAX_LOADED_MODELS=1`, `OLLAMA_NUM_PARALLEL=1`; перед ASR-джобой LLM выгружается (`ollama stop` / `serve-ollama.sh unload`). Полноценная арбитрация GPU-слота — T03/T09; до неё правило обеспечивается конфигурацией рантайма и порядком вызовов.
11. **Канал `reasoning` тратит `max_tokens`.** `qwen3.5:4b` размышляет и оплачивает это тем же лимитом генерации: при исчерпании `max_tokens` поле `content` приходит пустым, а это для нас невалидный вывод = failed run (п. 7). **С T02b размышление можно выключить:** `reasoning_effort` — опциональное поле профиля и запроса; `OpenAICompatibleProvider` отправляет его, только если оно задано (отсутствие = ключа в payload нет, прежнее поведение). Профили фазы 2 в примере конфига несут `reasoning_effort: none`. Замер интеграции T02b+T04 на теге `diary-stt`: та же правка STT — **1.2 с, 46 выходных токенов** против 47 с и пустого `content` при включённом размышлении. `reasoning_effort` — **подсказка, а не гарантия**: сервер вправе её проигнорировать, поэтому признак успеха — `usage` и латентность, а не факт отправки поля (ADR-009). Суффикс `… /no_think` в промпте по-прежнему **не действует** (проверено), `think` нативного API не используется. `max_tokens` профилей фазы 2 включают запас на размышление на случай, если его включат явно; для больших недельных входов (T06) и порога T10 значения перепроверить.
12. **`presence_penalty 1.5` — названный риск (T02).** Штраф за повтор токенов (`presence_penalty 1.5`, а также `top_k 20` и `top_p 0.95`) наследуется от базовой `qwen3.5:4b` и в T02 намеренно не переопределяется. Для `diary-stt` штраф потенциально вредит верности правки: повтор слова источника — не ошибка, а именно то, что мы хотим сохранить. Решение — по golden в T10 и, при необходимости, в T04; до этого риск считается названным и принятым, а не забытым.
13. **Capability `vision` подтверждена и бюджет VRAM не съедает.** У `qwen3.5:4b` в capabilities есть `vision` (сервер стартует с `--mmproj`), но замеры T01: резидентный размер 3.2 ГБ, пик 3925 MiB из 6144 при `num_ctx 8192` — до порога чеклиста §7 (пик < 5.5 ГБ) остаётся запас. Перепроверять при смене модели/кванта/контекста.
14. **`/v1` не наследует `top_p` тега.** Через `/v1/chat/completions` эффективный `top_p` = `1.0`, тогда как `ollama show <tag> --parameters` показывает `0.95`; `top_k` и `presence_penalty` доезжают корректно (проверено в T02 по логу сэмплера). То есть по проводу приложение работает с `top_p 1.0`, а значение `0.95` действует только для нативного `/api/*` и при прямом `ollama run`. **Оговорка про `temperature`:** она доезжает только потому, что приложение всегда отправляет её из профиля (`resolve_completion_params`, `src/diary/domain/llm/providers.py`); произвольный клиент `/v1`, не указавший `temperature` явно, получит `temp = 1.0` — то есть Modelfile-значение через `/v1` не действует ни для `top_p`, ни для `temperature`. Учитывать при разборе качества на T10 и не полагаться на `/v1` как на «тег целиком».
15. **`ollama ps` показывает резидентный тег, а не тот, что ответил.** Пока в VRAM загружен один тег `diary-*`, запрос к другому тегу обслуживает тот же раннер (`load_duration` — единицы мс, строк загрузки нет), при этом sampler-параметры берутся из **запрошенного** тега. Поэтому `ollama ps` нельзя читать как «какая модель ответила»; надёжный наблюдаемый признак — значения сэмплера в логе (`temp = 0.150` / `0.250` / `0.400` для `diary-stt` / `diary-sum` / `diary-coach`). Строка `msg="template selection" model=…:latest` ориентиром **не является**: она пишется только при загрузке модели и потому называет тот же резидентный тег, что и `ollama ps`.
16. **`create-phase2` идемпотентен.** `ollama create` перезаписывает существующий тег: повторный запуск безопасно пересоздаёт `diary-stt`/`diary-sum`/`diary-coach` из парных Modelfile (проверено: exit 0, три `success`, при идентичном содержимом идентификаторы тегов не меняются). `ollama rm` перед повторным созданием не требуется.
17. **Исключение для первой фазы (решение пользователя, 2026-09-19).** В `src/diary/domain/transcription/providers.py` строка импорта `faster_whisper` изменена с `# type: ignore[import-not-found]` на `# type: ignore[import-not-found,import-untyped]`. Причина: предсуществующий дефект — `faster-whisper` установлен без `py.typed`, поэтому mypy выдаёт `import-untyped`, не покрытый старым кодом ignore; ошибку маскировал инкрементальный кэш mypy, и правка `models_config.py` в T02 её проявила. Изменение чисто типовое, поведения не меняет; обе крайности (пакет отсутствует / пакет без типов) остаются покрытыми. Других правок первой фазы вне T02 нет.

## 13. F1: инварианты в рантайме (T17 → T17b)

**Почему.** Приёмка фазы (§7, пункты 4–5) зафиксировала воспроизводимый дефект: причинные связки, подмена числа и инверсия смысла доходили до сохранённых артефактов. Причина — инварианты `no_advice_or_judgement`, `no_causal_claims`, `no_new_facts` существовали **только в `eval/`**: ни оркестратор, ни слои, ни воркер их не применяли, поэтому в продакшне гарантия держалась на тексте промпта. ### T17 — единый модуль инвариантов и честность проверок (выполнено)

**Задача.** Вынести логику проверок в рантайм-импортируемый модуль, переиспользовать её в харнессе (один источник — дрейф невозможен) и убрать ложные срабатывания, из-за которых гейт в рантайме отвергал бы корректный вывод.

**Сделано.**

- Новый `src/diary/domain/contracts/invariants.py` — единственная реализация трёх проверок, плюс `InputFacts` (вход, приведённый к тексту и числам, считается один раз), `InvariantViolation` и `violation_summary` — **единственная форма нарушения, пригодная для логов**: имена проверок и счётчики, без текста дневника (AGENTS.md §7–8). Подробность `detail` цитирует токен и остаётся доступной харнессу.
- `eval/run.py` переведён на модуль: собственные копии хелперов удалены, три проверки делегируют общему коду, имена проверок и тексты подробностей сохранены — поведение харнесса не изменилось (`--strict` 10/10, 28 тестов харнесса зелёные).

**Измерение на реальном корпусе** (согласованные снимки баз сессии, только чтение; рабочий `data/` не тронут; 43 артефакта с восстановимым входом):

| | артефактов-нарушителей | ложных `no_new_facts` | настоящих нарушений |
|---|---|---|---|
| до правок | 8 | 8 (stt 2, день 2, неделя 4) | 2 причинные связки |
| после правок | **1** | **0** | **2** (те же связки) |

Числа воспроизведены независимым приёмщиком **двумя способами**: прогоном текущего модуля и загрузкой дорефакторного харнесса как модуля с вызовом его собственных проверок на том же корпусе. Обе дороги дают 8 → 0.

**Три исправленных класса ложных срабатываний.** Они **неравноценны по доказанности**, и это здесь фиксируется прямо:

1. **Источник пишет число словами — измерено на корпусе (единственный класс, который там встречается).** «…утром ходил в басейн, плавал **сорок** минут» → слой сохраняет «сорок», а проверка нормализовала слово в цифру `40` и искала **цифру** во входе. Лечение: `InputFacts.numbers` включает и цифры, и числа, записанные во входе словами. Этот класс объясняет **все 8** ложных срабатываний; подстановка числа по-прежнему ловится (находка T07 «два» против «трёх»), различие формы записи — нет. Мутационная проверка: снятие правки возвращает ровно 8 нарушений (`сорок`/`три`) и валит 6 тестов.
2. **Константа самого слоя — есть записанное срабатывание, но не в этом корпусе.** Живой харнесс сообщал его на golden-чанке coach-01 («семь дней», приёмка T12 и T10b); среди снимков сессии класс не наблюдался, потому что артефакты, где он возможен, — ровно те, чей вход не восстанавливается. Лечение: константа контракта разрешена в любом его поле; в контракте, который её не объявляет, та же цифра остаётся выдумкой (покрыто тестом). На корпусе правка **инертна** (снятие не меняет ни одного числа).
3. **Заглавная буква после двоеточия — случаев нет вовсе.** Отдельный поиск приёмщика по 799 артефактам (1148 заглавных слов в сгенерированных полях) не нашёл ни одного случая «двоеточие/тире + заглавная»; синтетический пример живёт только в тесте. Это не измеренный дефект, а **исправление заведомо неверного правила**: по орфографии заглавная после двоеточия именем не является. Правка **инертна** на корпусе, поэтому оставлена как устранение класса, а её цена (имя, введённое двоеточием, не проверяется) признана явно.

1. **Источник пишет число словами.** «…утром ходил в басейн, плавал **сорок** минут» → слой сохраняет «сорок», а проверка нормализовала слово в цифру `40` и искала **цифру** во входе. Лечение: `InputFacts.numbers` включает и цифры, и числа, записанные во входе словами. Подстановка числа по-прежнему ловится (находка T07 «два» против «трёх»), различие формы записи — нет.
2. **Константа самого слоя.** «Сон нарушался **семь дней** подряд» в `observations` отвергалось, хотя 7-дневный горизонт — параметр слоя, объявленный его же контрактом в `experiment_7d`. Лечение: константа контракта разрешена в любом поле этого контракта; в контракте, который её не объявляет, та же цифра остаётся выдумкой (покрыто тестом).
3. **Заглавная буква после двоеточия.** «Наблюдение: **Первый** день прошёл спокойно» считалось выдуманным именем. Лечение: двоеточие и тире открывают новое предложение для проверки имён. Принятая потеря: имя, введённое двоеточием посреди фразы, не проверяется — случай, не встречающийся в корпусе, и он оставлен тестом, чтобы правило не «починили» обратно.

**Тесты и гейты.** `tests/unit/test_invariants.py` — 22 теста: ложные срабатывания (по одному на класс), настоящие нарушения (совет, причинная связка, выдуманное число, выдуманное имя, подмена числа), константы по полям, `violation_summary` без текста дневника, чтение входов из контрактных моделей. **Мутационная проверка проведена дважды:** Ведущим до коммита и независимым приёмщиком (в копии дерева, оригинал не тронут). Правка №1 валит 6 тестов и возвращает 8 нарушений в корпусе; правки №2 и №3 валят по 2 теста и **не меняют счёт корпуса** — что и подтверждает их инертность, заявленную выше. `make lint`, `make typecheck`, `mypy --no-incremental` (104 файла; отдельно `eval/run.py`), `make test` = **1286** (полный прогон делал Ведущий; приёмщик независимо повторил харнесс 10/10, 28 тестов харнесса, ruff и mypy).

**Побочный эффект, зафиксированный приёмкой.** Общий модуль изменил и **другие** grounding-проверки харнесса, которые берут те же факты входа: `names_and_numbers_grounded` и `numbers_grounded` стали мягче ровно настолько же (число, записанное во входе словом, теперь заземляет цифру вывода). Это осознанная цена «одного источника»: факт — то, что модуль считает фактом, и меняется это во всех проверках сразу, а не расходится между копиями. Golden-прогон (`--strict` 10/10) и 28 тестов харнесса от этого не пострадали.

**Найдено при подготовке (в скоуп T17 не входило):** шаблон промпта coach использует форму «попробуйте», а `ADVICE_EVALUATION_LEXEMES` считает её советом, то есть гейт отверг бы корректную заметку. Измерено: в 11 реальных coach-артефактах форма не встречалась — противоречие латентное, но структурное. Решение вынесено в T17b.

### T17b — гейт в рантайме (выполнено)

**Задача.** Заставить слои проверять собственный вывод **до** сохранения. T17 сделал проверки честными, но не обязательными; без гейта F1 не закрыт.

**Сделано.** Новая ошибка `PipelineInvariantError` (наследник `PipelineOutputError` → `PipelinePermanentError`, дополнительно несёт имена нарушенных проверок в `checks`, чтобы харнесс зачитывал отказ без разбора сообщения); новый гейт `src/diary/domain/pipelines/quality.py` с `generate_with_invariants` (не более `GENERATION_ATTEMPTS = 2` генераций, затем отказ); гейт подключён в четырёх сервисах слоёв — `stt_fix`, `sum_daily`, `sum_weekly`, `coach`; в недельном слое проверяются и частичные сводки (против своего куска), и итоговая (против дней недели). Политика и её обоснование — **`ADR-012`**: отказ, а не пометка; повторная генерация — свежий вызов, а не правка текста; ошибка постоянная, поэтому воркер не уходит в retry-цикл; наружу выходит только `violation_summary` (имена проверок и счётчики), без текста дневника.

**Найдено и исправлено по ходу.**

- **Первый veto продукта не применялся в рантайме.** Базовый запретный список слоя `DEFAULT_FORBIDDEN_LEXEMES` («диагноз», «лечение», «тебе следует») существовал только в eval-проверке `forbidden_lexemes`, то есть запрет на диагнозы в продакшне держался **на промпте**. Теперь он входит в проверку советов, которую применяет гейт.
- **Промпт coach противоречил проверке.** `v2` перечислял среди допустимых форм «попробуй, если захочется…», а `ADVICE_EVALUATION_LEXEMES` считает это советом: при гейте модель, следуя промпту, получала бы отказ всей заметки. Создан `prompts/coach_note/v3.md` (`v1` и `v2` не тронуты, `git diff` по ним пуст), слой переведён на `v3`. Две машинные проверки: пример из промпта обязан проходить гейт; список допустимых форм не может содержать лексему из списка запретов.
- **Харнесс и гейт.** Негативные тесты харнесса полагались на то, что слой **сохранит** нарушающий вывод и его зачтёт харнесс. Теперь слой отказывает, поэтому харнесс ловит `PipelineInvariantError` и зачитывает чанк как провал названных гейтом проверок, а собственные проверки харнесса остались **второй линией защиты** (их точность проверяется прямыми вызовами и юнит-тестами модуля). Попутно закрыта находка T10b «харнесс не переживает ошибку слоя» — для этого класса.
- **Четыре фикстуры выдумывали данные.** Тексты тестов добавляли числительное («три тыщи восемьсот», «версия 1», «Частичная сводка 0»), которого не было во входе; гейт правильно их отвергал. Фикстуры сделаны согласованными с источником (числительные заменены словами там, где число не нужно), а не наоборот.

**Доказательства политики — замером, а не намерением.** (а) На корпусе из 43 реальных артефактов после правки проверок остаётся **1** нарушитель (~2 % прогонов требуют повторной генерации). (б) **Живой прогон** гейта на четырёх чанках, где нарушения измерялись ранее (`coach-01/02`, `week-01/02`): **4/4 инварианта, ни одного отказа** — гейт не отвергает корректную работу. Оговорка: неделя в харнессе по-прежнему идёт по GPU-профилю `diary_sum` (находка **F6**), поэтому CPU-маршрут `diary_week` этим прогоном не покрыт.

**Тесты и гейты.** Новые `tests/unit/test_quality_gate.py` (9 тестов: чистая генерация, повтор, постоянный отказ, `checks`, отсутствие текста в сообщении и логе, пустой источник, ограниченность попыток) и интеграционный `test_a_completion_that_breaks_an_invariant_stores_nothing` (нарушающий вывод → отказ, ноль артефактов, raw-строки не тронуты, ровно 2 вызова модели). Плюс две проверки согласованности промпта coach. `make lint`, `make typecheck`, `mypy --no-incremental` (105 файлов; отдельно `eval/run.py`), `make test` = **1298**.

**Остаётся открытым (не блокеры).**

- **Временные метки как факты** — **закрыто 2026-09-22 в T32**: источник заземления сужен до содержания записей, замер до/после на золотом корпусе (10/10 принятых «якорных» чисел → 0/10, ложных срабатываний **на корпусе** 0; цена — проба «сводка называет свой день/дату» 5/5 → 0/5, таких выводов на корпусе нет). - **Недельный профиль в харнессе (F6)** и пороги латентности с `KEEP_ALIVE` — **закрыто 2026-09-20**: F6 исправлен в T19, пороги разведены по маршрутам в T21, решение по `KEEP_ALIVE=0` зафиксировано в §14.0 и `docs/device-choice.md` §12.

**Что дала независимая приёмка (и что исправлено по её итогам).** Приёмщик работал в копии дерева, оригинал не тронут; его прогон живьём повторил 4/4 инварианта и ни одного отказа. Подтверждено приёмщиком вопреки моим ожиданиям: у слоя `stt_corrected` гарантия — «нет **привнесённых** советов и причин» (оговорка верности источнику работает), а у генеративных слоёв оговорки нет, и это правильно; ветка «источник без содержимого» через сервисы **недостижима** (метка времени и `source` попадают в текст входа), то есть она страховка, а не ослабление продакшна.

## 14. Следующий блок: гигиена харнесса (T18–T21) и дом (T22)

**Почему этот блок первым.** F1 закрыт (T17 + T17b, §13), но **измеримость осталась сломанной**: харнесс по-прежнему складывает нарушение латентности и нарушение инварианта в одно число (F5), недельный профиль мапится на `diary_sum` (F6), константы бюджета в eval-контракте занижены, а у coach-слоя гейта бюджета нет вовсе. Пока это так, красный прогон неотличим от холодного старта, а маршрутизация T13b не покрыта регрессиями. Блок **поведение продукта не меняет** — он чинит измерение, чтобы всё последующее (мелочи T11, UI-хвосты, T09-перевод ручной расшифровки) можно было принимать по числам, а не по впечатлению.

### T18 — развести счётчик латентности и счётчик инвариантов (F5)

| | |
|---|---|
| Владелец | A5 Eval |
| Тип | гигиена измерения; поведение продукта не меняет |
| Где | `eval/run.py` (итоговый счёт и печать), `tests/integration/test_eval_harness.py`, `eval/golden/README.md` (описание счёта) |
| Находка | F5: нарушение латентности и отказ по инварианту считаются одним числом, поэтому «9/10» читается как нарушение содержания, хотя это холодная загрузка модели |

**DoD:**

1. Счёт по инвариантам и счёт по латентности печатаются **раздельно**; итоговая строка не складывает их в одно число.
2. Причина провала чанка видна без разбора лога: имя проверки и маршрут (`latency stt` / `latency week`, `causal_claims_absent`, `pipeline_invariant_refused`).
3. Порог «8/10» применяется к счёту **инвариантов**; латентность сравнивается со своим бюджетом и называется отдельно (сам бюджет — T21).
4. Отказ гейта (`PipelineInvariantError`) и провал по латентности различимы в выводе **и в тестах**: по одному негативному тесту на каждое событие.
5. `--strict` (CI) остаётся детерминированным: без сети и модели, повторный прогон даёт тот же результат.
6. Ничего не ослабляется: набор чанков, инварианты и значения бюджетов не меняются — меняется только представление счёта.

**Запреты:** не менять проверки и лексиконы; не прогревать модель (прогрев — вопрос `KEEP_ALIVE`, решён в §14.0: `0`); не трогать слои, промпты и артефакты.

### T19 — покрыть харнессом недельный профиль (F6)

| | |
|---|---|
| Владелец | A5 Eval (+ Ведущий: профиль в конфиге примеров) |
| Тип | регрессионное покрытие маршрута T13b |
| Где | `eval/run.py` (`PROFILE_NAME_BY_CATEGORY`), `eval/golden/manifest.json` и `README.md`, `tests/integration/test_eval_harness.py` |
| Находка | F6: категория `week` мапится на `diary_sum`, поэтому профиль `diary_week` и CPU-тег `diary-sum-cpu` регрессиями **не проверяются вовсе**; живой прогон недели идёт по GPU-маршруту |

**DoD:**

1. `week` в харнессе идёт через профиль `diary_week` — тот же, которым пользуется слой `weekly_summary` в продакшне, то есть харнесс измеряет работающий маршрут.
2. Тест-страж закрепляет маппинг `week → diary_week`; возврат на `diary_sum` валит тест (проверено мутацией).
3. Живой прогон недельного чанка идёт на CPU-теге и подтверждается **наблюдаемым признаком** (лог сэмплера / `ollama ps`), а не только значением конфига.
4. Отсутствие профиля `diary_week` в конфиге = слой честно выключен, а не падение харнесса (§9.8 сохраняется).
5. У чанка недели в выводе назван использованный профиль — разница маршрутов видна в отчёте.
6. Порог латентности недели берётся из её маршрута (T21); после T21 недельный живой прогон на CPU не должен читаться как нарушение содержания (связка с T18).

**Зависимость:** T19 после T21 (иначе живой прогон недели на CPU всегда красный по бюджету 15 с). Допускается свести T19 и T21 в один этап с раздельными приёмками.

**Запреты:** не менять промпты и чанки; не возвращать неделю на GPU-профиль ради зелёного прогона.

### T20 — бюджеты: оценка из файла промпта и гейт для coach

| | |
|---|---|
| Владелец | A5 Eval (+ Ведущий: `src/diary/domain/contracts/golden.py`) |
| Тип | гигиена измерения + отсутствующий гейт бюджета |
| Где | `src/diary/domain/contracts/golden.py` (`LAYER_PROMPT_TOKENS_EST`, `BUDGET_RESERVE_TOKENS`), `eval/run.py`, тесты eval-контракта, `src/diary/domain/pipelines/coach/**` (только гейт, промпт не трогать) |
| Находка | Константы занижены: неделя 1629 → 3132, coach 1968 → 4029 (подтверждено приёмкой T10b). С исправленной константой проверка бюджета для coach-чанков уходит за 8192 (8518 и 8387) — то есть занижение маскировало именно coach-категорию. У coach-слоя гейта бюджета нет вовсе (ни `NUM_CTX`, ни `estimate_tokens`) |

**DoD:**

1. Оценка промпта считается **из файла промпта** во время прогона (тем же коэффициентом, что и чанкинг), а не хранится ручной константой: правка промпта больше не может «незаметно» съесть бюджет.
2. Тест согласования: оценка из файла против объявленной константы (по образцу `PROFILE_MAX_TOKENS` против примера конфига) — расхождение валит тест в обе стороны.
3. Проверка бюджета честная: `оценка промпта + reserve ≤ num_ctx`; превышение — провал, а не молчание.
4. У coach-слоя появляется гейт бюджета (как у дня и недели): превышение даёт громкую ошибку **до** вызова модели.
5. Ни один промпт не урезается и не переписывается ради прохождения гейта. Если объявленный бюджет не сходится — фиксируется честный провал и варианты решения (урезать вход / снизить `max_tokens` / дробить), но не тихая правка констант.
6. Свободный бюджет недели (≈964 оценочных токена) пересчитывается и попадает в `eval/golden/README.md`, влияя на порог чанкинга (T06) и на T09/T11.

**Запреты:** правка промптов, лексиконов, чанков и `max_tokens` профилей; изменение `num_ctx` тегов (T02) — только отдельным решением.

## 15. T24 — NLI-валидация суммаризации (T24a, T24b и T26 выполнены; недельная формулировка измерена и отвергнута)

**Основание:** `docs/nli-validation-analysis.md` — анализ, замеры на трёх судьях (NLI-модель ONNX/CPU, локальный 4B, лексические прокси) и честные ограничения. Задача заведена 2026-09-21 по решению пользователя «сначала задача, потом исполнение»; **код не начинался**.

**Проблема, которую закрываем.** Сегодня суммаризация валидируется формой контракта, лексиконами (советы/причинность) и заземлением цифр, числительных и имён собственных. Дыра названа приёмкой T10 и остаётся: **выдумка и абзац-пересказ без цифр и имён, а также инверсия смысла без лексического маркера** машинно не проверяются. NLI меряет ровно это — следует ли утверждение сводки из источника.

**Измерения, на которых стоит задача** (детали и таблицы — в `docs/nli-validation-analysis.md` §3):

- NLI-модель `rubert-base-cased-nli-threeway` (ONNX, CPU) даёт **31–39 мс на пару**, ноль VRAM, без `torch`/`transformers`: инверсия «позже плана» — contradiction p=0.68, подмена числа «девяносто минут» — contradiction p=0.97;
- на **реальной** сводке слоя дня (`day-03`, живой прогон 6.88 с) все 6 утверждений — entailment p=0.86–0.98, **ложных срабатываний ноль**;
- выдумку без противоречия модель **не ловит** (entailment p=0.53, margin 0.07 — тот самый пример «плохое самочувствие»), а правило «всё должно следовать» **наказывает верную генерализацию** («плавал» → «тренировка», neutral);
- 4B-судья: 7/7 на структурированном промпте, но **5/7** на перефразированном (4.67–9.35 с, занимает GPU/VRAM, судит свою же сводку) — как гейт отклонён;
- веса пинуются: `model.onnx` 711 690 609 Б sha256 `ee870cef…c6c2c`, `model.fp16.onnx` 356 088 115 Б sha256 `e838a882…a48e`.

**Развилка по недоступной модели решена пользователем 2026-09-21: fail-closed** («если NLI недоступен — Fail»). Харнесс с флагом `--nli` печатает `FAILED: the NLI check could not run: …` и возвращает код 1, если весов нет, extra не установлен, sha256 не совпал или судья ответил не тем числом строк; без флага инструмент не загружается вовсе.

**Подтверждено фактом 2026-09-22; причина признака «задано явно» уточнена замером 2026-09-23.** Условие
подмены — **значенческое**: `if current == DEFAULT_DATA_ROOT / subdir` в `_resolve_data_paths`, то есть
«задано ли значение» не проверяется вовсе, и подменяется **любое** заданное значение, равное дефолтному,

который получает `model_validator(mode="before")`: замер на копии `130b4b3` со снятыми из окружения
переменными `APP_*` даёт `{}` в чистом окружении, `{'data_root': …}` при `APP_DATA_ROOT=…`, `{'db_dir': …}`
при `APP_DB_DIR=…`, и — то, что решает задачу — **`APP_DB_DIR`, равный дефолтному значению, в словаре

pydantic-settings передаёт в модель слитый набор источников») была артефактом замера — в окружении сессии
экспортированы 15 переменных `APP_*` (тот же набор, что в локальном `.env`; проверка `env | grep -c '^APP_'`).
Источники передают **только** заданные поля (замер выше), но присваивание полю в pydantic v2 помечает его
заданным, поэтому after-хук `130b4b3` сам дописывает в множество шесть каталогов и `data_root`: в чистом
окружении `model_fields_set` равен семи полям, а с вырезанным телом хука — пуст (замер 2026-09-23). Приёмник `nli_model_dir` уже сообщает понятно
(`NliUnavailableError` с полным путём и подсказкой про `scripts/fetch-nli-model.sh`), поэтому DoD 4
закрывается отказом от подмены, а не проверкой существования каталогов (веса качает скрипт позже —
проверка сломала бы свежий чекаут).
