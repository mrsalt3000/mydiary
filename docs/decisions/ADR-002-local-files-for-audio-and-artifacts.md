# ADR-002: Локальная файловая система для аудио и артефактов выгрузки

- Status: Accepted
- Date: 2026-09-09

## Context

Аудиосообщения и еженедельные артефакты (оригиналы и производные TXT/Markdown) — крупные двоичные/текстовые данные, которые нецелесообразно хранить внутри SQLite. Требуются: неизменяемость оригиналов, версионирование производных артефактов, атомарная запись и понятная структура каталогов для бэкапов.

## Decision

Аудиофайлы и файлы артефактов хранятся на локальной файловой системе под управляемыми серверными путями; SQLite хранит метаданные, хэши и безопасные относительные пути (ADR-001). Схема каталогов:

- `data/audio/YYYY/MM/` — аудио, имена генерируются сервером (UUID), пользовательские имена/пути не принимаются.
- `data/exports/01_original/`, `02_normalized/`, `03_summaries/`, `04_wellbeing/` — слои артефактов.
- `data/temp/` — временные файлы (очистка по политике Task 18); `data/backups/` — бэкапы (Task 18).

Запись файлов — атомарная (временный путь → flush/fsync → rename). Все пути, отображаемые пользователю/в UI, — относительные и безопасные.

## Consequences

Положительные:

- Простая работа с большими файлами, воспроизведение/скачивание без раздувания БД.
- Естественная неизменяемость оригиналов и версионирование через именование файлов (ADR-005).
- Бэкап «БД + каталоги» прозрачен (Task 18).

Отрицательные/требующие внимания:

- Согласованность «файл ↔ запись БД» должна обеспечиваться кодом (порядок записи, очистка при сбое — Task 07, атомарность — Task 10/12).
- Каталоги данных — личные и локальные; реальное содержимое `data/` не должно попадать в Git (политика `../data/README.md`; `.gitignore` — Task 01).

## Alternatives considered

- Хранение BLOB в SQLite: приемлемо для текста, неудобно для аудио и бэкапов больших объёмов; отклонено.
- Объектное хранилище/S3: внешняя зависимость, вне скоупа MVP.
