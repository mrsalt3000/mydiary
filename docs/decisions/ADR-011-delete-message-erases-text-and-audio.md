# ADR-011: Удаление сообщения стирает его текст и голосовой файл (явное действие пользователя)

- Status: Accepted
- Date: 2026-09-20
- Развивает и **ограничивает** ADR-005 (первичные данные неизменяемы); заменяет
  политику удаления, зафиксированную в Task 05 и миграции
  `0002_messages_soft_delete`. Исполняется в задаче **T15**
  (`docs/tasklist-phase2.md` §12).

## Context

**Политика Task 05 (что было).** Удаление сообщения — это только метка:
`DELETE /api/v1/messages/{id}` ставит `messages.deleted_at = utc_now()`,
строка остаётся в БД, `body_text` не перезаписывается, скрытые записи не
попадают в историю. Это прямо следует из ADR-005: класс «источник» (сообщения,
аудио, сырые транскрипции, оригинальные выгрузки) неизменяем, ни один конвейер
его не модифицирует, файлы не перезаписываются. В `docs/known-limitations.md`
ограничение было названо честно: «Удаление сообщений — только soft-delete
(скрытие из истории); жёсткого удаления и восстановления нет».

**Запрос пользователя (2026-09-20).** «Добавить удаление сообщений. и звук, и
текст». Решение пользователя по развилкам: удаление делает метку `deleted_at`
**плюс** физическое стирание — файл `.webm` с диска и текст (`messages.body_text`
и текст транскрипций). Производные артефакты (нормализация/саммари/wellbeing,
`artifacts`) и файлы недельных выгрузок (`exports/01_original`,
`exports/02_normalized`) остаются как история — это принятое следствие, а не
дефект.

**Почему это не «перезапись оригинала» в смысле veto фазы 2.** ADR-005 и veto
§2.3 (`docs/tasklist-phase2.md`) запрещают **тихую правку источника конвейером**:
LLM-слой не имеет права менять/переписывать raw, повторный прогон не трогает
оригинал. Речь идёт о необратимой операции по **явному действию пользователя**,
которая в контракте проекта разрешена отдельно: AGENTS.md §14 — «Действия, …
удаляющие данные …, — только через явное действие/подтверждение пользователя в
UI или CLI с обязательным флагом подтверждения», и там же назван пример
«удаление сообщений по политике». То есть это не самовольная правка источника, а
исполнение воли владельца данных над своими же данными: конвейеры по-прежнему
не могут изменить raw ни на байт, а удаление остаётся доступным только человеку
через интерфейс с подтверждением.

**Чего в схеме нет.** Миграции для T15 не нужны: `messages.deleted_at`
существует с `0002`. Политика меняется, схема — нет.

## Decision

1. **Единственный путь удаления — существующий.** Расширяется тот же
   сервисный путь, что и в Task 05 (`chat.service`: теперь `delete_message`,
   ранее `soft_delete_message`) и тот же endpoint `DELETE
   /api/v1/messages/{id}` (204/404). Второго механизма удаления нет; отдельного
   «жёсткого» API/эндпоинта не вводится.
2. **Метка остаётся.** `deleted_at` по-прежнему ставится: он скрывает запись из
   истории и из всех выборок конвейеров (`MessageRepository` фильтрует
   `deleted_at IS NULL`), то есть служит и признаком «удалено» для
   трассируемости.
3. **Текст стирается.** `messages.body_text` обнуляется для любого типа
   сообщения, и `transcriptions.raw_text` обнуляется у **всех** транскрипций
   всех аудиофайлов этого сообщения (включая служебную строку
   `not_requested`). Строки `transcriptions` при этом сохраняются: их статус,
   профиль/модель, время и `metadata_json` — это история прогонов, а не текст
   пользователя.
4. **Байты стираются.** Файл голосового сообщения удаляется с диска
   (`Path.unlink(missing_ok=True)`, ошибки ОС глушатся — тот же подход, что в
   `diary.domain.audio.service._unlink_safe`). Строка `audio_files` сохраняется:
   на неё ссылаются строки `transcriptions`, а линия происхождения результата
   слоя (`artifacts.raw_id` → `messages.id`) обязана оставаться разрешимой.
   Удалять строки значило бы рвать и внешние ключи, и якоря второй семьи.
5. **Порядок: сначала атомарный переход БД, потом файл.**
   `deleted_at` + стирание текста + `commit()` выполняются одной транзакцией, и
   только после успешного коммита удаляются байты. Обоснование:
   - источник истины — БД (ADR-001), а сам переход является атомарным: либо
     сообщение помечено и текст стёрт, либо не изменено ничего (тогда удаление
     можно повторить, файл цел);
   - обратный порядок (сначала `unlink`, потом БД) оставляет худшее состояние:
     файла нет, а сообщение всё ещё видно в истории и «воспроизводится» отказом —
     то есть пользователь видит неконсистентность;
   - при выбранном порядке сбой удаления файла (например, `EACCES`) даёт
     «метка стоит, байты остались» — и это состояние **не** видно приложению:
     воспроизведение удалённого голосового отказывает по п. 6 независимо от
     наличия байтов. Остаточный файл — это утечка места на диске, а не
     противоречие в состоянии; она называется здесь честно.
6. **Воспроизведение удалённого голосового — понятный отказ.**
   `resolve_audio_file` (домен аудио) отказывает с `AudioNotFoundError` → HTTP
   404, если сообщение-владелец помечено `deleted_at`. Это гарантия не зависит
   от того, удались ли байты физически, и заодно закрывает случай
   уже поставленной в очередь STT-джобы: она падает перманентно
   («аудиофайл больше не существует»), не создавая текст заново.
7. **Производные артефакты и выгрузки не трогаются.** `artifacts` (слои 2–5,
   включая `stt_corrected` с текстом правки), файлы `exports/**` и
   `weekly_exports` остаются как история: это производные данные, а не оригинал.
   `trace_layer_result` продолжает работать — строка `messages` сохранена.
8. **Идемпотентность.** Повторное удаление не падает и не меняет состояние:
   запись уже помечена → `MessageNotFoundError` → HTTP 404, который интерфейс
   трактует как «уже удалено». Восстановления нет (как и в Task 05).
9. **UI: удаление только через подтверждение.** Действие есть у каждого
   сообщения (текстового и голосового), подтверждение — не визуальная подсказка,
   а отдельный шаг с настоящей кнопкой (после нажатия «Удалить» сообщение можно
   только «Да, удалить»/«Отмена»), 404 в интерфейсе = «уже удалено».

## Consequences

**Что становится необратимым:**

- текст записи (`body_text`) и текст всех её транскрипций уничтожаются;
- байты голосового файла уничтожаются (`.webm`/`.ogg`/`.wav`/… в
  `<APP_DATA_ROOT>/audio/YYYY/MM/`);
- восстановления нет: ни soft-delete-отмена, ни бэкап внутри приложения
  (бэкапы Task 18 — отдельный механизм и отдельное решение).

**Что остаётся:**

- строка `messages` и `deleted_at` (факт и время удаления, трассируемость);
- строки `audio_files` (метаданные, SHA-256, размер, `storage_path`) и
  `transcriptions` (статусы, профиль/модель, время, `job_id`) — без текста;
- производные артефакты и файлы недельных выгрузок, включая уже посчитанные
  нормализации/саммари/wellbeing и `result_json` слоя `stt_corrected`;
- работоспособность `trace_layer_result` по затронутым артефактам.

**Что инвариант ADR-005 теряет и что сохраняет.** Слово «неизменяем» перестаёт
быть абсолютным для класса «источник»: оригинал может быть уничтожен — но
исключительно явным действием пользователя через подтверждённый UI-путь.
Запрет на правку источника **конвейерами** (вето §2.3) не ослабевает ни в чём:
ни один автоматический путь (`pipeline.py`, воркер, повторный прогон, экспорт)
удаление не вызывает. Проверяется тестами неизменности raw при прогонах слоёв —
они не ослаблены.

**Цена и риски:**

- остаточный файл при сбое `unlink` не виден приложению (п. 6), но занимает
  место на диске; автоповторов очистки нет;
- гонка: STT-джоба, **уже запущенная** в момент удаления (модель считает в этот
  момент), технически может записать строку-успех с `raw_text` в скрытую
  запись — воспроизведение/история её не показывают, но текст окажется в БД.
  Джоба, ещё не начавшая работу, отказывает по п. 6. Закрытие этой гонки —
  отдельное решение (отмена джоб при удалении или проверка `deleted_at` перед
  записью результата), в T15 не входит;
- удаление не трогает уже сделанные бэкапы и внешние копии файлов.

**Открытый пункт (не входит в T15).** Docstring класса `Message` в
`src/diary/db/models.py` продолжает описывать политику Task 05
(«the body is never overwritten»). Файл принадлежит зоне схемы (сквозное правило
§9.1: `src/diary/db/models.py` и `alembic/` — только T08), а изменение схемы для
T15 не требуется, поэтому текст там не правился. Правку docstring нужно провести
владельцу схемы (или отдельным решением), чтобы код не противоречил этому ADR.

## Alternatives considered

- **Оставить политику Task 05** (только метка). Отвергнуто пользователем:
  запрос был «удалить и звук, и текст», а метка не стирала ни байты, ни текст из
  БД (текст оставался читаемым в файле БД и в бэкапах).
- **Жёсткое удаление строк** (`DELETE FROM messages`, `transcriptions`,
  `audio_files`). Отвергнуто: `artifacts.raw_id` — внешний ключ на `messages.id`,
  а `trace_layer_result` строит «результат → источник → прогон» именно по нему;
  удаление строки обрывает линию происхождения и противоречит ADR-005/ADR-007.
  Кроме того, тогда «удалено» перестало бы быть наблюдаемым фактом.
- **Сначала удалить файл, потом поставить метку.** Отвергнуто: при сбое на
  середине пользователь видит живое сообщение со сломанным воспроизведением
  (см. п. 5).
- **Перезаписать байты нулями вместо `unlink`.** Отвергнуто: для целей политики
  не отличается от удаления, но добавляет код и оставляет мусорный файл в
  дереве `audio/`; SSD-семантика перезаписи всё равно не гарантирует
  уничтожение копий.
- **Удалять и производные артефакты/файлы выгрузок.** Отвергнуто решением
  пользователя: производные — история, и они остаются.
- **Канцелярия-подтверждение `window.confirm()`.** Отвергнуто в пользу
  встроенной панели подтверждения: она соответствует принятому в проекте
  паттерну необратимых действий (wellbeing/re-export), доступна с клавиатуры и
  тестируема статически (см. §14 AGENTS.md, T15 DoD 1).
