# ADR-009: Опциональное поле `reasoning_effort` у LLM-профиля и запроса

- Status: Accepted
- Date: 2026-09-19

## Context

Задача **T02b** (решение Ведущего, `docs/tasklist-phase2.md` §10) вынесена по факту замеров фазы 2:

- `qwen3.5:4b` по умолчанию размышляет, и размышление оплачивается тем же `max_tokens`, что и ответ. При `num_predict=16` поле `content` приходит **пустым** (`done_reason=length`), при `num_predict=256` канал `thinking` даёт ~560–750 символов против ответа «Париж» (~222 completion-токена, 3.5–3.8 с). Для приложения пустой `content` — невалидный вывод = failed run (AGENTS.md §15, `docs/tasklist-phase2.md` §9.7).
- Тривиальный ответ стоит ~233 completion-токена / ~3.7 с, а порог T10 для правки STT — **< 5 с**: размышление съедает не бюджет VRAM, а латентность и качество бюджета `max_tokens`.
- `/v1/chat/completions` Ollama 0.34.2 **принимает и слушает** `reasoning_effort: "none"`: 4 completion-токена, 0.44 с, размышления нет. Неизвестные поля сервер игнорирует, ошибок не возвращает.
- `OpenAICompatibleProvider` отправлял только `model`/`temperature`/`max_tokens`/`messages` (`resolve_completion_params`, `src/diary/domain/llm/providers.py`), а `LLMRequest` объявлен с `extra="forbid"` — то есть «прокинуть» поле извне было нельзя ни из конфига, ни из кода. Суффикс `… /no_think` в промпте не действует (проверено).

`reasoning_effort` — штатное поле OpenAI API, а не особенность Ollama: у внешних OpenAI-совместимых провайдеров оно тоже существует (`low`/`medium`/`high`; `none` — выключение размышления там, где канал есть). Поэтому поддержка уместна именно в `OpenAICompatibleProvider`, а код не должен знать про `qwen3.5`/Ollama (ADR-004).

Ограничения, которые решение обязано уважать:

1. **обратная совместимость обязательна:** по умолчанию — ровно прежнее поведение (поле не отправляется); ни один существующий профиль и ни один тест первой фазы не меняются;
2. новый профиль-параметр обязан быть **опциональным** (`ModelsConfig` — `extra="forbid"`, четыре профиля MVP обязательны, а рабочий `configs/models.yaml` не коммитится и существует у пользователя раньше T02b);
3. `null`/пустое значение в payload отправлять нельзя — внешний провайдер может отвергнуть его валидацией;
4. `num_ctx` уже показал, что Modelfile — не универсальное место для параметров запроса (ADR-007 §9).

## Decision

### 1. Поле живёт и в профиле, и в запросе (вариант «в»)

- `OpenAICompatibleProfile.reasoning_effort: ReasoningEffort | None = None` (`src/diary/core/models_config.py`) — значение по умолчанию для задачи;
- `LLMRequest.reasoning_effort: ReasoningEffort | None = None` (`src/diary/domain/llm/models.py`) — переопределение на один вызов.

`ReasoningEffort = Literal["none", "low", "medium", "high"]` объявлен один раз в `core.models_config` (core не зависит от domain) и импортируется моделями запроса.

Выбор варианта «в» мотивирован тем, что он уже принят в проекте для всех прочих параметров генерации: `model`, `temperature`, `max_tokens` имеют ровно эту пару «значение профиля + переопределение в запросе» и сливаются в одном месте — `resolve_completion_params()`. Вводить для нового поля другой механизм значило бы завести второе правило слияния. Профиль — то, чем управляет пользователь в `configs/models.yaml` (и что нужно слоям T04–T07 по умолчанию), запрос — то, чем управляет вызывающий код (например, редкий вызов, которому размышление полезно).

### 2. Отправка только при явном значении

`resolve_completion_params()` добавляет четвёртый параметр в `CompletionParams`, но `complete()` отбрасывает `None`-значения при сборке payload: при `reasoning_effort=None` ключа в JSON **нет вообще**. Это выполняет требования 1 и 3 одним правилом (а не проверкой конкретного поля) и совпадает с прежним поведением по проводу байт-в-байт.

### 3. Ноль изменений по умолчанию

`None` — значение по умолчанию и профиля, и запроса, поэтому:

- четыре профиля MVP и рабочий `configs/models.yaml` пользователя продолжают работать без правок;
- ни один тест первой фазы не меняет поведение (в частности, ожидание «по умолчанию `temperature` 0.2» и форма payload остаются прежними — поле просто отсутствует);
- конфиг **без** нового поля валиден, и это закреплено тестом.

### 4. Поле ставят только профили фазы 2

`configs/models.example.yaml`: у `diary_stt`, `diary_sum`, `diary_coach` стоит `reasoning_effort: none` — по замеру это то, что нужно слоям T04–T07 и порогу T10. Профили MVP не трогаются. `max_tokens` профилей фазы 2 (3072/4096/4096) остаются как есть: уменьшать их в этой задаче нечем измеренно, а запас не мешает (это cap генерации, не резерв VRAM), и он снова понадобится, если для отдельного вызова размышление включат через `LLMRequest`.

### 5. Почему не в Modelfile

- это **параметр запроса**, а не свойство созданного тега: `reasoning_effort` задаётся на конкретный вызов и должен уметь отличаться от вызова к вызову; Modelfile-значение было бы фиксированным для тега и потребовало бы пересоздания модели;
- у Modelfile уже есть ровно этот класс ошибок: Modelfile-значения через `/v1` не действуют или перекрываются профилем (`top_p` не наследуется — `docs/tasklist-phase2.md` §9.14; `temperature` доезжает только потому, что профиль всегда её отправляет). Ставить туда ещё один параметр — множить тихие подмены;
- Modelfile привязан к Ollama, а поле — часть OpenAI-совместимого контракта: держать его в профиле значит не терять провайдер-агностичность (ADR-004).

## Consequences

Положительные:

- слои фазы 2 могут не платить за размышление: у профилей T02 канал выключен, и весь `max_tokens` уходит на ответ (по замеру разница «4 токена / 0.44 с» против «~222 токена / ~3.7 с»);
- поведение по умолчанию не меняется ни для одного существующего профиля или теста;
- параметр доступен и на уровне одного вызова, без правки конфига пользователя;
- поле провайдер-агностично: то же имя понимают внешние OpenAI-совместимые провайдеры.

Отрицательные / требующие внимания:

- `reasoning_effort` — **подсказка**, а не гарантия: сервер вправе её проигнорировать (Ollama игнорирует неизвестные поля). Признак успеха — не факт отправки, а `usage.output_tokens` / латентность, что и проверяется живым замером, а не тестом на payload;
- уровень `none` не является частью «классического» набора OpenAI (`low`/`medium`/`high`); провайдер, который его не знает, может ответить ошибкой валидации 400. Это осознанный выбор значения для локального Ollama; для внешних профилей допустимо `low`/`medium`/`high` или отсутствие поля;
- `max_tokens` профилей фазы 2 остаются с запасом «на размышление» — если канал когда-нибудь снова включат, места хватит, но сейчас запас не используется;
- формулировка `docs/tasklist-phase2.md` §9.11 («`reasoning_effort`/`think` через текущий провайдер **недостижимы**») после T02b верна только исторически: поле теперь достижимо, но **только** если его явно задать. Документ фазы 2 принадлежит Ведущему и этой задачей не правится.

## Alternatives considered

- **Только поле профиля (вариант «а»).** Минимальнее, но вводит второе правило для параметра генерации (у `model`/`temperature`/`max_tokens` переопределение в запросе есть) и не даёт включить размышление для одного вызова без правки пользовательского конфига. Отклонён как асимметричный.
- **Только поле `LLMRequest` (вариант «б»).** Тогда значение нельзя задать в `configs/models.yaml`, то есть требование «поставить `none` профилям фазы 2» выполнялось бы кодом, а не конфигом. Отклонён.
- **Обязательное поле профиля.** Ломает старт принятого приложения на существующем `configs/models.yaml` (`extra="forbid"`, профили MVP обязательны) и противоречит правилу §9.8. Отклонён.
- **Отправлять `reasoning_effort: null`, когда значение не задано.** `null` — не то же самое, что «поля нет»: внешний провайдер может отвергнуть его валидацией, а поведение по умолчанию перестало бы быть прежним. Отклонён.
- **Задать параметр в `ollama/Modelfile.stt|sum|coach`.** Это свойство тега, а не запроса; Modelfile-значения через `/v1` уже показали себя ненадёжными (§9.14), а пересоздание тега ради смены значения — лишний шаг. Отклонён.
- **Только суффикс `… /no_think` в промптах T04–T07.** Проверено: не действует на `qwen3.5:4b`; полагаться на него — значит оставить латентность и пустой `content` нерешёнными. Отклонён.
- **Отдельный флаг `think: false` (нативный `/api/chat`).** Привязывает код к Ollama и к её нативному API, тогда как у нас принята OpenAI-совместимая абстракция (ADR-004). Отклонён.
