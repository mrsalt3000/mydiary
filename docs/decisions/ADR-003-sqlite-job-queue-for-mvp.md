# ADR-003: Durable-очередь задач на SQLite для MVP

- Status: Accepted
- Date: 2026-09-09

## Context

Транскрибация и LLM-конвейеры должны исполняться в фоне отдельным процессом-воркером, переживать рестарты приложения/воркера, не теряться и не обрабатываться дважды. Классическое решение — Redis + Celery — добавляет внешнюю службу и операционную сложность, неоправданную для однопользовательского локального приложения MVP.

## Decision

Для MVP реализуется durable-очередь поверх SQLite (таблица `jobs`, Task 08): статусы `pending`/`running`/`succeeded`/`failed`/`retrying`/`cancelled`; атомарный claim условным UPDATE (`pending` → `running` c владельцем); настраиваемое число попыток с экспоненциальной задержкой; idempotency keys; безопасные сводки ошибок. Воркер — отдельный процесс (CLI/модуль `diary.workers.runner`), разделяющий БД с web-приложением.

## Consequences

Положительные:

- Нет внешних служб; задачи переживают рестарты; атомарность claim'ов в одной транзакции с SQLite исключает двойную обработку.
- Простое развёртывание в Compose (web + worker, Task 17).

Отрицательные/требующие внимания:

- SQLite-очередь не рассчитана на высокий параллелизм и множество воркеров; для MVP достаточно одного-нескольких локальных воркеров.
- Требуются аккуратные политики восстановления «зависших» `running` (таймаут владения) и идемпотентности потребителей.

## Alternatives considered

- Redis + Celery: мощно, но внешняя служба и сложность, не нужные MVP; зафиксировано в пост-MVP бэклоге `tasklist.md` (Kubernetes, Redis, Celery, Kafka — вне MVP).
- In-process asyncio-задачи в web-процессе: не переживают рестарт и не дают отдельного воркера; отклонено.
- APScheduler/файловые очереди: слабее по атомарности и восстановлению; отклонено.
