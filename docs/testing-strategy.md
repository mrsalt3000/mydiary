# Стратегия тестирования

- Архитектурный контекст: `architecture-brief.md`, раздел «Стратегия тестирования».
- Исполнение: `../skills/testing/SKILL.md`; команды появятся после Task 01.

## 1. Слои тестирования

| Слой | Что покрывает | Где |
|---|---|---|
| Unit | доменная логика: границы недель, нумерация/ревизии/версии, статусы задач/прогонов, валидаторы, именование артефактов, правила wellbeing-классификатора | `../tests/unit/` |
| Integration | SQLite/миграции, репозитории, API-роуты, файловое поведение (атомарность, path traversal), очередь и воркер (claim/retry/идемпотентность/рестарт) | `../tests/integration/` |
| End-to-end | полный путь: текстовое сообщение → аудио → мок-транскрибация → выгрузка недели → нормализация → саммари → wellbeing → проверка трассировки (Task 19) | `../tests/` (сценарий e2e) |

## 2. Mocks/fakes и провайдеры

- В обычных прогонах тестов используются **mock/fake-провайдеры** STT и LLM; реальные модели, GPU, скачивание весов и сетевые вызовы в CI не требуются.
- Fake-провайдеры конфигурируются на: успех, таймаут, ошибку аутентификации, rate-limit, сетевую ошибку, невалидный JSON/структуру ответа.
- Интерфейсы провайдеров проектируются так, чтобы подмена была тривиальной (Tasks 09, 11).
- Провайдеры и конфигурация задач валидируются отдельными unit-тестами (Task 03).

## 3. Фикстуры

- **Только синтетические** данные: вымышленные тексты сообщений, синтетические метаданные аудио (без реальных аудиофайлов в Git), сырой STT и мок-результаты LLM.
- Фикстуры размещаются в `../tests/fixtures/`; реальные данные дневника запрещены (см. `privacy-and-safety.md`).
- Синтетический e2e-набор фиксируется в Task 19.

## 4. Ключевые интеграционные сценарии по задачам

- Task 03: валидные/невалидные конфигурации; отсутствие секрета; отсутствие ключей в сериализованном виде.
- Task 04: свежая БД только через Alembic; повторяемость миграций; запись/чтение сущностей; индексы.
- Task 05–06: валидация, порядок, часовой пояс, персистентность, безопасный рендер.
- Task 07: валидация загрузки; согласованность файл↔БД; отсутствие автотранскрибации.
- Task 08: атомарный claim, retry, идемпотентность, переживание рестарта.
- Task 09: фейковый STT; сохранность аудио/сообщения при сбое; история ретранскрибаций.
- Task 10: границы недель, пустая неделя, нумерация без пропусков, ревизии, отсутствующий STT.
- Task 11: безопасные сбои без реальных вызовов.
- Task 12–14: трассировка, именование/версии, чанкинг, невалидный вывод → failed run, оригинал не меняется.
- Task 15: `normal`, `needs_support`, `urgent`, невалидный вывод, отключённое состояние.
- Task 18: манифест бэкапа, path validation.
- Task 19: полный e2e-путь и сценарии ошибок.

## 5. Ожидания по покрытию

- Новое поведение сопровождается автоматическими тестами в той же задаче (правило AGENTS.md §13).
- Критичные инварианты обязательны к покрытию: неизменяемость оригиналов, атомарность артефактов, отсутствие секретов/дневника в логах и Git, детерминированность выгрузок.
- Покрытие измеряется при настройке инструментов (Task 01), целевые пороги устанавливаются там же; «зелёный» результат без проверок не заявляется.

## 6. CI-готовые конвенции команд (появятся после Task 01)

- `make test` — быстрый набор (unit + integration, мок-провайдеры).
- `make lint` — форматирование/линт (Ruff).
- `make typecheck` — статическая проверка типов (mypy или Pyright).
- e2e-сценарий — отдельной целью/командой по мере готовности (Task 19).
- Все команды исполняются из корня репозитория; имена целей фиксируются в Task 01 и не меняются без плана.
