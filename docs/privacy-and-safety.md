# Приватность и безопасность (privacy & safety)

- Архитектурный контекст: `architecture-brief.md`; решения: `decisions/ADR-001…006`.
- Источник требований: `../tasklist.md`, разделы «Privacy and secrets», «Product decisions fixed for MVP».

## 1. Классификация данных

| Класс | Примеры | Обращение |
|---|---|---|
| Личные данные дневника | текст сообщений, аудио, сырые транскрипции, выгрузки, производные артефакты, SQLite-файл, бэкапы | Локально; никогда в Git, фикстурах, скриншотах, публичных артефактах; в логи не пишется |
| Конфигурация (не секретная) | профили моделей без ключей, примеры конфигов | Git-отслеживаема, только синтетические примеры |
| Секреты | API-ключи, токены | Только переменные окружения; в коде/YAML/БД/логах/UI — только имя переменной |
| Метаданные операций | статусы задач, длительности, идентификаторы моделей | Безопасны для логов при отсутствии содержимого дневника |

Реальное содержимое каталога `data/` приватно и не должно попадать в систему контроля версий (политика `../data/README.md`; физический `.gitignore` вводится в Task 01).

## 2. Политика секретов

- Секреты не помещаются в: исходный код, Git-отслеживаемые YAML, SQLite, логи, фикстуры тестов, скриншоты, сообщения об ошибках.
- Конфигурация ссылается на секрет только по имени переменной окружения (`api_key_env`); значение резолвится в рантайме.
- Отсутствие обязательного секрета → понятная ошибка конфигурации без чувствительных данных (Task 03).
- Диагностика профилей не возвращает ключи (Task 03).

## 3. Политика локальных и внешних провайдеров

- Локальная обработка (STT, локальные OpenAI-совместимые эндпоинты) — базовый режим; данные не покидают машину.
- Внешний эндпоинт получает содержимое дневника **только** при: (1) явном включении в конфигурации профиля (`external: true`) и (2) явном раскрытии пользователю в UI/документации (какой провайдер внешний). Автоматических облачных вызовов нет.
- Список «локальный/внешний» для профилей показывается пользователю (Task 16/18 — privacy disclosure view).
- Каждая задача (транскрипция/нормализация/саммаризация/wellbeing) настраивает провайдера независимо.

## 4. Политика логирования

- Запрещено логировать на INFO/WARNING/ERROR: тексты дневника, промпты с содержимым дневника, байты аудио, тексты транскрипций, ответы LLM.
- В логах допустимы: request/job ID, тип задачи, статус, длительность, идентификатор модели/профиля, число токенов при наличии, размеры файлов — без содержимого.
- Ошибки провайдеров логируются безопасной сводкой (класс ошибки), не сырым payload'ом и не полным стектрейсом внешнего сервиса.
- Логи структурированные; настройка — в Task 01, request ID — в Task 19.

## 5. Политика хранения и файлов

- Привязка к localhost по умолчанию (web; worker не публикует порты).
- Загрузка файлов: серверная валидация MIME/размера; серверные имена (UUID); пути пользователя не используются; защита от path traversal на всех пользовательских идентификаторах/путях (Tasks 07, 16, 18).
- Атомарная запись артефактов; временные файлы — только в `data/temp/`.
- Очистка — только `data/temp/` по политике Task 18; исходные аудио/артефакты автоматически не удаляются.
- Бэкапы: режимы «БД + текстовые артефакты» и «полный, с аудио» (Task 18); восстановление — явной командой с обязательным подтверждением.

## 6. Wellbeing: границы безопасности и эскалация

- Wellbeing-анализ — всегда явное действие пользователя; автозапуск запрещён; отключаем конфигурацией.
- Вход — только нормализованные тексты (слой 2); вывод недиагностический (ADR-006).
- Каждый отчёт содержит оговорку о недиагностическом характере.
- Уровни правил `normal` / `needs_support` / `urgent`; для `urgent` — **детерминированный** сценарий: фиксированный эскалационный контент и минимальные метаданные, без управления свободным LLM-текстом.
- Граница ответственности: приложение не оказывает медицинскую/психологическую помощь и не предоставляет кризисную линию; эскалационный контент направляет пользователя к профессиональной помощи.

## 7. Дизайн-границы кризисной эскалации

- Детерминированный классификатор/правила и фиксированный контент проектируются кодом (Task 15) и отдельно от LLM-промпта.
- Классификатор консервативен: пропуск `urgent` недопустим, ложное срабатывание допустимо.
- Запись при `urgent`: безопасный минимум метаданных (без текста рефлексии в логах, если это не требуется для продукта).
- Тесты на синтетических данных покрывают `normal`, `needs_support`, `urgent`, невалидный вывод LLM и отключённое состояние (Task 15).
