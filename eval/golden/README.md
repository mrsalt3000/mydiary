# eval/golden/ — golden-набор фазы 2 (11 синтетических RU-чанков)

Набор проверяет производные слои второй фазы (ADR-007): правку STT, сводку дня, сводку недели и заметку слоя 5. Здесь лежат **входы и машинно-проверяемые инварианты**, а не эталонные ответы: качество оценивается инвариантами (grounding, отсутствие запрещённых лексем), а не совпадением строки.

Формат описан кодом — `diary.domain.contracts.golden` (Pydantic-модели `GoldenChunk`/`GoldenManifest`, `load_manifest()`, `load_chunk()`). И тест T00, и будущий harness T10 читают набор только через него, поэтому описания ниже — комментарий к формату, а не второй источник истины.

## Состав

```text
eval/golden/
├── manifest.json          # версия, порог, миксы, лимиты латентности, список чанков
└── chunks/<id>.json       # ровно 11 чанков
```

| Категория | Контракт | Кол-во | Что проверяет |
|---|---|---|---|
| `stt_error` | `stt_corrected` | 3 | правка сырой транскрипции: фонетика, пунктуация/регистр, имена собственные |
| `day` | `daily_summary` | 4 | сводка одного дня по `raw_entry[]` (в том числе день, который слой **делит** на части) |
| `week` | `weekly_summary` | 2 | сводка недели по `daily_summary[]` |
| `wellbeing` | `coach_note` | 2 | заметка слоя 5 по `weekly_summary` |

Прогон считается успешным, когда **два счёта** сходятся независимо (T18): инварианты — не менее **8 из 11** чанков чистыми (`manifest.threshold`; число выдающихся чанков — решение T00, добавление чанка его не меняет), и латентность — **каждый вызов** каждого чанка с объявленным бюджетом уложился в бюджет **своего маршрута** (T21: правка STT < 5 с и день < 15 с на GPU, неделя < 180 с на CPU; у заметки коуча бюджета нет — T40: бюджет сравнивается с одним вызовом, а не с суммой вызовов чанка, см. «Единица бюджета латентности — один вызов»; T41: вызов сведения поделённого дня судится своим бюджетом 25 с, см. «Бюджет вызова сведения — свой»). Числа никогда не складываются в одно: отказ гейта по инварианту и холодная загрузка модели — разные события.

## Поля чанка

- `id` — идентификатор и имя файла (`chunks/<id>.json`).
- `contract` / `category` — контракт и категория; связаны правилом «одна категория → один контракт» (категория `wellbeing` пишется под `coach_note`, отдельного контракта для слоя 4 нет).
- `lang: "ru"`, `synthetic: true`, `origin: "authored-for-eval"` — набор целиком синтетический; реального содержимого дневника здесь нет и быть не может (AGENTS.md §7).
- `input` — объекты **апстрим-контрактов**: `raw_entry[]` (STT и день), `daily_summary[]` (неделя), `weekly_summary` (заметка).
- `invariants` — ожидания к **выводу** слоя (дискриминированное объединение по `kind`, `kind` всегда равен `contract`).

### Бюджет контекста

- `budget.num_ctx` — 8192 по умолчанию, 16384 для недельного чанка, вход которого подаётся несколькими кусками (`chunks_planned > 1`). Правило закреплено функцией `num_ctx_for()` и проверяется при загрузке чанка.
- `budget.chunk_chars` — длина канонической сериализации `input` (`canonical_input_json()`: `ensure_ascii=False, sort_keys=True, separators=(",", ":")`), то есть длина того, что реально уйдёт в промпт.
- `budget.chunk_tokens_est` — оценка токенов: `ceil(chunk_chars / 2.5)` (`CHARS_PER_TOKEN_EST = 2.5` — константа-документированная оценка для русского текста).
- `budget.chunks_planned` — на сколько **вызовов** рассчитан вход чанка; у дня это число частей, на которые слой делит день. Это **нижняя граница ожидания**, и харнесс её проверяет (`expected_parts`): чанк, объявивший деление, которого слой не делает, зачитывается провалом, а не «на всякий случай» пропускается. У недельного чанка `chunks_planned > 1` поднимает окно (`num_ctx_for`), у дневного — нет: день делится внутри того же 8192.
- `reserve` — фиксированная часть **одного вызова** (промпт слоя + `max_tokens` профиля); правило харнесса `input_tokens_est + prompt_tokens_est + max_tokens <= num_ctx` **на каждый вызов**, где `input_tokens_est` — оценка входа этого вызова: для дня, который делится, это оценка **части** (харнесс спрашивает части у чанкера слоя, `SumDailyPipeline.chunk_entries`), а не всего входа чанка. Таблица чисел и то, как с T20 считается половина `reserve` для промпта, — в разделе «Контекстный бюджет и `reserve`» ниже. Отдельного поля в манифесте нет: `reserve` — производная величина eval-контракта (`BUDGET_RESERVE_TOKENS`, `LAYER_PROMPT_TOKENS_EST`, `PROFILE_MAX_TOKENS` в `golden.py` — заявленное ожидание, которое харнесс проверяет против файлов промптов), зависящая от категории.
- `num_ctx` — правило **eval-контракта**, а не настройка приложения: контекстное окно тега задано в `Modelfile` (T02), профиль ограничивает только `max_tokens`; проводка — задачи T02 и T04–T07 (ADR-007 §9).

Честная пометка про дробление. Ветка «16384 / несколько кусков» правилом описана, но в данных не представлена: ни один недельный чанк не раздут настолько, чтобы его пришлось подавать кусками. **Дневное** деление с T35 представлено: `day-04-long-wednesday` (29 сообщений одного дня, объявлены ≥ 2 частей) не влезает в одно окно — `chunk_tokens_est` 2368 при `reserve` 6220 против окна 8192, то есть старая проверка «чанк целиком» валила бы его, хотя каждая часть влезает (ADR-016 §Consequences 4).

## Семантика инвариантов

Все проверки реализованы харнессом T10 (`eval/run.py`); каждая проверка имеет машинное
имя, и тест харнесса падает, если поле инварианта объявлено, но проверки у него нет.
Неизвестный `kind` — ошибка харнесса, а не молчаливый пропуск.

Общие (`GoldenInvariants`):

- `check_output_contract` — вывод валидируется контрактом (`schemas/<contract>.json`; эти
  схемы генерируются из тех же Pydantic-моделей, которыми валидирует харнесс; невалидный
  вывод = failed run ещё на слое, AGENTS.md §15);
- `check_input_unchanged` — сериализованный вход после прогона байт-в-байт тот же
  (оригиналы неизменяемы, ADR-005); для STT/дневных чанков дополнительно сверяются
  значения строк исходных таблиц (`messages`, `audio_files`, `transcriptions`) до и после
  прогона;
- `forbidden_lexemes` — список лексем, которых не должно быть в **сгенерированных
  текстовых полях** вывода (`GENERATED_TEXT_FIELDS`: `text`, `facts`, `themes`,
  `open_questions`, `rollup`, `observations`, `hypotheses`, `experiment_7d`).
  Фиксированные поля-константы (`disclaimer`) не проверяются: их формулировка задана
  контрактом и именно снимает риск («это не диагноз»), а не создаёт его.
  Харнесс проверяет **объединение** списка чанка и `ADVICE_EVALUATION_LEXEMES` (см. ниже) —
  добавить лексемы чанк может, отключить проверку не может;
- `no_advice_or_judgement` — нет советов/оценок/морали (`ADVICE_EVALUATION_LEXEMES`);
- `no_causal_claims` — нет каузальных связок и утверждённых причин
  (`CAUSAL_CONNECTOR_LEXEMES`) в **утверждающих** полях (`ASSERTIVE_TEXT_FIELDS`).
  `open_questions` исключены намеренно: вопрос обозначает открытый пункт, а не утверждает
  причину, и сам набор (week-01) содержит «Непонятно, из-за чего сбился сон.» как
  легитимный открытый вопрос;
- `no_new_facts` — числа, числительные словами (`NUMERAL_WORDS`) и имена собственные
  вывода grounded во входе.

### Почему списки лексем именно такие

- `ADVICE_EVALUATION_LEXEMES` (`ты молодец`, `молодец`, `умница`, `правильно сделала`,
  `лучше было бы`, `стоило бы`, `тебе следует`, `рекомендую`, `попробуй`, `ты должен`,
  `надо было` и т. п.) — закрывает дыру, зафиксированную приёмкой T05: базовый трио-список
  в чанках (`диагноз`, `лечение`, `тебе следует`) не ловил ни похвалы, ни оценок, ни
  сослагательных рекомендаций. Записи — **узкие фразы**, а не корни: «как следует»,
  «правильный ответ» и подобные обороты остаются допустимыми;
- `CAUSAL_CONNECTOR_LEXEMES` — список, собранный из трёх находок. **Связки и находки приёмок
  T06/T07:**
  `из-за`, `потому что`, `поэтому`, `оттого`, `так как`, `поскольку`, `в результате`,
  `вследствие`, `причин*`, `привел/привёл`, `привело к`/`привела к`/`привели к`, `повлиял*`
  (живые прогоны выдавали «что привело к плохому самочувствию», «из-за ночных пробуждений,
  что повлияло на энергию», «повлияла на» вопреки промптам; оба написания (`е`/`ё`) в
  списке, потому что модель смешивает их). **Семейство «вызвать» (T34):** `что вызв`,
  `что вызыв`, `это вызв`, `это вызыв` — причинное чтение глагола в двух построениях,
  которые утверждают причину; сам глагол в список не входит, потому что «вызвала врача» —
  это визит, а не причинность (замер: 3 отказа из 3 на верной сводке,
  `docs/nli-validation-analysis.md` §12). **Семейство «влияние» (T34, доработка):**
  `влияет`, `влияют`, `влиял`, `влиять`, `влияни` — закрывает формы, которые промпты
  недельного и coach-слоя уже перечисляют как запрещённые, а лексикон пропускал
  («повлияет», «влияет», «влияют», «влияния»), вместе с косвенными падежами существительного
  (`влияни` вместо одиночной формы `влияние`). Голые корни (`влия` — ловит «влиятельного
  человека») и причастия (`влияющ`/`влияю` — ловят «влияющие связи») в список **не**
  входят: оба класса измерены как ложные (§12.1);
- `NUMERAL_WORDS` — кардинальные числительные 2…10, десятки, `сто`, `тысяча` в падежных
  формах. `один/одна/одно` исключены (слишком часто не считают: «один из», «однажды»), как
  и `пара`, `полтора`, `несколько`, `много`. Это делает машинно-проверяемым случай T07
  «два созвона при трёх во входе»: числительное слово нормализуется в цифру и обязано
  встречаться во входе.

### Две оговорки, без которых проверки давали бы ложные провалы

- **Верность источнику у STT** (`LEXEME_FIDELITY_CONTRACTS = {"stt_corrected"}`): правка
  STT обязана сохранять слова говорящего (DoD T04: «не сглаживать эмоции», «не улучшать
  стиль»), поэтому для этого контракта лексема-совет/связка нарушением **не** считается,
  если она уже есть во входе. Нарушение — только **привнесённая** лексика. Живой пример:
  вход stt-02 содержит «надо было» — честная правка обязана его сохранить. Генеративные
  слои (день/неделя/coach) такой оговорки не имеют: их промпты запрещают советы и причины
  безусловно;
- **Константа контракта** (`CONTRACT_CONSTANT_DIGITS`): цифра `7` в `experiment_7d` — это
  горизонт эксперимента, требуемый контрактом (его проверяет `experiment_horizon_days`), а
  не факт, выдуманный моделью; поэтому она исключена из grounding-проверки этого поля.

### Честная граница проверки «нет новых фактов»

Точны только три класса: цифры, числительные словами и имена собственные. Свободные
содержательные слова **машинно не проверяемы** без семантической модели: пересказ
(«трудовой» вместо «работа») и выдумка («плохое самочувствие» из T06) для лексической
проверки неразличимы. Поэтому харнесс печатает неподтверждённые длинные содержательные
токены как **диагностику** (подсказка человеку) и **никогда** не считает их провалом —
выдумывать «зелёную» проверку-пустышку хуже, чем честно назвать пробел. Ещё две границы:
grounding сравнивает со **всеми** содержательными значениями входа, включая метки времени
и якоря (число, встречающееся только внутри `ts`/ISO-даты, считается подтверждённым), а
проверка ищет цифровые токены, поэтому авторское правило 2 (количества — цифрами) остаётся
обязательным.

По категориям:

- `stt_error`: `names_and_numbers_grounded_in_input` — все **числа** вывода встречаются во входе, а все **имена собственные** (слова с заглавной буквы, кроме начала предложения) встречаются во входе **без учёта регистра**; исправлять можно смазанные служебные слова, пунктуацию и регистр, но не придумывать новые имена/числа. `uncertain_values_are_verbatim_substrings_of_text` — каждая запись `uncertain` дословно входит в `text` (то же проверяет валидатор контракта); литерал `[?]` внутри текста не вводится (ADR-007 §3).
- `day`: `expected_date` — дата сводки (календарный день `APP_TIMEZONE`), проверяется против дат входных записей; `expected_energy` — ожидаемый уровень энергии, где **`null` — это положительное ожидание** «источник молчит ⇒ в выводе `null`» (выдуманный уровень = провал чанка); `facts_non_empty`; `numbers_grounded_in_input` — числовые токены вывода есть во входе.
- `week`: `expected_week_id` — ISO-неделя (`YYYY-Www`, ISO-год), сверяется с датами входных сводок; `daily_ids_subset_of_input` — `set(daily_ids) ⊆` даты входных `DailySummary`; `rollup_non_empty`.
- `wellbeing` (`coach_note`): `observations_count == 3`, `hypotheses_count == 2`, `experiment_horizon_days == 7` (в `experiment_7d` явно указан горизонт «7»), `disclaimer_equals_coach_disclaimer` (равенство константе `COACH_DISCLAIMER`).

## Контекстный бюджет и `reserve`

Правило харнесса: `input_tokens_est + prompt_tokens_est + max_tokens <= num_ctx` **на каждый
вызов слоя** (T35; до этого — на чанк целиком, что давало ложный провал на дне, который слой
честно поделил). `input_tokens_est` — оценка входа этого вызова: у чанка, который слой не
делит, это `budget.chunk_tokens_est`, у дневного чанка с `chunks_planned > 1` — оценка
**части**, и части харнесс спрашивает у самого слоя (`SumDailyPipeline.chunk_entries`), то
есть реализация деления одна и на рантайме, и в проверке. `reserve` — фиксированная часть
вызова, которую вход не занимает: версия промпта слоя плюс `max_tokens` его профиля.
**С T20 половину `reserve`, отвечающую за промпт, харнесс считает
не из константы, а из самого файла промпта**, который загружает слой (`eval/run.py`:
`PROMPT_PATH_BY_CATEGORY` берётся из пакетов слоёв, оценка — `estimate_tokens`,
тот же коэффициент 2.5 символа/токен). Константы `LAYER_PROMPT_TOKENS_EST` и
`PROFILE_MAX_TOKENS` в `golden.py` остались **заявленным ожиданием**: тест
`test_the_declared_prompt_overhead_matches_the_template_files` падает при расхождении в
любую сторону. Так промпт, который вырос, больше не может незаметно съесть окно.

Фактические числа измерения T20 (оценка по файлам, `num_ctx 8192`):

| Категория | Промпт-файл | Промпт, токенов | Профиль (`max_tokens`) | reserve | Доступно входу |
|---|---|---|---|---|---|
| `stt_error` | `prompts/stt_fix/v1.md` | 1509 | `diary_stt` 3072 | 4581 | 3611 |
| `day` | `prompts/sum_daily/v1.md` | 2124 | `diary_sum` 4096 | 6220 | 1972 |
| `week` | `prompts/sum_weekly/v2.md` | 3132 | `diary_week` 4096 | 7228 | **964** |
| `wellbeing` | `prompts/coach_note/v3.md` | 4113 | `diary_coach` 2048 | 6161 | 2031 |

Прежние значения (`day` 1932 «измерено в T05», `week` 1629, `wellbeing` 1968) были сняты
с **других** версий промптов и занижали `reserve` до двух раз — у coach-категории проверка
проходила только из-за занижения: `4113 + 4096 = 8209` уже больше окна 8192 **до** входа.
Поэтому T20 снизил `diary_coach.max_tokens` до 2048 (заметка коуча по контракту коротка:
3 наблюдения + 2 гипотезы + эксперимент, живой прогон T07 — ~200 токенов) и запретил
«тихую» правку констант: не сходится — фиксируется провал и решение, а не подгонка.

Оценка токенов — константа `CHARS_PER_TOKEN_EST = 2.5`. Насколько она консервативна,
измерено живыми прогонами 2026-09-20 (`measured input tokens` в отчёте): чанк `day-01` —
оценка 2420 против **2324** фактических (запас 4 %); чанк `week-01` — оценка 3819 против
~**2892** (запас 24 %, из `prompt processing, progress` лога раннера); чанк `week-02`
(замер приёмщика) — оценка 3525 против **2904** (запас 21 %). То есть на этих чанках гейт
консервативен, но не абсурдно: расхождение зависит от доли Markdown/JSON в запросе — и на
длинном JSON-тяжёлом дне знак расхождения переворачивается (замер T35 ниже). Живой прогон харнесса
дополнительно сверяет **измеренный** `usage.input_tokens + max_tokens <= num_ctx` (проверка
`measured_context_budget`) по **самому большому вызову** чанка, а не по последнему (T35: у
дня, поделённого на части, последний вызов — сведение, и он мельче всех), и печатает
максимумы строкой `measured input tokens (endpoint), max call per category`; в таблице
отчёта есть столбец `calls`, по которому видно, что день считался частями.
`tests/integration/test_eval_harness.py` следит, чтобы `PROFILE_MAX_TOKENS` не разошёлся с
`configs/models.example.yaml`.

**Замер частей длинного дня (2026-09-22, T35, живой прогон `--live --chunk
day-04-long-wednesday`, профиль `diary_sum`, тег `diary-sum`, `OLLAMA_KEEP_ALIVE=0`).** День
ушёл в **три** вызова (2 части + сведение), и endpoint измерял по каждому вызову отдельно:

| Вызов | Символов запроса | Оценка, токенов | Измерено endpoint, токенов | Латентность |
|---|---|---|---|---|
| часть 1 (23 записи) | 10223 | 4090 | **4493** | 17.76 с |
| часть 2 (6 записей) | 6579 | 2632 | 2613 | 8.14 с |
| сведение | 7703 | 3082 | 2383 | 18.77 с |

(Строки — живого прогона T35, и части там 23 и 6 записей: строка БД на 5 символов короче чанковой
(`Z` против `+03:00`), поэтому жадное правило приняло на запись больше — на входе чанка те же записи
делятся как `[22, 7]`. В чанковой форме короткие дни дают 6138 / 6065 / 6028 символов
(2456 / 2426 / 2412), а часть 1 входа чанка (22 записи) — 10128 и 4052.)

Отсюда два измеренных факта, которых до T35 в наборе не было. Первый: **оценка перестаёт
быть консервативной на длинном JSON-тяжёлом дне** — на самой большой части она оказалась на
9.0 % *ниже* измеренного (4090 против 4493; 9.9 % от оценки, 9.0 % от измерения), тогда как на коротких днях была на 4 % выше (замер T20: оценка конверта харнесса 2420 против измеренных endpoint 2324);
4493 + 4096 = 8589 уже больше окна 8192, и живой прогон честно показывает
`measured_context_budget`. Это ограничение слоя и оценки, а не харнесса, и решается решением
владельца (окно, `max_tokens` дня или оценка), а не подгонкой числа в наборе — T35 его
**измеряет** и не ослабляет. Второй: **день, который слой делит, не укладывается в 15 с**
маршрута — три вызова заняли 44.7 с машинного времени (полный прогон харнесса — 65–68 с), то
есть бюджет T21 откалиброван на день из **одного** вызова и на поделённый день не
переносится. Оба факта — повод для отдельного решения; `num_ctx`, `max_tokens` дня и
промпты T35 не меняет.

**Замер T39 (2026-09-22): оценка стала поклассной, и живой прогон длинного дня стал зелёным по
бюджету.** Первое следствие T35 выше решено задачей T39, и числа ниже — это тот же инструмент
после решения (тот же `--live`, тот же профиль, `OLLAMA_KEEP_ALIVE=0`, `num_ctx` и `max_tokens`
дня не менялись, чанк-манифест не подгонялся). Оценка входа дня теперь считается по двум
измеренным коэффициентам (`estimate_request_tokens`: кириллица и пробелы 2.5, JSON/обвязка 1.25):

| Проба (символы, `raw: true` `/api/generate`) | Символов | Токенов endpoint | символов/токен |
|---|---|---|---|
| строки UUID | 1109 | 1109 | 1.00 |
| ISO-таймстемпы | 629 | 629 | 1.00 |
| скелет `raw_entry`, пустой текст | 3209 | 2339 | 1.37 |

Длинный день после решения идёт в **4 вызова** (3 части + сведение), и отчёт печатает
`measured input tokens (endpoint), max call per category: day 3508 (cap 4096)` — то есть
**каждый** вызов измерен ниже бюджета 4096, а `measured_context_budget` больше не срабатывает
(остался только провал по латентности — это T40, единица «на вызов» сделана в T40 и сняла ложную
красноту деления; сам вызов сведения выше порога — предмет T41). Короткие дни вердикт не меняют: `day-01/02/03`
остаются одним вызовом (оценка 2585–2630 против 2412–2456 прежней при бюджете 4096 — обе по строке
входа чанка), длинный
делится на 3 части вместо 2. Замеры, решение и его границы (недельный и коуч-слой остаются на
прозовом коэффициенте; вырожденные строки UUID оценены ниже) — `ADR-016`, раздел «Update
2026-09-22 — T39».

**Замер T40 (2026-09-22): бюджет сравнивается с одним вызовом.** Второе следствие T35 («бюджет
дня 15 с откалиброван на один вызов и на поделённый день не переносится») решено задачей T40 без
изменения порогов: единица сравнения — **самый долгий вызов** чанка, время чанка целиком остаётся
в отчёте. Живой прогон длинного дня: части 12.51 / 12.46 / 5.34 с укладываются в 15 с, за бюджет
выходит сведение (18.95 с) — то есть красный вердикт следует из времени одного вызова, а не из
числа вызовов. Числа, таблица по вызовам и границы — раздел «Единица бюджета латентности — один
вызов» ниже.

**Честный предел этой проверки (измерен мутацией приёмки T20).** Оценка из файла гарантирует,
что правка промпта не может **незаметно** съесть бюджет, но не делает чанк красным при любом
росте: +11 % текста к дневному промпту (5310 → 5904 символов) подняло `reserve` c 6220 до
6458, а чанк всё ещё укладывался (6754 ≤ 8192). Громким сигналом в этом случае остаётся
**тест константы** (`test_the_declared_prompt_overhead_matches_the_template_files`), то есть
промпт можно только «перемерить и решить». Провал самого чанка начнётся, когда рост съест
свободный запас категории (для дня — около 1972 оценённых токенов).

Тот же бюджет обязателен и в рантайме (T20): недельный слой дробит вход, если он не влезает
(`NUM_CTX - max_tokens`), а слой коуча дробить нечего — он отказывает громко
(`require_request_fits`), не отправляя усечённый запрос. Свободный бюджет недели — те самые
**964** оценённых токена из таблицы: это порог чанкинга T06 и ограничение на размер сводки
дня. Дневной слой считает бюджет и **делит** вход по записям, когда он не влезает
(`SumDailyPipeline.input_budget_tokens`/`chunk_entries`), а части сводит шаблон
`prompts/sum_daily/v2.md` (T23, `ADR-016`). Харнесс проверяет **тот же предел по частям**
(T35, см. выше) и отдельно требует, чтобы объявленное деление действительно произошло
(`expected_parts`): поделил — проверка идёт по частям, не поделил — это провал объявленного
ожидания, а не «нечего проверять».

## Латентность по маршрутам (T21)

Бюджет латентности — свойство **маршрута инференса**, а не прогона целиком
(`manifest.latency_budget_s`):

| Категория | Профиль | Маршрут | Бюджет |
|---|---|---|---|
| `stt_error` | `diary_stt` | GPU | 5 с |
| `day` | `diary_sum` | GPU | 15 с |
| `day`, вызов **сведения** (T41) | `diary_sum` | GPU | 25 с |
| `week` | `diary_week` | CPU (`diary-sum-cpu`) | 180 с |
| `wellbeing` | `diary_coach` | GPU | нет (отчёт `n/a`) |

Недельные 180 с — решение пользователя («до 3 минут на операцию»), опирающееся на замер T13:
CPU-неделя до 126.5 с холодной. GPU-пороги не менялись: они калиброваны под тег на GPU.
Харнесс применяет бюджет своей категории и **не считает провал по латентности нарушением
инварианта** (T18): в отчёте это две отдельные строки, а в строке чанка — `FAIL:latency`
против `FAIL:content`.

### Единица бюджета латентности — один вызов (T40, решение 2026-09-22)

**Единица — вызов, не чанк.** Бюджеты 5/15/180 с калиброваны на **один** вызов модели, поэтому
и сравниваются с одним вызовом: харнесс измеряет **каждый** вызов слоя (обёртка `TimedProvider`
вокруг провайдера — измерение харнесса, а не свойство адаптера) и применяет бюджет к самому
долгому из них. До T40 с бюджетом сравнивалось **всё** машинное время чанка, и после T23 (слой
делит длинный день) любой корректно поделённый день был красным **по построению** — находка T35:
части 17.76 и 8.14 с плюс сведение 18.77 с. Числовые пороги при этом **не менялись** (решение
пользователя 2026-09-20, T21), а **общее** время чанка остаётся в отчёте: столбец `latency`
(суммарное), столбец `slowest` (то, с чем сравнивается бюджет) и блок `per-call latency` по
вызовам — цена деления видна, а не спрятана. Чанк из **одного** вызова оценивается **почти** как
раньше: оцениваемая фигура — этот вызов, а работа слоя вне вызова (сбор дня, NLI-гейт, запись
артефакта) в бюджет больше не входит. Живой замер трёх коротких дней (2026-09-22): чанк
13.36 / 7.54 / 7.60 с против вызова 10.33 / 7.20 / 7.36 с; приёмочный прогон тех же чанков —
10.05 / 8.80 / 8.16 с против 7.44 / 6.82 / 6.30 с, то есть из 15 с освобождено 0.24–3.03 с работы,
которая вызовом не является. У трёх измеренных коротких дней вердикт от этого не изменился (обе
фигуры ниже 15 с), но граница сдвинулась на эту работу: день, у которого **вызов** уложился, а сумма с
работой вокруг нет, теперь зелёный. Правило держали два теста (на момент T40):
`test_a_single_call_chunk_over_its_budget_stays_red`
(вызов 16 с — красный) и `test_a_slow_call_of_a_split_day_is_still_red` (один вызов поделённого дня за бюджет;
с T41 этот тест называется `test_a_slow_part_call_of_a_split_day_is_still_red`, а правило держат четыре теста —
раздел «Бюджет вызова сведения» ниже).

**Замер T40 (2026-09-22, живой прогон `--live --chunk day-04-long-wednesday`, профиль
`diary_sum`, `OLLAMA_KEEP_ALIVE=0` — режим T29 не переключался; после T39 день идёт в 4 вызова).**
Три прогона харнесса (третий — на финальной ревизии): 12.51 / 12.46 / 5.34 / **18.95** с,
12.86 / 12.46 / 5.63 / **18.95** с и 12.52 / 12.01 / 5.63 / **18.93** с (чанк целиком 72.07, 74.78
и 73.25 с). Проба с покомандным счётом endpoint того же дня:

| Вызов (4 = 3 части + сведение) | Токенов endpoint (вход / выход) | Латентность |
|---|---|---|
| часть 1 | 3508 / 524 | 13.52 с |
| часть 2 | 3490 / 440 | 12.13 с |
| часть 3 | 2062 / 65 | 5.63 с |
| сведение | 2414 / **924** | **19.16 с** |

**Части внутри 15 с, за бюджет выходит сведение** — вызов, возвращающий сводку всего дня (924
выходных токена против 65–524 у частей) и платящий те же 3.5–4.6 с холодной загрузки. То есть
красный вердикт живого прогона больше не следует из числа вызовов; он следует из времени одного
конкретного вызова. Разбор времени сведения по загрузке / префиллу / декоду в T40 не делался, и

слой прошёл путь заново): 8 вызовов вместо 4, время чанка целиком 144.61 с, самые долгие 17.20 и 19.74 с,
инварианты 1/1 зелёные. Число вызовов в отчёте — счёт самого харнесса (T40), поэтому повтор виден
как 8 вызовов, и бюджет применяется к каждому из них, а не к сумме. Границы и единица:
`docs/device-choice.md` §12, `ADR-016` §«Update 2026-09-22 — T40».

### Бюджет вызова сведения — свой (T41, решение 2026-09-22)

**Что решено.** Единица остаётся «один вызов» (T40) и числа частей **не меняются** (5/15/180 с,
решение 2026-09-20, T21); меняется одно: у **вызова сведения** — того единственного вызова, которым
дневной слой сворачивает части поделённого дня, — в `manifest.latency_budget_s` есть своя запись
**`daily_merge = 25`**. Само число — решение владельца (2026-09-22), а не округление замера: запас
над измеренным худшим случаем 19.74 с — **+27 %**. Это сняло последнюю красноту живого длинного дня.

**Почему его нельзя судить бюджетом части.** Это другой вызов, а не часть: другой шаблон
(`prompts/sum_daily/v2.md` против `v1.md`), и выход размером во **весь** день — **924 выходных
токена** против **65–524** у частей при входе 2414 (замер T40), плюс те же 3.5–4.6 с холодной
загрузки. Один и тот же порог на два разных по природе вызова смешивал категории: части уложились,
сведение — нет.

**Измерено по вызовам** (`--live --chunk day-04-long-wednesday`, `OLLAMA_KEEP_ALIVE=0`, конфигурация
не менялась; живой прогон 2026-09-22 на этой машине):

| Источник | части, с | сведение, с | при 15 с |
|---|---|---|---|
| живой прогон **до** T41 (ревизия T40) | 13.71 / 12.38 / 5.40 | **19.34** | `FAILED: latency` |
| два живых прогона **после** T41 | 12.35 / 12.08 / 5.30 и 13.39 / 12.56 / 5.68 | **17.77** и **19.16** | зелёный |
| три живых прогона T40 (журнал задачи) | 12.5–12.9 / 12.0–12.5 / 5.3–5.6 | 18.93 / 18.95 / 18.95 | `FAILED: latency` |
| приёмочные прогоны T40 | — | 18.56 / 18.43 | `FAILED: latency` |
| покомандная проба endpoint (T40) | 13.52 / 12.13 / 5.63 | 19.16 | — |
| прогон с **регенерацией** гейта (T40) | — | **19.74** (и 17.20) | `FAILED: latency` |

25 с выбраны по худшему из измеренных (19.74 с, прогон с регенерацией); запас +27 % — это запас на
разброс машины, а не новая калибровка. **Порог частей (15 с) и пороги остальных маршрутов не
менялись**, и ни один чанк под новый порог не подгонялся.

**Как харнесс узнаёт сведение — по версии промпта в самом запросе, а не по месту вызова.**
`SumDailyPipeline.build_merge_request` ставит на свой запрос `prompt_version = MERGE_PROMPT_VERSION`
(«v2»), части — `PROMPT_VERSION` («v1»); харнесс импортирует **тот же** константный `MERGE_PROMPT_VERSION`
из слоя (`MERGE_PROMPT_VERSION_BY_CATEGORY`), поэтому переименование шаблона не оставит
классификацию позади. Порядок вызова для этого не годится: день, который NLI-гейт отправляет на
повтор, делает **8** вызовов вместо 4 (части, сведение, части, сведение) — «последний вызов»
промахнулся бы мимо первого сведения целиком, «каждый N-й» требует ещё и допущения, что никакой
другой шаг не повторяется. Классификация по версии — свойство **запроса**, и она переживает повтор;
закреплено тестом `test_the_fold_back_is_recognised_by_its_prompt_version_not_by_its_place` (8 вызовов,
два сведения на разных местах) и `test_the_fold_back_budget_belongs_to_a_route_the_harness_can_recognise`
(набор ключей бюджета и набор распознаваемых категорий совпадают).

**Что видно в отчёте.** Строка чанка печатает и `latency` (сумма), и `slowest`; блок `per-call latency`
печатает **каждый** вызов со **своим** порогом; сводка по категории называет обе фигуры раздельно.
Порог, которым судился вызов, читается из вывода, а не выводится читателем:

```
  day-04-long-wednesday (4 call(s)): 12.35s (part < 15s), 12.08s (part < 15s),
  5.30s (part < 15s), 17.77s (fold-back < 25s) — slowest 17.77s, chunk total 70.80s
latency day: slowest part call 12.35s (budget < 15s), slowest fold-back call 17.77s
  (budget < 25s), slowest chunk total 70.80s
latency: 1/1 within budget (day < 15s, stt_error < 5s, week < 180s, day fold-back < 25s)
```

Обе стороны правила держат тесты: `test_a_fold_back_call_inside_its_own_budget_does_not_fail_the_chunk`
(сведение 19 с — зелёный, хотя это больше 15 с) и `test_a_fold_back_call_over_its_own_budget_is_still_red`
(сведение 26 с — красный), плюс `test_a_slow_part_call_of_a_split_day_is_still_red` и
`test_a_single_call_chunk_over_its_budget_stays_red` (часть и обычный день — по-прежнему красные).
Числа и границы: `docs/device-choice.md` §12, `ADR-016` §«Update 2026-09-22 — T41».

## Правила авторинга чанков

1. Только синтетический текст, придуманный для набора; ничего из `data/` (проверяется privacy-тестом, который сравнивает «фразы» golden-наборов с файлами под `data/` и скипается, если каталога нет).
2. Количества в текстах — **цифрами** (`2 билета`, `15:30`, `700 рублей`): проверка grounding ищет числовые токены, а словесные числительные («два») сделали бы её недостоверной (проверка `no_new_facts` нормализует их в цифры и требует цифру во входе).
3. Ни один вход не содержит запрещённых лексем (`диагноз`, `лечение`, `тебе следует`): иначе честный вывод, grounded в источнике, нарушил бы blacklist.
4. Ни один вход не содержит литерала `[?]`.
5. Сырая транскрипция STT — без заглавных букв и завершающей пунктуации: восстановление регистра и пунктуации — часть задачи правки.
6. Внутренняя согласованность: день принадлежит своей дате, неделя — своей ISO-неделе, каждая заметка ссылается на неделю, которая есть в наборе, и её `daily_ids` совпадают с днями этой недели.

## Как пользоваться

```python
from diary.domain.contracts.golden import chunk_path, load_chunk, load_manifest

manifest = load_manifest()
for chunk_id in manifest.chunks:
    chunk = load_chunk(chunk_path(chunk_id))
    ...
```

### Харнесс T10 (`eval/run.py`)

```bash
.venv/bin/python eval/run.py                      # CI: мок-провайдер, без сети и GPU
.venv/bin/python eval/run.py --strict             # требуются все 11 чанков
.venv/bin/python eval/run.py --chunk day-01-quiet-monday
.venv/bin/python eval/run.py --live               # реальный провайдер из configs/models.yaml
.venv/bin/python eval/run.py --live --models-config configs/models.example.yaml
```

- Каждый чанк прогоняется через **реальные сервисы слоёв** на временной SQLite-БД, которую
  создают миграции Alembic (по одной БД на чанк, каталог в `$TMPDIR`); провайдер
  инъектируется. Для STT/дневных чанков входные строки сеются в `messages`/`audio_files`/
  `transcriptions`, и харнесс сверяет, что дневной вход читается обратно ровно как
  объявленный (`collect_day_entries`); для недели вход подаётся контрактами `DailySummary`;
  для coach входная недельная сводка сначала сохраняется в хранилище T08, а затем
  используется слоем;
- режим `ci` — детерминированный мок-провайдер из `configs/models.example.yaml` (сеть, GPU
  и API-ключ не нужны). Мок **построен так, чтобы инварианты выполнялись**: он проверяет
  обвязку, а не модель. День, который слой делит, мок отвечает **на каждый вызов отдельно**
  (части — по записям этой части, сведение — по фактам поданных частей, `ci_call_payload`):
  один и тот же ответ на все вызовы положил бы весь день в сведение столько раз, сколько
  частей, и провалился бы бюджет сведения — то есть провалился бы мок, а не слой (T35;
  измерено: ответ дня в 2369 символов тратит 3849 из 4096 оценённых токенов сведения уже на
  двух частях и 4796 с трёх). Силу самих проверок доказывают негативные тесты
  `tests/integration/test_eval_harness.py` (совет, каузальная связка, выдуманное число,
  выдуманное числительное словом, выдуманное имя — каждое валит свой чанк), а части и бюджет
  по частям — `tests/integration/test_long_day_split.py` (T35);
- режим `--live` печатает таблицу «id чанка, категория, профиль, латентность чанка **целиком**,
  число вызовов, латентность **самого долгого вызова**, PASS / `FAIL:content` / `FAIL:latency`,
  имена провалившихся проверок» и метрики токенов; ниже таблицы — блок `per-call latency` с
  временем каждого вызова чанка, сделавшего больше одного вызова, и с **порогом, которым этот
  вызов судился** (`part < 15s` / `fold-back < 25s`, T40/T41); **содержимое дневника
  в отчёт не попадает** — только id, метрики и имена проверок.
  Итог — **два отдельных счёта** (T18): инварианты (с порогом `manifest.threshold`, 8/11) и
  латентность по маршруту (T21: правка < 5 с и день < 15 с на GPU, неделя < 180 с на CPU,
  у coach бюджета нет — `n/a`; T40: бюджет сравним с **одним вызовом**, строка отчёта называет
  `slowest call … , slowest chunk total …`; T41: у вызова сведения свой порог, строка называет
  `slowest part call … (budget < 15s), slowest fold-back call … (budget < 25s)`). Числа не
  складываются в одно;
- код возврата: `0`, если инварианты прошли порог манифеста **и** ни один измеренный чанк не
  вышел за бюджет латентности своего маршрута; иначе `1`. С `--strict` (CI) требуется больше:
  **каждый выбранный чанк должен быть измерен и пройти** — поэтому пропущенный чанк в
  strict-режиме означает провал (strict требует полного покрытия, а не «всех измеренных»;
  обычный прогон без `--strict` пропуск переживает, но требует порог 8/10 по измеренным).
  Провал по латентности печатается отдельной строкой и не выдаётся за нарушение содержания;
- **слой, выключенный в конфиге, — это пропуск, а не падение** (T19, §9.8): если профиля
  категории нет в конфиге (например, `diary_week` в конфиге без недельного слоя), чанки
  этой категории печатаются как `SKIP:profile_off`, в отчёт добавляется строка
  `skipped (profile off): N chunk(s) — <ids>`, и они **исключаются из обоих счётчиков**
  (знаменатель — измеренные чанки). Харнесс не падает трейсбеком и не считает пропущенное
  успехом; прогон, где не измерено **ничего**, заканчивается `FAILED: nothing was measured`.
  Тест-страж `test_the_example_config_resolves_every_category_profile` не даёт категории
  «уехать» в пропуски незаметно в CI.
